# 上游同步调度可扩展架构

## 目标与硬约束

Monitor 必须允许所有有消费的上游长期同时开启，账户数量从当前十余个增长到数十或上百个时，仍满足：

- 管理员保存账户、Key 和名称不被后台补数阻塞；
- 当天消费 Tail 优先，正常延迟目标不超过 30 分钟；
- 历史补数使用剩余容量，不能拖慢实时水位；
- 同一账户严格串行，保护 Sub2API 旋转 refresh token 和 AICodeWith 多 Key 原子发布；
- 不同账户相互隔离，一个上游的超时、429、鉴权失败或大客户日志不能拖住其他上游；
- 同一主机始终单请求、带启动间隔、Retry-After、退避和持久熔断；
- 页面只读 Monitor SQLite，用户刷新不访问上游；
- 窗口原子发布、游标单调前进、失败自动续跑，不把部分数据标成完整。

## 现有瓶颈

旧实现同时存在三个全局串行点：

1. 余额、日志和配置保存共用一把长锁；一次高量历史扫描可占用约两分钟。
2. 余额、日志和倍率依次运行在同一个一分钟循环；余额批次慢会直接推迟日志与倍率。
3. 日志每分钟只选择一个账户，并在同一轮里先 Tail 再历史补数；账户增加后，历史任务会挤占其他账户的实时水位。

因此，“读取现有配置失败”不是 Key 格式问题，而是保存请求等待全局锁直至超时后，带着已取消的 context 读取 SQLite。

## 目标架构

### 1. 控制面与数据面分离

- **控制面**：账户启停、Key 增删改名、人工重试。最高优先级，操作必须原子。
- **数据面**：余额、当天 Tail、历史 Backfill、倍率证据。只消费持久状态，可以中断、重启和续跑。
- 控制面不直接等待其他域名的数据面任务；同账户正在执行时明确显示“忙”，不能伪装成读取配置失败。

### 2. 按账户和主机双层隔离

- 账户门：同一域名只允许一个凭据相关操作，后台 try-lock，管理员操作优先。
- 主机门：同一 host 始终最多一个请求，防止同站点多账户触发限流。
- 全局门：限制 Monitor 对所有上游的总并发和请求启动速率；可配置但有硬上限。
- 账户失败只影响自身；429/网络/5xx 同时进入主机级退避和熔断。

### 3. 分级调度

| 优先级 | 通道 | 调度原则 |
|---|---|---|
| P0 | 配置保存、人工操作 | 下一次账户空闲时优先 |
| P1 | 当天 Tail | 按数据水位最旧优先，保障 30 分钟 SLO |
| P2 | 余额与余额预警 | 按到期时间公平轮转 |
| P3 | 最近倍率证据 | 不影响旧消费账单健康 |
| P4 | 历史补数 | 只使用 P1～P3 的剩余预算 |

P1 有积压时暂停发放新的 P4 配额；已经开始的窗口在安全边界结束后让路。历史补数不能和 Tail 绑定成不可拆分的长任务。

### 4. 公平与吞吐

- 调度单位从“一个账户一整轮”改成“账户 × 通道 × 有界窗口”。
- 使用最旧截止时间优先并结合轮转序号，防止低流量账户长期抢占，也防止高量账户永久饿死。
- NewAPI 分页断点逐页持久化；Sub2API 按自然日；AICodeWith 按 Key 子任务完成后整轮原子发布。
- 初期保持全局保守并发；验证后只增加跨主机并发，不提高单主机频率。

### 5. 持久状态与 ETA

每个账户、每个通道至少暴露：

- 当前水位、目标水位、剩余小时/天/页；
- 最近一次尝试、成功、失败及下次重试；
- 最近 15/60 分钟处理速率的指数移动平均；
- 基于剩余工作量和有效速率计算的 ETA；样本不足、退避或限流时不伪造 ETA；
- 当前是否因管理员操作、主机限流、全局容量或自身错误而等待。

## 分阶段实施

### 第一阶段：消除错误串行点

- 全局账户锁改为按域名账户门；
- 后台操作 try-lock，管理员保存优先；
- 保存超时从取得账户门后开始计算；
- 余额、日志、倍率拆为独立循环；
- 不改变请求频率、单主机并发、分页预算和数据口径。

### 第二阶段：实时与历史拆分

- Tail 与 Backfill 独立候选队列和预算；
- Tail 积压时历史自动让路；
- 增加公平轮转序号、积压量、速率和 ETA。

### 第三阶段：受控跨主机并发

- 默认同时在途 2 个不同主机，单主机仍为 1；
- 全局请求启动间隔保持保守，可配置且有硬上限；
- 所有 SQLite 发布通过短事务和 busy timeout，压测无 `SQLITE_BUSY` 后才逐步增至 3～4。

### 第四阶段：容量自适应

- 以 429、5xx、平均响应时间、Host Circuit、SQLite busy/WAL 和实例负载作为止损指标；
- 指标健康时缓慢加并发，异常时立即降到 1；
- 永远不自动突破单主机请求间隔和上游明确的 Retry-After。

## 上线原则

- 第一阶段只改变锁和调度归属，不改变消费金额、倍率、游标或历史范围；
- 第二、三阶段必须分别上线，不夹带；
- 使用生产备份 SQLite 和模拟慢上游、429、令牌轮换、四 Key 保存进行本机验收；
- 线上先保持并发 1，验证所有账户 Tail 正常、配置保存正常、无 SQLite busy 后再启用跨主机并发 2；
- 任一阶段都不得修改 NewAPI 代码、生产数据库或中转站 Nginx。
