# 第三小步：当前经济事实查询计划治理（仅本机）

## 目标与边界

缩短经营核算重建中的主库查询占用，减少单连接 SQLite 池被长查询占用的时间。只修改内部测试成本核验、共用经济账读取的同一类关联查询。

不修改金额算法、覆盖规则、发布和回填流程、缓存版本/有效期、连接池大小、表结构或索引；不连接生产，不部署，不提交或打 tag。前两轮未提交内容保持原状；无关 ECS 脚本未修改。

## 原因与修改

本地真实备份（5 月至 9 月）的 CPU/SQL 剖析发现：两次完整报表构建中，7 次当前经济事实查询累计约 3.67 秒。使用 Monitor 自带 SQLite 驱动的 EXPLAIN 显示，`p.hour_ts` 的范围传播使 `mp` 按供应商和整个日期区间反复查找，而不是按相同小时等值匹配。

新增小型共用查询构造函数 `currentEconomicsPublicationQuery`，两个调用点保留原有投影、范围、域名、排序和行数上限：

1. 用 SQLite `CROSS JOIN ... ON` 固定先读取当前 manifest 指针，再按 manifest ID 主键查发布头；ON 条件未删除，不是无条件笛卡尔积。
2. 明确选择原有 `idx_channel_economics_hour_publications_hour_ts`，按发布头的准确小时查子记录。该索引已在正式模型的 `HourTs` 字段和 AutoMigrate 中存在。
3. 仍同时验证当前 manifest 指针、权威账户 epoch、语义版本和子记录 current 指针；下游记录数量、发布集合哈希、金额完整性判断全部不变。

初版仅固定关联顺序时，供应商过滤回归发现 SQLite 又选中了 domain 单列索引，月组件反而变慢。未放行该版本；补齐小时索引约束后，有/无域名筛选均验证准确键查找。

## 本地对照结果

同一份不可变备份，不重新下载线上数据。旧查询通过临时验收回调恢复为修改前的 JOIN 和无索引提示形式，随后和新查询各运行冷构建、复用月组件构建。

| 项目 | 修改前 | 修改后 |
|---|---:|---:|
| 完整报表冷构建 | 4.45 秒 | 1.58 秒 |
| 复用月组件后的完整构建 | 1.54 秒 | 0.79 秒 |
| 两次构建内 7 次热点关联查询累计 | 3.67 秒 | 0.059 秒 |

归一化 `generated_at` 后，完整 JSON 字节一致（包括 5 个月、149 天及成本明细、金额、覆盖状态）；未归一化金额或缺口字段。现有历史缺口仍保留，不因性能优化消失。

这是本机该快照的性能测量，不是线上 SLA，也不是磁盘物理 IOPS 或长期并发写负载测试。未新增数据量上限；既有 500,000 行保护继续生效。当前 manifest 目录未来持续增长时，仍需持续评估长历史查询，不承诺无限规模恒定耗时。

## 测试

- 新增独立旧查询对照：多供应商、多小时、旧/新账户 epoch、历史/当前发布修订、供应商过滤、半开时间区间、空结果、行数限制。
- 查询计划回归：带域名过滤和无过滤都必须按 manifest ID、准确小时查找，避免只靠不稳定的机器耗时阈值。
- 取消查询后单连接池可以正常复用。
- 既有 manifest 缺失/哈希不符、零小时、权威 epoch、内部账号与自动测试分离、混合流量、并发发布等业务断言保持不变。
- 定向业务测试通过；定向 race 通过（31.496 秒）；`go vet ./...` 通过；前端 110 通过、1 项既有跳过。
- 本机断网、只读根文件系统 Docker（1.25 CPU / 768MiB）定向回归与真实备份构建通过。相同资源下旧查询冷构建 5.34 秒、复用月组件后 1.95 秒；优化后分别为 1.94 秒、1.04 秒。临时验收容器自动移除，不替换既有预览。
- 原始本地备份主库和事实库的 SHA-256 与验收前一致，私有对照报表仅在临时目录，没有加入 Git。
- 最终全量 `go test ./... -count=1 -timeout 360s` 全部通过（Monitor 包 265.875 秒）。默认跳过的外部验收用例不代表已做生产验收。

## 兼容与回退

查询依赖已有小时索引，正常启动的既有 AutoMigrate 负责维护。将来若改索引命名，需同步修改本函数及查询计划测试；不在请求过程中临时建索引。异常缺索引时查询明确失败，不冒充完整金额。

这次 SQL 等价优化不更改缓存键或计费语义版本。回退只需恢复两个调用点的原查询，不需要回滚数据库。尚未安排生产发布。
