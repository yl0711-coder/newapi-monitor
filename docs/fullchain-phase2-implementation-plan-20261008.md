### 必须遵循的映射约束

- 共享 `evidence_level` 只有 `exact/correlated/inferred/unavailable`。
  既有 `ambiguous` 是候选匹配状态，不是第五种共享证据等级；第二批应保留“多候选/不可唯一关联”的事实，
  与共享证据等级分开展示，不能简单改名后声称关联成立。既有 `telemetry_gap` 表达数据缺口，
  也不能作为共享 evidence level；它属于契约 `fault_class`，缺观察点时证据等级为 `unavailable`。
- `fault_class` 只使用 01.3 第 4 节枚举；异常已知但无法分类是 `unknown`，观察点缺失是 `telemetry_gap`。
  `configuration_drift` 是第 6 节指定的数据质量事件，不应添加为私有 fault class。
- 状态字段必须为 `observed_state/recommended_state/approved_state/applied_newapi_state`，
  不能自行简写成另一套 `applied_state`。前三层使用契约治理状态；实际层来自 NewAPI 只读配置快照，
  enabled/disabled、分组、优先级、权重不能冒充治理状态。
- 治理状态只用 `HEALTHY/SUSPECT/DEGRADED/QUARANTINED/RECOVERY_PROBATION`；事故严重度只用 `SEV0～SEV3`。
  `M0/M1` 是研发优先级，不进入运行时接口。严重度及响应目标已按 01.2 核对如下，不能仅凭名称猜定义。
- 机器时间按契约使用 RFC 3339 UTC；页面显示北京时间并保留时区。已有 Unix 时间接口通过兼容适配过渡。
- `schema_version` 必填；未识别的必需枚举或主版本拒绝并告警，不得静默转为 `unknown`。
  同主版本只增加可选字段；至少一个发布周期兼容当前与前一主版本，并由 CI 校验 Schema、接口与持久化枚举一致。

### 已确认的 SEV 标准与响应时限

| 严重度 | 01.2 定义 | 响应目标 |
|---|---|---|
| SEV0 | 全站文本 API 不可用、安全事件、严重错路由或大面积重复计费 | 2 分钟通知，5 分钟开始止损 |
| SEV1 | 主力模型或主渠道多用户持续失败、无可用备用 | 5 分钟通知，10 分钟首个决策 |
| SEV2 | 单渠道/分组退化但有备用，持续慢、429 或局部协议问题 | 15 分钟通知，30 分钟决策 |
| SEV3 | 单请求、低样本、短抖动或数据质量问题 | 观察或工作时间处理 |

以上是 B/C 期需要实现及验证的目标，不代表 A 期已具备 SEV 自动判断、Owner/ACK 或超时升级。
具体接收人、双通道、值班责任及演练证据仍待确认；既有 SMTP 告警不能算作完整 SEV 通知闭环。

### A 期交付清单

- `internal/observability/` 实现 `observability.v1`、四级证据、24 项故障、五个治理状态、四级 SEV 的基础定义与校验，

- `/ready` 新增 `source_quality`；排障投影附本次查询的来源质量。连续采集水位与查询局部完整性分开，

- 客户排障新增独立表单入口，不依赖已查到的业务日志行；复用受控 POST、原有时间窗和查询预算，不增加另一条采集链路。
- 新指标投影保持 FRT 与严格 TTFB/TTFE/TTFC/TTFT、thinking、工具事件、合法终态的区别，未取得相应观察点时返回未知。

上述结果是基于现有事实的**只读投影**，不是新的持久统一事件事实库。没有实现 Source Event 持久去重/重放、
Incident、Eval 联调或全节点数据质量治理；不能据此宣布 MON-001/002 整体验收完成。

### 无业务日志的排障入口

后端 investigation 接受时间、用户、路径、CloudFront ID 等信息，没有业务行仍可查询其他来源。
A 期已增加受限时间窗的独立排障表单，复用已有 POST investigation，不新建平行系统；
原始身份只进入受控请求体，不写入 URL、浏览器历史或响应投影。
回归与运行验收场景包括：没有业务日志、无可用渠道、仅有 CloudFront ID、仅有路径/用户、所有来源都没有证据。
“没有证据”不能被解释为客户没发请求或客户必然有责任。

### 指标语义

现有流式 `other.frt` 是首个 `data:` 事件延迟（FRT），已有独立覆盖、P50/P95/P99、样本数和实际窗口。
它不等于首个有效模型 token，不能伪装为严格 TTFT。

A 期已按 01.3 第 7 节建立指标字段、证据等级及未知值验证；实际缺失的协议观察点尚未补采。
后续继续落实观测点、分母及覆盖：TTFB 是响应头、TTFE 是首个合法协议事件、
TTFC 是首个用户可见内容、TTFT 是首个文本 token/delta，均相对请求开始。
thinking 与工具调用各有独立指标；控制事件可属于 TTFE，但不属于 TTFT；无文本的工具调用不能伪造 TTFT。
`other.frt` 只证明首个 `data:` 到达，未验证事件是否合法，不能直接把 FRT 改名为 TTFE、TTFC 或 TTFT。
旧 `firstTokenMs` 若混合文本/工具，仅在可从原事件重算时迁移，否则标为不可用。

协议成功按契约分别验证 Chat/Responses/Claude 的合法结构、顺序及终态；HTTP 200、断开、部分文本、费用
不能单独构成成功。Monitor 没有协议级观察点的记录继续明确标注“日志推断”，不凭统计升级为协议成功。
分位数同时展示样本和实际窗口，来源未覆盖时不能把缺失当成快请求。
客户端完整收到结果、retry/compact 只有经授权的客户端直接遥测才能作为 `exact`；`logical_request_key` 不得猜测。
若真正 TTFT 需要外部增加事件，先提出依赖并单独申请变更，不自动修改 NewAPI。

## 5. Incident、联调与恢复的详细设计约束

### Incident 与状态仲裁

- `incident_id` 由 Monitor 生成且全局唯一；聚合键严格采用 MON-003 所列六维，窗口只作观测属性。
  每个 Incident 只有一个主故障，可附多个伴随故障、observation 和 Eval Run。
- 同键冷却期间更新原 Incident；升级立即通知；配置变更前后用 `config_change_ref` 分段保留。
- `correlated` 最多支持 `DEGRADED` 建议；`inferred` 仅提供排查方向；`unavailable` 不支持健康或处置结论。
  即使 `exact` 也必须结合影响面和人工审批，不能直接隔离渠道。
- Monitor 异常但 Eval 正常时保持异常并继续真实流量观察；Monitor 正常/低样本但 Eval 确定性异常时按契约进入
  `SUSPECT`，重复确定性失败可建议 `DEGRADED`。任一关键源不可用时不判 `HEALTHY`。
- 人工覆盖记录理由、批准人、有效期和恢复条件，到期重新计算；审批与实际配置不符产生漂移事件，不互相覆盖。

### Eval 请求、结果与可靠投递

- 仅创建受控 Run，语义包括契约版本、Incident、Target、Suite、场景、时间窗、证据引用、预算策略和配置变更引用；
  不接受任意 URL、密钥、认证头、原始提示词或用户正文。
- 幂等键由 Incident、Target、Suite、配置变更引用组成：同键同载荷返回原 `eval_run_id`；同键异载荷报冲突、
  不新建任务，并产生契约要求的 SEV2 数据契约事件。成功受理仅表示排队。
- Eval 结果通过其 transactional outbox 发布。Monitor 按 `event_id` 幂等消费，重复事件不重复改状态或通知；
  撤回用新事件表示，不删除旧历史。旧事件只补证据，不能回退更新后的状态；双方详细设计应确定可校验的顺序/版本依据。
- 重试复用原幂等键与载荷哈希；限流遵守 Retry-After 并退避+jitter，暂时故障有界重试后进失败队列。
  参数/枚举、授权、目标不存在、幂等冲突不盲重试；大载荷改用 evidence ref，不重复投递原超大载荷。
  失败队列支持人工重放并保留失败原因。
- Target 按契约绑定唯一内部测试分组、定向目标渠道并关闭跨组重试；Monitor 只核验，不修改 NewAPI。
  Eval 的每次实际网络请求必须有 `attempt_id`，由 NewAPI 只读日志验证实际渠道/模型/分组/Attempt。
  命中不符或无法证明时结果不可用、故障为 `telemetry_gap`，不得参与准入、隔离或恢复。
  结果状态与四级 evidence level 是不同字段，不混用大小写或枚举。

### 两段式恢复门禁

1. **Eval 段**：原故障场景连续 5 次通过；30 分钟内至少 20 次文本请求、成功率至少 99%；
   流式请求全部合法终止、无同类连续故障、计费与路由命中一致。通过后只能建议 `RECOVERY_PROBATION`。
2. **Monitor 段**：经人工实施低权重/低优先级灰度 30～60 分钟，至少 50 个真实文本请求；
   错误率与 TTFB/TTFE/TTFT 回归近期基线，无关键错误和同类 Incident。通过并经人工审批才能回到 `HEALTHY`。
3. 60 分钟不足 50 请求不自动恢复；可延长至 24 小时。契约例外是两名负责人批准“20 个真实请求、两个独立时间窗、
   Eval 深度套件”，必须完整留痕。用户取消普通/超级管理员区分不等于自动取消这一批准要求；如需调整须另行明确，
   在此之前不启用低样本捷径。缺少门禁所需指标时显示门禁未满足，不用 FRT 代替 TTFT 通过恢复。
