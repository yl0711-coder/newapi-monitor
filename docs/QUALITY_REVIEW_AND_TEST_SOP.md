# Monitor / Usage 质量审查与测试 SOP

- 文档版本：1.0
- 生效日期：2026-08-03
- 适用范围：`newapi-monitor`、Usage Portal、Monitor 管理端、HostAgent，以及它们依赖的数据库、Redis、容器和网络配置
- 目标：用可重复、可审计、对线上低风险的流程发现功能缺陷、代码问题、性能风险、运维风险和安全漏洞

## 1. 基本原则

### 1.1 权限与修改边界

1. 用户要求“检查、审查、分析”时，只允许只读检查，不修改文件、配置或外部状态。
2. 用户授权修改时，只修改双方已经确认的范围；发现范围外问题，只记录和报告，不顺手修复。
3. 未经明确授权，不执行 commit、push、tag、合并、部署、重启线上容器或修改线上配置。
4. 工作区已有修改和未跟踪文件默认属于用户；除非明确纳入范围，否则不得修改、删除或提交。
5. 修改前必须记录当前分支、工作区状态、基线提交和本批次允许修改的文件或功能。

### 1.2 测试真实性

1. 不得用“看起来正常”代替测试证据。
2. 不得把未执行、执行失败或受环境限制的测试写成“已通过”。
3. 每项结论必须标记为：通过、有限通过、失败、未测试。
4. 测试报告必须记录命令、环境、关键结果和未覆盖项；不能只写“测试完成”。
5. 模拟数据测试、真实数据库只读测试和线上运行观测必须分别说明，不能混为一谈。

### 1.3 线上安全

1. 优先使用单元测试、模拟数据、本地数据库快照和本地 Redis，最后才使用线上只读数据。
2. 线上数据验证默认只读、单并发、最小时间范围、最少查询次数，禁止压力测试。
3. 未经授权，不对 NewAPI 数据库建索引、改表、写测试数据或执行数据修复。
4. 禁止在生产数据库执行可能完整扫描大表的探索性 SQL；执行前必须先在本地快照检查 SQL 和执行计划。
5. 线上验证发现异常负载、超时增多或服务状态变化时，应立即停止，不以“测完整”为理由继续施压。
6. 日志、截图和测试输出不得暴露数据库密码、Redis 密码、完整 Token、Session、Cookie 或用户隐私信息。

## 2. 三角色审查制度

每个批次必须分别给出技术总监、运维总监和测试总监三个视角的结论。任一视角存在阻断项，都不能得出“可以上线”的总评。

## 3. 技术总监审查手册

技术总监关注代码是否正确、清晰、可维护，并且修改范围与需求一致。

### 3.1 需求与改动范围

- 需求是否被拆成可验证的行为和验收条件。
- 实际 diff 是否只包含获准修改的内容。
- 是否存在半成品、占位代码、不可达分支、临时调试输出或遗留 TODO。
- 是否同时检查了被修改函数的调用方、被调用方和数据结构，而不是只看 diff。
- 新旧行为是否有明确兼容策略，是否意外改变公开接口、环境变量或数据格式。

### 3.2 代码质量与规范

- 命名是否表达业务含义，函数和结构是否职责单一。
- 是否存在过长函数、重复逻辑、隐式全局状态或难以追踪的副作用。
- 错误是否保留上下文并正确返回，是否存在吞错、误报成功或重复记录。
- 资源是否正确关闭，包括数据库结果集、HTTP 响应体、定时器、goroutine 和客户端连接。
- Context、超时和取消是否能够沿调用链传递。
- 并发读写是否有竞态、锁顺序问题、goroutine 泄漏或重复执行。
- 金额、Token、时间等关键字段是否使用合适的数据类型，避免浮点误差和时区歧义。
- 对外错误信息是否保留原始事实；稳定性报表不得将推测伪装成客观结论。

### 3.3 注释质量

- 注释应解释“为什么这样设计、有什么边界”，不重复代码表面含义。
- 缓存一致性、故障降级、权限边界、特殊 SQL 口径等非显然逻辑必须有注释。
- 注释必须与当前实现一致；过期注释视为缺陷。
- 不保留聊天式、临时性或无法验证的注释。

### 3.4 架构与可维护性

- UI、业务口径、数据访问、缓存和外部依赖是否合理分层。
- 数据源是否有唯一事实口径，避免不同页面各算一套而产生数字不一致。
- 可选组件失败时是否有明确行为，不能因为 Redis、HostAgent 等辅助组件故障拖垮主功能。
- 配置是否有安全默认值、清晰文档和启动时校验。
- 新依赖是否必要、维护活跃、许可证可接受、版本明确且无可达高危漏洞。
- 修改是否便于后续 NewAPI 升级，尽量不侵入 NewAPI 数据库结构。

### 3.5 技术总监必须执行或核对的检查

```bash
gofmt -d <本批次修改的 Go 文件>
go test ./...
go test -race ./...
go vet ./...
golangci-lint run --new-from-rev=<基线提交> ./...
go run golang.org/x/vuln/cmd/govulncheck@latest ./...
```

根据修改类型补充定向测试和多轮重复测试。全量 lint 中的历史问题与本批新增问题必须分开报告，不得混淆。

### 3.6 技术总监输出

- 改动范围是否准确。
- 代码质量结论。
- 可维护性和架构影响。
- 新增及历史问题列表。
- 阻断上线项、非阻断改进项和未验证项。

## 4. 运维总监审查手册

运维总监关注功能是否真的帮助运营人员发现问题，以及它是否会给线上系统带来新的风险。

### 4.1 运维需求与可理解性

- 页面是否能让非技术人员快速回答“哪里有问题、影响谁、从何时开始、规模多大”。
- 关键指标名称、时间范围、数据来源和统计口径是否明确。
- 空数据、延迟数据、采集器未接入和真实的零值是否能被区分。
- 状态和颜色不能只有视觉含义，必须有文字或数值辅助。
- 客观报表与建议性问题分析必须分开；建议必须明确标注为建议或可能原因。
- 错误详情应保留原始错误内容，不能用未经证实的总结替换。

### 4.2 数据库影响

- 列出新增或变化的每条 SQL、触发页面、最大时间范围和调用频率。
- 检查过滤条件、排序、分页、聚合、参数绑定和取消机制。
- 确认是否存在 N+1 查询、重复聚合、无界查询或把全部结果读入内存。
- 执行计划优先在本地快照检查；生产环境禁止未经批准执行 `EXPLAIN ANALYZE`。
- 检查连接池、查询超时和请求取消后 SQL 是否真正停止。
- 缓存必须减少重复查询；缓存故障时回源流量不能形成雪崩。

### 4.3 Redis 与缓存影响

- Cache key 必须包含所有影响结果的权限、用户、分组、Token、时间和口径维度。
- 验证 TTL、失效、成员变更、序列化失败、脏数据和版本升级行为。
- 验证冷缓存、热缓存、并发击穿、Redis 超时、认证失败、断线和恢复。
- 设置连接、命令超时和熔断/退避，防止 Redis 故障拖慢每个请求。
- 本地应保留有界兜底，必须限制条数、字节数和单对象大小。
- 缓存不得存储不必要的敏感信息。

### 4.4 容器与主机影响

- 核对 CPU、内存、磁盘、文件描述符和网络连接预算。
- 核对容器内存限制、健康检查、重启策略和优雅退出。
- 确认新增组件不会占用已有端口、覆盖其他容器或复用不属于本项目的数据卷。
- 检查基础镜像和运行依赖漏洞，确认升级不会破坏证书、时区、字体或健康检查。
- 部署、回滚和配置变更必须只作用于明确目标容器。

### 4.5 故障场景

至少验证或演练：

- Redis 不可用、超时、密码错误、返回损坏数据。
- 数据库不可用、慢查询、连接池耗尽、查询取消。
- 上游数据为空、字段为 NULL、数据量异常增大。
- Monitor 重启、Redis 重启、容器 OOM 前后的恢复行为。
- 配置缺失、配置错误、网络隔离和证书错误。
- 多实例同时运行时缓存和任务是否互相影响。

### 4.6 可观测性

- 健康检查应区分主服务可用与辅助组件降级。
- 日志应说明发生了什么、影响哪个组件，不得输出密钥和完整用户数据。
- 性能优化上线后至少观察接口耗时、数据库查询量、错误率、Redis 命中/错误和容器资源。
- 只有上线后的真实指标才能证明实际收益；本地网络耗时不能代替线上结论。

### 4.7 运维总监输出

- 非技术人员能否理解并使用该功能。
- 对 NewAPI、数据库、Redis、主机和其他容器的影响。
- 故障降级和恢复结论。
- 上线步骤、观察项、停止条件与回滚方案。
- 阻断上线项、非阻断风险和未验证项。

## 5. 测试总监审查手册

测试总监负责把需求转换成可重复测试，验证正确性、边界、兼容性、安全性和回归风险。

### 5.1 测试设计

每条需求必须建立以下对应关系：

```text
需求 -> 代码路径 -> 测试用例 -> 预期结果 -> 实际证据 -> 结论
```

测试数据至少包含正常值、零值、边界值、非法值、重复值、空值和大数据量场景。

### 5.2 单元测试

- 核心统计口径、时间边界、金额与 Token 计算。
- 缓存 key、TTL、失效、序列化、容量限制和敏感字段剥离。
- 权限隔离、用户/分组/Token 维度隔离。
- 错误传播、Context 取消和资源回收。
- 关键条件分支和历史缺陷的回归用例。

### 5.3 白盒测试

- 覆盖成功、失败、超时、取消、重试、缓存命中和缓存未命中路径。
- 检查数据库调用次数，证明重复查询确实被减少。
- 检查相同请求并发时是否只执行一次重计算。
- 检查缓存返回后，余额、用户名等实时字段是否仍从权威数据源获取。
- 使用 race detector 检查并发竞态，并重复执行关键并发测试。

### 5.4 黑盒与功能测试

- 登录、退出、Session 过期和无权限访问。
- 总览、成员详情、Token 详情、日志、筛选、分页和导出。
- 日期边界、跨月/跨年、无数据日期和最大允许范围。
- 页面刷新、连续切换筛选、重复提交和浏览器返回。
- 接口响应状态、字段结构和错误展示。
- Monitor 与 Usage 对同一事实口径的数字一致性。

### 5.5 边界与异常测试

- 0 条、1 条、最大分页量、最大导出量和长时间范围。
- 超长用户名、模型名、分组名、Unicode 和特殊字符。
- NULL、负数、小数、极大 Token、极小金额和舍入边界。
- 当天 00:00:00 至 23:59:59、时区转换和数据库时间格式差异。
- 用户换组、成员增删、Token 归属变化和权限变化。
- 请求取消时，应该取消的工作被取消，不应该影响的共享工作继续完成。

### 5.6 集成与故障注入测试

- 使用本地数据库/快照和真实本地 Redis 验证完整调用链。
- Redis 正常、停止、错误密码、不可达和损坏值分别测试。
- 重启 Monitor 后验证缓存和连接恢复。
- 数据源错误时不得缓存错误结果。
- 故障测试结束后必须恢复环境并再次执行健康检查。

### 5.7 性能测试

- 生产环境禁止压测；性能测试使用本地模拟数据或数据库快照。
- 对比改造前后的冷查询、热查询、数据库调用次数、内存和并发行为。
- 至少记录首请求和重复请求，不能只报告最佳值。
- 缓存优化必须证明数据一致，不能以牺牲正确性换取速度。
- 本地连接线上数据库的耗时只能用于排查，不能作为线上性能验收数据。

### 5.8 安全测试

- 管理员与普通用户数据隔离。
- ID 越权、Token 越权、Session 固定和未授权接口访问。
- XSS、CSV 公式注入、SQL 注入、敏感信息泄漏和日志脱敏。
- HTTP 超时、请求体限制、响应头和拒绝服务风险。
- 依赖漏洞、基础镜像漏洞和默认密码风险。

### 5.9 回归测试

- 修改前的已有功能必须有回归清单。
- 修复取消/缓存问题时，必须同时验证“应该取消的已取消”和“不该取消的没有取消”。
- 修复数据口径时，必须验证总览、明细、趋势、导出和不同角色显示。
- 新增可选组件时，必须验证开启与关闭两种部署模式。

### 5.10 测试总监输出

- 测试环境与数据来源。
- 用例、命令、次数和结果。
- 失败项、未覆盖项及原因。
- 功能、边界、性能、安全和回归结论。
- 是否建议进入人工验收。

## 6. 标准执行流程

### 阶段 0：确认授权和范围

1. 写明用户要求、明确不做的内容和验收目标。
2. 记录分支、基线提交、工作区已有修改和用户文件。
3. 如果范围不清会导致不同实现结果，先与用户确认；不能自行扩展。

### 阶段 1：建立基线

1. 在修改前执行相关现有测试。
2. 记录已有失败、已知 lint 问题和环境限制。
3. 对性能改造记录原始调用次数、资源占用或基准；无法取得时必须说明。

### 阶段 2：审查设计

1. 从三角色视角列出风险和测试点。
2. 对数据库、缓存、权限、时间和金额口径建立数据流图或文字调用链。
3. 确认失败策略、数据新鲜度、兼容性和回滚方式。

### 阶段 3：实现与代码审查

1. 只修改获准范围。
2. 优先补测试，再修复或同步补齐测试。
3. 完成后检查完整 diff、调用链和配置文档。

### 阶段 4：自动化测试

按风险由低到高执行：

1. 定向单元测试。
2. 全量单元测试。
3. 关键用例重复测试。
4. race、vet、lint 和漏洞检查。
5. 本地真实组件集成测试。
6. 故障注入和恢复测试。
7. 本地容器健康和资源检查。

前一层失败时，先分析原因；不得跳过失败继续宣称整体通过。

### 阶段 5：线上数据只读验证

只有本地自动化测试通过后才能进入本阶段。

1. 使用只读账号或只读隧道。
2. 先验证连接目标和权限，避免连接错库。
3. 默认单并发、短范围、单次冷查询；不循环请求、不批量导出、不压测。
4. 观察查询耗时和服务状态，发现异常立即停止。
5. 不修改线上数据库、Redis、容器或配置。

### 阶段 6：人工验收

向用户提供可访问地址和只需人工判断的项目，例如页面显示、操作流程、文案和数据业务含义。缓存命中、竞态、SQL 次数等技术项不得推给用户肉眼判断。

### 阶段 7：三角色签字

分别输出：

- 技术总监结论：通过 / 有限通过 / 不通过。
- 运维总监结论：通过 / 有限通过 / 不通过。
- 测试总监结论：通过 / 有限通过 / 不通过。
- 总体结论：可提交 / 可上线准备 / 阻断。

“有限通过”必须列明限制和上线前置条件。

### 阶段 8：提交与上线

1. 用户验收并明确授权后才能 commit、push。
2. CI 通过后再进行上线准备。
3. 上线前列出命令、影响范围、真正切换流量的步骤和回滚步骤。
4. 到真正上线步骤前停下，取得明确授权后执行。
5. 上线后观察真实指标；稳定后才宣布完成。

## 7. 缺陷等级与门禁

### 7.1 缺陷等级

- P0：数据泄漏、越权、破坏数据、主服务不可用、不可控高负载。
- P1：核心统计错误、缓存串用户、错误结果持久化、明显资源泄漏、无法安全回滚。
- P2：边界数据错误、性能退化、故障提示不清、局部功能异常。
- P3：样式、文案、可维护性和非关键体验问题。

### 7.2 阻断提交或上线的条件

- 存在未解决的 P0/P1。
- 核心测试、race、静态检查或可达漏洞检查失败。
- 数据口径无法解释或不同页面关键数字不一致。
- 未证明普通用户数据隔离。
- SQL 可能对生产数据库产生不可控负载。
- 无故障降级或回滚方案。
- 修改范围包含未经用户授权的内容。
- 关键测试未执行却无法说明原因和风险。

## 8. 每批次测试报告模板

```markdown
# <批次名称> 质量审查与测试报告

## 1. 范围
- 需求：
- 基线提交：
- 当前分支：
- 修改文件：
- 明确不在范围内：
```

## 9. Usage Redis 缓存专项清单

涉及 Usage 聚合缓存时，除通用流程外必须验证：

- 总览与明细使用同一统计口径，并证明不会重复执行重查询。
- Cache key 隔离日期、用户、分组、成员集合和 Token。
- 用户增删、换组或 Token 归属变化后不会命中旧权限结果。
- 当前余额、用户名等实时字段不被缓存结果覆盖。
- Redis 中不包含邮箱、完整 Token、Session、Cookie 和原始日志。
- 冷缓存与热缓存返回完全一致。
- 相同并发请求只触发一次重计算。
- Redis 停止、错误密码、网络超时和损坏 JSON 时安全回源。
- Redis 故障不会被无限重试放大，也不会缓存错误响应。
- 本地兜底缓存有 TTL、条数、总字节和单对象上限。
- Monitor 退出时正确关闭 Redis 客户端。
- Redis 恢复后无需重启 Monitor 即可重新使用。
- 开启 Redis 和不配置 Redis 两种模式均能正常运行。
