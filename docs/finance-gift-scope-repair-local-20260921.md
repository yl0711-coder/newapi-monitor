# 历史赠送分组依据：定向补齐第一小步

## 本轮范围

只增加单用户、单小时的后端修复原语及测试。没有注册 HTTP 写入接口、定时任务或自动队列，没有改变现有同步循环和主水位，没有修改生产、NewAPI 或本机验收数据卷；原始备份保持不变。本轮不是“历史数据已经修复完毕”。

## 真实本地缺口

只读检查 `local-data/production-snapshot-20260920-164220/usage-facts.db`：旧表没有 `grp` / `group_known` 列，也没有原始 NewAPI `logs` 表。现存顺序与金额事实不能推导历史分组，更不能使用用户当前分组替代。

总计 228,731 条、15 个用户、915 个“用户×小时”，其中 3,140 条金额为零。页面约 22.4 万条指所选范围、内部用户排除及非零金额等规则后的影响数，不能与全表行数混用。没有查生产，因此尚未确认这些历史原始日志在 RDS 或其他历史源中还是否保留。

## 修复约束

1. 原本用户小时必须完整、版本正确，且与目标来源 epoch 一致；顺序表的行数、逐条 hash、汇总 hash 必须先通过校验。
2. 每次只读一个用户一个小时的原始日志，复用原有 monetary 查询和 50,000 行上限，加 8 秒查询超时。不取 Prompt、密钥或请求体；本轮测试只用合成源。
3. 新旧逐条核对日志 ID、用户、发生时间、小时、类型、quota；总额相同但记录不同也拒绝。
4. 只能补充原先未知的分组；已经核验的历史分组不能被替换。来源缺失、被清理、重编号或聚合不一致时不发布。
5. 网络读取在本地事务外；发布前重新核对本地版本，发现并发更新就停止。沿用既有事务发布，同时更新明细和内容 hash，且再次核对用户小时金额与请求数。
6. 修复成功后重复调用不请求来源、不重复写入、不改更新时间；失败保留旧记录。主同步游标、用户金额事实和其他用户均不改。
7. 已有完整报表指纹包含赠送期初依赖的内容 hash。补齐历史后，依赖它的后续报表失效；不重算与其无关的后续月份基础事实。缓存保留旧值/异步更新机制未改。

## 本地验收

- 合成源：测试分组消费、业务消费、退款、内部账号排除，修复前不给出完整赠送结果，修复后按证据分配；没有重复扣赠送。
- 幂等与守恒：重复修复零写入；用户金额聚合、其他用户、主回填水位保持不变。
- 拒绝与回滚：缺少记录、ID 变化、总额不变但逐条金额变化、时间变化、用户变化、来源不可用、已知分组变化、来源 epoch 变化、聚合金额不符、并发发布以及事务插入失败。
- 真实旧库：测试只复制备份至临时目录，补上新版已有的列后读取一个真实用户小时（11 条）。没有原始分组来源时明确拒绝，11 条原事实和状态均未改变。没有为真实用户注入合成分组。
- 本机定向测试含真实副本通过，Monitor 测试耗时 1.478 秒；赠送修复、历史兼容、缓存指纹和平台毛利相关定向 race 通过（13.409 秒），`go vet ./monitor` 与 `git diff --check` 通过。本步未重跑整个仓库测试；没有改页面，未重新部署本机预览容器。
- 可复现命令：`MONITOR_GIFT_SCOPE_REPAIR_SNAPSHOT=<已下载且无活动WAL的usage-facts.db绝对路径> GOTOOLCHAIN=go1.26.6 go test ./monitor -run TestFinanceGiftScopeRepair -count=1 -v`。不设置环境变量时仅跳过真实备份用例，正常 CI 仍运行合成场景。
