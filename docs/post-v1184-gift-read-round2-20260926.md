# 第二轮第一小步：赠送证据读取与保守缓存（仅本地）

## 范围

减少经营核算重建时的赠送明细重复读取与原始明细占用；保持现有赠送优先、退款回补、内部账号排除、分组排除和未知历史分组处理算法不变。

本轮不做持久化钱包检查点、不改数据库表/触发器、不增加 Redis、不修改生产同步频率或连接预算、不上线。后台调度公平性和其他报表慢查询仍属后续工作。

## 实现

1. 原始赠送边界明细按当前需要的 `hour/user/epoch` 分批读取。每批最多 64 个键、预估 25,000 行；不可再拆的大小时单独读取。查询复用原有小时/用户索引。
2. 每批原始事件核验后转为原有标准账本，不再在内存中同时持有全部历史原始事件和标准账本。SQL 游标在批次之间释放；不持有跨整个报表的长读事务。
3. 复用已有有界缓存：最多 8,192 项、8MiB 载荷、单项 1MiB、30 分钟 TTL。元数据另有小量开销；过大项不入缓存，淘汰不改变金额。
4. 缓存键包含完整小时证明、当前业务分组/内部账号配置以及本地 SQLite 变更版本。每次仍读取并核验用户小时、赠送小时和边界覆盖台账。
5. 原有回归要求即使明细被修改而台账未更新，也必须拒绝发布。因此增加一个专用只读 SQLite 连接，仅用 `PRAGMA data_version` 检查提交版本，不执行写入、不长持读事务。任何事实库提交都会令旧缓存不可复用；缓存命中期间发生提交也按既有事实变更重试流程处理。
6. 只读版本检查不可用、内存库、缓存坏值/过期时，退回原始明细核验，不使用陈旧证据。连接随 Monitor.Close 关闭。

## 明确限制

这是保守的读取优化，不是“历史小时永不重算”：事实库有任何写入时，都重新核验。正在持续回填时缓存收益会减小；缓存容量不足也会限制收益。不为提高命中率放松原有完整性断言。

真正跨写入复用的持久增量钱包检查点需要独立设计修订传播与完整性依据，本次没有暗中加入。

## 本地证据

使用已存在的 2026-09-26 本地备份，数据库 immutable/只读打开；没有重新读取线上。临时对照函数来自已发布 HEAD 的原完整重算函数，不提交私有备份或对照文件。

- 总赠送分配、覆盖状态以及可完整核验场景的逐日分配：优化前、冷读、热读一致。
- 示例：带排除分组的赠送核验，原约 0.59s，热读约 0.43–0.46s。
- 不排除分组、账本较大的场景：原约 1.15–1.24s，优化后约 0.78–0.83s；8MiB 缓存无法全部容纳时，热读未明显优于冷读。
- 上述仅为赠送核验阶段，不是页面总体加载耗时，也不是生产 SLA。

新增测试覆盖未变化复用、查询尾部扩展、历史金额修订、未知分组修复、内部账号配置变化、缓存淘汰/过期/坏 JSON、并发读、取消、只读权限和关闭降级，以及缓存命中期间的明细未发布变更。

原有明细缺失、金额篡改、证据哈希篡改、台账哈希篡改的拒绝发布测试保持不变并继续通过；没有通过删除这些断言来换取缓存命中。

- 真实本地备份新旧算法对照通过，测试前后主库及事实库 SHA-256 保持一致。
