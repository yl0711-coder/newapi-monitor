# Monitor 功能与采集整合分析

## 1. 已确认的产品边界

1. Monitor 中所有数据同步的运行状态、历史补数、水位、积压、失败、重试、熔断、迁移、完整性、备份与修复操作，统一归属「数据同步状态」。
2. 「客户排障」由并行开发者负责。本次不直接改动该功能，只通过需求和接口契约输入。详见 [客户排障-问题与证据整合需求.md](客户排障-问题与证据整合需求.md)。
3. Monitor 「用户用量」与 Usage 客户站共用同一套本地用量事实，但页面、权限、用户对象和展示需求不同，不合并页面。
4. 「上游消费/倍率/成本」已经是「渠道管理」的内部能力，不是第二个独立页面。后续只需把导航和信息架构收敛为「渠道与成本」。

## 2. 现有功能实际职责

| 现有页面 | 实际回答的业务问题 | 主要数据来源 |
| --- | --- | --- |
| 用户用量 | 客户余额、每日消费、成员/客户分组、模型与分组消费、跟进客户 | 用量事实 SQLite，用户/余额快照 |
| 渠道管理 | 渠道流量归因、上游账户余额与消费、网站/上游倍率、未来成本与利润 | `stability_hour_samples`、`channel_upstream_usage_hours`、渠道/财务配置 |
| 模型监控 | 15 分钟至 24 小时的实时请求质量、错误、延迟、SLO、分组/渠道/模型/Key 维度 | `metric_samples`、`token_samples`、`hour_samples`、`rejection_samples` |
| 稳定性报表 | 1‑90 天的历史服务质量、稳定率、问题率、时间条和维度下钻 | `stability_hour_samples`、`stability_reject_hours` |
| 服务端监控 | 域名探活、源站锁、实例、数据库、负载均衡和运行告警 | `infra_samples`、主机容器快照、告警事实 |
| 容量规划 | RPM/TPM/并发估算、前置拒绝、入口节点占用、资源同轴、负载排名与扩容依据 | `metric_samples`、`rejection_samples`、`nginx_minute_samples`、`infra_samples` |
| 数据同步状态 | 各条采集/同步链路是否在跑、数据到哪里、为什么卡住、何时重试、是否完整 | 各个本地状态表、水位、worker 生命周期、SQLite/备份状态 |
| 客户排障 | 具体客户、令牌或 Request ID 发生了什么，请求走了哪个渠道，有什么证据 | 管理员主动查询时有界直读来源 `logs`；未来接入本地问题聚合 |

## 3. 目标导航结构

### 3.1 用户用量

保持独立，不与 Usage 客户站合并。

页面只展示客户与消费事实；移除全历史任务阶段、分页水位、修复队列、重试和燃断细节。这些统一进入「数据同步状态 / 用户用量事实」。

### 3.2 渠道与成本

由现有「渠道管理」改名，页内分为：

- **渠道总览**：主域名、厂商、实际渠道、服务分组和当前开关。
- **业务流量**：请求数、Tokens、用户侧消费以及流量占比。
- **上游账户**：账户、余额事实、账单消费事实和数据对应的实际时间区间。
- **计价配置**：网站分组倍率、上游基础倍率、折扣、充值比例和版本。
- **成本与利润**：后续在数据证据足够时接入成本、毛利、毛利率和余额可用天数。

上游凭据、站点类型、账户与手工计价基准仍在该页配置，因为它们是渠道的业务属性。但以下运行操作移到「数据同步状态」：

- 开启/停用后台余额同步；
- 开启/停用上游消费同步；
- 立即同步、历史补数、重试、退避和熔断操作；
- 下次执行、历史游标、当天追平、计价证据回溯进度。

配置保存时可保留一次有界的「连接验证」，但不要再隐式启动历史同步。

### 3.3 服务质量

合并「模型监控」和「稳定性报表」，但不强行合并两套数据粒度：

- **实时质量**：原模型监控，保留 15 分钟至 24 小时、SLO、延迟、错误、分组/渠道/模型/Key 维度和自动刷新。
- **历史质量**：原稳定性总览，保留 1‑90 天、厂商/分组/渠道/模型筛选、日趋势和详情下钻。

「问题与证据」不进入「服务质量」，按已确认需求交给「客户排障 / 问题聚合」。

实时与历史页的共通维度筛选可以统一交互和命名，但底层仍分别读分钟事实和小时事实，避免一次大重写。

### 3.4 运行与容量

合并「服务端监控」和「容量规划」，页内分为：

- **运行状态**：端到端探活、源站锁、实例、数据库、负载均衡、容器和运行告警。
- **业务吞吐**：业务 RPM、日志 RPM、前置拒绝 RPM、TPM、并发估算与时间趋势。
- **负载归因**：分组、渠道和模型的负载排名，用于定位扩容或局部不稳定的业务来源。
- **容量判断**：入口节点占用、CPU/内存/磁盘/数据库证据与业务负载同轴观察，数据不足时不自动给扩容结论。
- **扩容经济性**：待「渠道与成本」产出可信利润事实后，再计算增量资源成本和利润覆盖。

运行资源在原服务端监控和容量页重复展示，合并后只保留一份当前资源视图，容量视图主要表达资源与流量的时序关系。

### 3.5 数据同步状态

成为唯一的同步运维中心，而不只是一个展示页。建议页内按数据链路分区：

1. **总览**：服务中心状态、异常链路数、数据延迟上限、需人工处理任务和最近备份。
2. **NewAPI 本地采样**：来源 worker、租约、分钟指标、Token 维度、渠道快照和来源查询保护。
3. **用户用量事实**：近期服务窗口、实时 Tail、近 7 天窗口、全历史归档、成员水位、签收审计和修复任务。
4. **服务质量事实**：实时指标水位、历史小时汇总、稳定性重签、问题 Tail 与历史问题迁移。
5. **上游账户**：每个账户的余额、当天账单、历史补数、分页游标、限流、退避、熔断、对账和计价证据回溯。
6. **入口与基础设施采集**：Nginx 节点、前置拒绝、主机 Agent、AWS 资源、HTTPS 探活、源站锁以及各自的心跳、backlog、丢弃和水位。
7. **存储与恢复**：主 SQLite、事实 SQLite、WAL、磁盘水位、完整性检查、成套备份和恢复演练。

根管理员可在此执行重试、启停同步、小范围修复和手动触发；普通管理员只读。所有动作必须有幂等键、确认提示、审计记录和有界执行预算。

### 3.6 客户排障

保持独立。稳定性「问题与证据」整合为客户排障的「问题聚合」二级视图，由该功能开发者落地。本轮只维护需求契约，不与对方并行修改 `logchain` 代码。

## 4. 同步状态的统一数据模型

当前不同链路使用 `ok/error/stale/backfilling/paging` 等各自状态，前端在多处重复解释。建议后端统一为以下状态契约：

| 字段 | 含义 |
| --- | --- |
| `pipeline_id` | 稳定的链路标识，例如 `usage-facts`、`upstream:4sapi`、`nginx:ubuntu-1` |
| `enabled` / `serving` | 是否启用、该数据是否已被业务页使用 |
| `health` | `ok / warning / failed / disabled / unsupported` |
| `source_watermark` | 来源中已知的最新可读时间 |
| `committed_watermark` | 本地已原子提交、可供页面使用的时间 |
| `lag_seconds` | 两个水位的差，而不是简单的「距现在多久」 |
| `coverage` | 请求范围内的完整时段/成员/账户数 |
| `backlog` / `cursor` | 待处理量与持久化断点 |
| `last_success_at` / `last_error` | 最近成功和最近失败证据 |
| `next_run_at` / `retry_count` | 调度、退避和重试情况 |
| `circuit_state` | 熔断是否打开以及恢复条件 |
| `operator_action` | 是否需要人工操作，可执行什么安全动作 |

所有链路共用统一颜色和级别判定，避免同一个 `backfilling` 在一个页面是橙色、另一个页面变成异常。

## 5. 业务页如何不显示同步状态但不误导

集中同步状态不等于业务页可以把部分数据当成完整数据。建议做以下区分：

- **业务页保留的是数据边界**：统计时间范围、实际数据截止时间、未覆盖区间不显示为零。这是数字的口径，不是同步运维。
- **业务页删除的是运行过程**：补数百分比、游标、任务阶段、下次重试、失败原因、熔断、迁移和修复按钮。
- **全站顶部可保留一个统一数据健康指示灯**：只显示「正常 / 需关注 / 有异常」，点击后进入「数据同步状态」，不在业务页重复展开细节。

对于上游消费、成本、利润这类不能接受部分误差的结论，如果选定区间不完整，业务页不得给出「最终成本/毛利」；可以展示已覆盖子区间和明确的时间边界。

## 6. 现有采集是否重复

### 6.1 已经共用，不应重做

- 模型监控与容量规划已共用 `metric_samples`；容量页不需要再扫一遍生产 `logs`。
- 服务端监控与容量规划已共用 `infra_samples`。
- 历史稳定性与渠道使用排行已共用 `stability_hour_samples`。
- 稳定性近期小时事实由本地分钟事实滚动生成，实时路径不会因为展示两个页面就重复查生产库。
- Usage 客户站与 Monitor 用户用量已共用用量事实，不应再各自建一条同步链。

### 6.2 必须保留的独立链路

- 用户用量事实需要成员级、严格窗口和可签收数据，不能用全站分钟采样代替。
- 问题签名需读取错误原文后脱敏归一，不能从只有计数的指标事实反推。
- 上游余额、消费账单和计价证据来自不同上游 API，不能由 NewAPI 本站日志代替。
- 客户排障的请求明细是管理员按需直读，不应为了页面整合变成另一条全量历史复制任务。

### 6.3 当前应优先消除的重复

1. **状态解释重复**：用量、稳定性、渠道和容量页分别翻译水位和完整性，容易出现同一任务在两个页面颜色或结论不一致。
2. **状态读取过重**：当前同步状态页每 30 秒调用 `/channels/report?hours=24`，该接口同时组装渠道业务排行和上游账户数据。同步页只需账户状态，不应周期性计算完整业务报表。
3. **页面请求重复**：同步页和用量/稳定性等业务页会分别请求 facts/history/health 接口，再各自实现状态判定。
4. **资源展示重复**：服务端监控已展示实例/数据库/负载均衡，容量页又展示一次服务容量状态，应收敛为「运行当前值 + 容量时序关系」。

## 7. 同步状态页当前缺口

现有页已覆盖来源 worker/租约、SQLite/备份、用户用量事实、上游余额/账单/计价证据和稳定性问题采样。要成为全量管控中心，还需补全：

- 分钟指标、Token 维度和渠道快照的独立水位/失败信息；
- Nginx 每个节点的最近批次、backlog、断点、丢弃行与延迟；
- 前置拒绝每个来源节点的心跳和最近成功批次；
- 主机 Agent 和容器快照的节点心跳；
- AWS 采集、HTTPS 探活和源站锁检查的各自调度与失败；
- 网站分组目录、渠道快照及计价版本的最近成功水位；
- 统一的操作审计、重试结果和人工处理队列。

## 8. 接口整合建议

第一阶段不改底层采集，增加一个只读本地状态的统一聚合接口，例如：

```text
GET /sync/status
```

该接口只读各链路的状态表和水位，不执行业务报表聚合，不访问生产 MySQL，不访问上游 API，目标响应时间小于 2 秒。

现有 `/ready`、`/usage/facts-status`、`/usage/facts-history`、`/stability/health` 在过渡期保留；统一接口先作为组装层，验证口径稳定后再考虑收敛旧端点。

对上游账户新增轻量状态查询，不再让同步页周期请求完整 `/channels/report`。

## 9. 建议的改造顺序

### P0：先收敛状态，不改业务数据

1. 增加统一 `/sync/status` 聚合层和公共状态类型。
2. 补齐入口/基础设施采集状态。
3. 将用量修复、上游手动同步/重试和历史补数操作集中到同步页。
4. 业务页删除同步过程文案，但保留统计时间边界。
5. 增加全局一个数据健康指示灯和到同步页的跳转。

### P1：再收敛导航和页面展示

1. 模型监控 + 稳定性报表 → 服务质量。
2. 服务端监控 + 容量规划 → 运行与容量。
3. 渠道管理 → 渠道与成本。
4. 保留用户用量、数据同步状态和客户排障三个独立导航。

此阶段优先复用现有 API 和组件，不重写稳定性、用量、渠道或容量计算口径。

### P2：最后做跨域分析

1. 渠道收入、上游账单成本、倍率版本和毛利分析。
2. 运行资源、RPM/TPM/并发与稳定性的关联分析。
3. 扩容成本与利润覆盖。

这些功能依赖前两阶段的数据完整性和统一时间口径，不应与导航整合同时大范围开发。

## 10. 验收门槛

- 合并导航前后，用户用量、Usage、渠道汇总、实时质量、历史稳定性和服务端监控的数值必须一致。
- 业务页刷新不得因为页面合并增加生产 MySQL 或上游 API 访问。
- 同步状态页刷新只读本地状态，不运行业务聚合，不触发同步。
- 业务页不再出现任务阶段、游标、补数进度、重试时间或迁移错误。
- 任何未完整时段不得在业务图表中伪装成零值；成本/利润在证据不完整时不给最终结论。
- 页面合并后的旧 hash 路由仍能跳转到新页的对应二级视图，避免已有书签和告警链接失效。
- 本地快照模式、同步 worker 关闭、来源库不可用和上游限流时，各业务页相互隔离，不能因一条同步链失败拖垮整个 Monitor。
