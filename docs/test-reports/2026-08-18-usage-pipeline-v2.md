# Usage facts pipeline v2 本地与只读来源验收

日期：2026-08-18 CST

范围：只验收用户用量事实管道；使用日志明细本地化不在本报告范围。

## 结论

- 来源读取已改为单成员、有界时间窗、`LIMIT 1000`、稳定游标分页，不在 MySQL 执行大范围高维 `GROUP BY`。
- 每个分片必须经过两遍独立有界分页，事件数、请求/退款、tokens、quota 和语义指纹全部一致后才可生成小时证明。
- 分页事实、累计指标、滚动指纹与下一游标在同一 SQLite 事务提交；失败、退出、重启均从最后已提交页续跑。
- 低量成员自动扩展到不跨 CST 自然日的 24 小时分片；高量成员按 `24h -> 6h -> 3h -> 1h` 收缩。
- 每轮最多 3 页。公平调度使用持久单调序号，50/200/500 个成员全部为高量时，任一成员获得第二轮前其他成员均已获得一轮。
- 实时近期水位与冷历史水位独立；历史热点不能跳过或伪造近期水位。
- 服务窗口又与深历史拆分：先公平补齐“最近 7 个完整 CST 自然日 + 今日已闭合小时”，完整后才原子左移可读边界；冷历史继续低优先级扩展。
- 已发布成员和范围按 serving generation 与 fingerprint 绑定；一个成员损坏只撤销该成员，组织不完整时不返回假 0。

## 真实只读来源 pilot

已对一个已知高量成员的最近完整小时执行两遍只读分页：

- 原始事件：1,794 条。
- 每遍：2 页；两遍均完成。
- 单页最大约 0.95 秒，低于 5 秒 SQL 上限。
- 两遍事件语义指纹完全一致。
- 未执行任何写操作，未执行无界 `COUNT/SUM/GROUP BY`。

随后使用线上 Monitor SQLite 的本地副本、生产 `nexus_ro` SSH
隧道和当前代码镜像做了完整断点续跑（线上 Monitor 不写、不停）：

- 复用既有 migration v12 水位与原始分页状态，没有清库或重新拉取已完成历史。
- 已知高量成员依次完成 5,879、5,686、6,020、3,994、2,210 条事件的完整小时；每个小时均按最多 1,000 行/页执行两遍独立验证。
- 6,020 行小时在第一遍 7 页完成、第二遍进行到 3 页后经历容器退出；新镜像从第二遍第 4 页继续，最终校验 6,020 行一致并推进 live 水位，没有重复累计或跨过未完成小时。
- 升级时发现并修复旧版 1 小时分页检查点被新版 24 小时偏好错误解释的问题。持久检查点现在拥有其原始精确范围；完成后才由密度策略选择下一范围。
- 修复“成员首条日志位于当日 21:00 时，把 21:00 当作日证明键”的误判；只有完整自然日使用 CST 00:00 的日证明键。
- 真实续跑进一步发现：把首日志小时简单向前扩成 00:00 仍然错误，因为首个部分自然日本来没有完整日汇总。最终契约改为“首尾部分日逐小时验、中间完整日按日证明验”；删除任一小时证明的负向测试会 fail-closed。
- 释放本地旧误报任务的退避时间后，36/36 个 `full_history_local_audit` 均由新 worker 自行推进为 `complete`，`attempts=0`、`day_mismatch=0`，未伪造任务状态。
- 启动时在线成套备份与 live 写入短暂冲突产生一次 `SQLITE_BUSY`。该错误现在按本地锁竞争处理，约 30 秒后重试，不消耗来源失败次数，也不等待正常 5 分钟周期。真实重启中 live 调度恢复、已发布成员继续服务。
- 验收时 36 个活跃成员无 paused job；已发布成员由 32 增至 34，来源 lease 为 held、failure streak 为 0，容器 0 restart、无 OOM。
- 本轮改动后再次通过全仓普通、全仓 race、`go vet` 与 `golangci-lint`。

2026-08-19 凌晨又在同一真实 SQLite 卷上验收了服务窗口桥接：

- 边界按 8 月 19 日业务日锁为 8 月 12–18 日七个完整自然日，不再把“今天 + 前 6 天”误当完整七日。
- 最近窗口会直接复用已有冷水位，不重查 MySQL；只对冷水位和实时水位之间的缺口做有界分页。
- 真实开始时最近窗口从 15/36 提升到 34/36，高量成员的单小时已实测 13,941 条事件，按 14 页导入 + 14 页独立复核推进，无超时、无暂停、无重复累加。
