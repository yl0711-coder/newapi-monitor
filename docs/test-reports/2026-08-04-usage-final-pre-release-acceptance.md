本轮确认的代码问题已修复，最终代码态通过单元、边界、权限、竞态、随机顺序、静态分析、

生产 Redis 私网、ACL、`maxmemory`/淘汰策略、固定 Session Secret 属于部署前置条件，
本轮没有越权代替生产配置检查，也没有执行生产上线。

## 2. 本轮最终复审发现并修复的问题

| 等级 | 原问题 | 修复结果 |
|---|---|---|
| P1 | CI 的 Redis 服务未启用密码，但集成测试要求验证“错误密码必须快速降级”；无密码 Redis 会接受连接，导致真实 CI 必然失败 | CI 启动后为一次性 Redis 服务启用专用测试密码，健康检查与正常客户端使用正确密码，专项分支继续使用错误密码；本机按同一配置复现后全项目 `-race` 通过，健康检查在启用认证前后均保持 `healthy` |
| P1 | `.dockerignore` 只写根级通配符，实测 builder 中出现约 85 MiB 的 `.local-data/nexus_monitor.db`、审计文件和本机 `tools/`；最终运行镜像虽未复制这些文件，但本地/远程 BuildKit 缓存存在数据暴露风险 | 改为默认拒绝整个工作树，只放行 `go.mod/go.sum`、生产 Go 源码和内嵌前端资源；运行目录、`.env*`、DB/SQLite 和私钥格式作为第二道保险继续排除；新增正向源码断言与负向任意文件哨兵，builder 与两个最终镜像实测干净 |
| P1 | 主站用户名可进入待跟进区的内联 `onclick` JavaScript；引号/反斜杠组合可形成存储型 XSS | 显示文本不再进入 JavaScript 源码；元素只携带数值 `user_id`，统一使用事件委托，点击后再从内存数据取显示名；增加恶意文本回归测试 |
| P1 | Usage Portal 读取本地成员名单失败时忽略 SQLite 错误，可能把系统故障伪装成“本组暂无数据” | 增加明确错误链和统一 500 通用响应；服务端保留结构化日志，对客户不泄漏表名/SQL 细节 |
| P1 | CSV 虽由 Go 服务端分页流式输出，但前端仍用 `chunks + Blob` 把最多 5 万行完整积压在浏览器内存 | 改为短期 HMAC 签名预检票据，随后交给浏览器原生下载直接写磁盘；服务端仍保持每页 500 行和总量 5 万行上限 |
| P1 | CSV 预检与下载之间新日志可能进入结果，导致预检总数和上限判断漂移 | 预检一次取得 `COUNT(*) + MAX(id)`，票据绑定最大 ID 快照；下载从该游标开始，新到日志不混入本次文件 |
| P2 | 新增预检接口若被同一账号并发点击，可能重复执行昂贵 COUNT | 同组增加 5 秒原子预检窗口；成功下载的原有 5 分钟限额不变，不同客户组互不阻塞 |
| P2 | 缓存只有内部计数，运维无法确认 Redis 命中、回源、错误、退避和本机容量 | 增加管理员会话保护的只读 `GET /usage/cache-stats`；接口不 PING Redis，不返回缓存键、筛选条件或客户数据 |
| P2 | Redis 未配置、退避或逐键保护时也可能被记成远端 miss，指标会误导 | 只有实际访问 Redis 并得到 miss 才累计 `remote_misses`；本地模式和主动旁路不伪报 |
| P2 | `golang.org/x/crypto` / `x/net` / `x/sys` 落后于当前安全兼容版本 | 升级为 `x/crypto v0.53.0`、`x/net v0.56.0`、`x/sys v0.46.0`；三者最低 Go 版本均为 1.25，与 CI 一致 |
| P2 | 官方 `alpine:3.23` tag 内基础包可能落后于同一小版本仓库补丁 | Monitor 和 hostagent 运行阶段构建时先执行 `apk upgrade --no-cache`；本地最终镜像复核无落后包 |

此前四个性能提交及其 Redis 新旧值回流、删除/填充竞态、Portal 同页缓存世代、日期请求取消、
实时资料查询合并等修复，仍以

## 3. 数据库与运行影响复核

- 没有修改 NewAPI 表、索引、字段、数据或 SQL 权限。
- CSV 仍只读 `logs`：预检受全局用量查询闸门和 15 秒超时保护，分页受同一闸门和 25 秒单页超时保护。
- 普通小于 5 万行导出仍是一次计数后分页，未增加计数次数；超过 5 万行确认流程由票据复用预检，避免旧流程二次 COUNT。
- CSV 内存上限同时存在于两侧：服务端最多一页 500 行；浏览器不再持有完整文件 Blob。
- Redis 仍是可选优化，不参与鉴权和业务真值；连接池最多 8 个活动连接，单操作 150ms，错误后快速退避并安全回源。
- 缓存指标读取只访问进程内原子计数和有界缓存容量，不产生 Redis/数据库请求。
- 本地容器重建触发应用既有的一次启动采样；除此之外没有执行线上压测、批量导出或写操作。
- 修复前生成的部分本机 OrbStack BuildKit 记录仍被底层标记为 `shared`；实测解除单条历史引用并按精确 ID 回收仍被拒绝。它们不在 Git、最终镜像或运行容器中，也未上传远端；彻底清除需重置共享构建缓存，会连带降低其他项目后续构建命中率，因此本轮未越界执行。新构建已由默认拒绝白名单和 CI 门禁阻断同类数据再次进入。

镜像以非 root 用户运行，Alpine 运行包已更新。结论：未发现会放大线上负载或影响其他容器的代码阻断。

### 测试总监

正常、权限、篡改、存储故障、超限、并发连点、快照竞态、Redis 故障、前端语法和容器启动均有证据；

## 7. commit/push 后与上线前仍需完成

1. 提交前仍人工确认 `tools/` 未进入 Git；Docker 构建侧已有 `.dockerignore` 和 CI 双重门禁。
2. push 后等待 GitHub Actions 的带密码真实 Redis race、vet、govulncheck、lint、构建上下文隔离和双镜像构建全部通过。
3. 生产启用 Redis 前确认私网可达、独立 ACL、仅允许既定前缀与 GET/SET/DEL、`maxmemory` 和只淘汰带 TTL key 的策略。
4. 确认生产 `MONITOR_SESSION_SECRET` 为固定高强度随机值，DSN 仍为只读账号。
5. 真正替换生产容器前再次取得用户授权；上线后只做低负载健康、错误率、接口时延、数据库连接/慢查询、Redis 命中/错误和容器资源观察，不做线上压测。
