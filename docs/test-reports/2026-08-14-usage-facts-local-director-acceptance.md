## 1. 联合结论

**当前不能上线。** 代码层已经证明：当且仅当事实采集已启用、完整服务快照已发布、读取开关已启用且 `facts.read_active=true` 时，管理端和 Portal 的用量聚合会固定读取 Monitor 本地事实 SQLite，不再读取中转站 `logs`。原始日志分页、搜索和 CSV 导出仍按设计直接读取 `logs`。

不能把上述结论简化为“现在聚合都不读库”：

| 运行状态 | 页面聚合读源 | 对中转站影响 |
|---|---|---|
| 当前基线或两个 facts 开关保持默认 `false` | 直接聚合来源 `logs` | 与旧版相同，数据量越大越慢 |
| `ENABLED=true`、`READ_ENABLED=false`（Shadow） | 页面仍聚合 `logs`；后台同时回填事实 | 压力一定高于旧版，属于过渡态而非减压态 |
| 已请求切读但快照未完成/本地事实查询失败 | fail-closed，返回明确不可用 | 不允许静默回扫 `logs` |
| `facts.read_active=true` | 聚合、矩阵、日/分组/模型/令牌用量读本地 SQLite | 页面聚合对来源 `logs` 为零；只剩受控后台同步 |
| 原始日志分页/搜索/CSV | 仍读来源 `logs` | 已有限流、超时、游标/上限保护，但不是事实层范围 |

本轮已关闭会导致“页面无数据但数据库压力持续上涨”的主要代码缺陷，并完成 10,000 用户/200 关注成员/366 天的合成来源、200×366 事实库、256 MiB 容器 60 分钟混合负载、在线备份、全新副本恢复、Redis 跨进程命中、磁盘满和结构损坏演练。受测 API 全部成功且聚合页面来源 `logs` 查询数为零，代码正确性与纯本地合成容量门禁通过。

**这仍不构成上线许可。** 合成数据不代表真实峰值小时密度、维度基数和查询分布；20,000 格矩阵及 366 天全组织统计的冷 P95 未达到本报告原建议值；真实浏览器黑盒、脱敏实际分布、CSV/content 并发和最终 CI 镜像 digest 仍未验收。当前工作区只能作为本地候选，保持禁止上线、禁止连接线上补验。

## 2. 同步频率与数据延迟

设监测成员数为 `N`，成员批次数 `B=ceil(N/200)`。

| 同步任务 | 默认频率 | 单轮来源 SQL | 说明 |
|---|---:|---:|---|
| Tail | 每 5 分钟 | `3B` 条 `logs` SQL | 重读最近 3 个已闭合小时 |
| 用户/令牌资料 | 每 5 分钟 | `2B` 条 | `users`、`tokens` 各一条/批次 |
| 历史 reconcile | 每 30 分钟 | `B` 条 `logs` SQL | 每轮只复核 1 小时，近期窗口默认 8 天 |
| 首次/扩窗回填 | 每批次小时默认间隔 15 秒 | 总计 `H×B` 条 | `H=24×天数`；串行且前台等待时主动让路 |
| 本地 gap 审计 | 最多每 1 小时 | 0 条来源 SQL | 只查本地 proof，先 grouped count，再定位首个缺口 |

回填结束后，后台理论稳态为：

- 来源 `logs`：`36B` 条 Tail + `2B` 条 reconcile = `38B` 条/小时；
- `users/tokens`：`24B` 条/小时；
- 合计：`62B` 条来源 SQL/小时，即 `1488B` 条/天；
- 页面聚合在 `read_active=true` 后不包含在这个数值中，因为其来源 `logs` 查询数应为零。

首次 366 天回填的理论下限为 `36.6×B` 小时，90 天为 `9×B` 小时，且不含来源变慢、前台让路和失败退避。已存在且 proof/事实 hash 匹配的小时现在每轮最多跳过 168 小时，只推进本地游标，不重复查来源。因此 90→366 天扩窗只应补新增历史，而不是重扫已完成的 90 天。

延迟不是固定 10 分钟：

- 普通日志：10 分钟落库缓冲 + 0～60 分钟等待小时闭合 + 0～5 分钟 Tail 调度，约 10～75 分钟，均值约 42.5 分钟；
- 用户资料/余额/令牌快照：约 0～5 分钟；
- 最近 3 小时内晚到日志：下一轮 Tail，通常再等不超过 5 分钟；
- 3 小时至 8 天内晚到日志：依赖 reconcile；每 30 分钟仅复核 1 小时，完整轮转约 94.5 小时；
- 超过 8 天的晚到/事后修订：当前不会自动纠正，需要离线审计或受控补数。

事实变化会切换缓存 generation，所以正常情况下不会再额外等待完整 TTL；本轮还把候选世代与服务世代分离，新成员或扩窗的候选回填不会每 15 秒击穿仍在服务的旧快照缓存。

## 3. 缓存与返回量

当前候选使用两级可选缓存：

- L1：最多 128 项、总计 16 MiB、单项最多 4 MiB、最长 60 秒；
- Redis：活跃区间 60 秒、已结束历史区间 10 分钟；单操作 150 ms，错误后退避 30 秒；
- 同键冷请求通过 singleflight 合并为一次填充；
- Redis 只是可重算聚合缓存，不是事实源；原始日志、CSV、会话、当前用户资料和余额不缓存；
- 本地 facts 冷查询增加容量为 2 的并发闸门，避免不同 key 同时放大 SQLite CPU/RSS；计数由 `/usage/cache-stats` 的 `facts_read_budget` 暴露。

矩阵新增服务端硬上限 `20,000` 格（成员数×自然日数）。超过上限时在 facts/source 查询和缓存 fill 之前跳过，只返回成员资料及明确提示。边界测试确认 200×100=20,000 允许，201×100=20,100 拒绝且来源查询计数为零。

本地微基准中，20,000 格核心缓存 JSON 为 3,381,071 B；不同“成员数×天数”形状的完整响应约 3.41～3.91 MB，v3 黑盒 200×100 天为 3,905,822 B。原 2 MiB 单项上限会导致连续两次都重新查询；调整为 4 MiB 后核心值可以驻留，微基准热命中约 23 ms。60 分钟黑盒终态 L1 为 45 项/15,795,104 B，未突破 128 项/16 MiB；不得继续上调单项或总量上限。

主压测的固定工作集全部可由 L1 承接，因此 Redis 远端命中为 0，但这不表示 Redis 未使用：临时 Redis 实际有 18 个带 TTL 聚合键、约 8.81 MiB。离线恢复容器先填充、重启清空 L1 后再次黑盒，前置 3 个聚合及随后 16 个成员键全部命中 Redis，`remote_hits=19`、`source_fills=0`、`facts_read_budget.acquired=0`，证明跨进程缓存有效。

## 4. 查询效率与规模结果

### 4.1 本地事实读取

补充 `user_id,date_ts` 与 `user_id,day_ts` 复合索引后，查询计划已命中目标索引：

| 场景 | 本地结果 |
|---|---:|
| 单用户 90 天，组织 10/50/200 人 | 3.04 / 3.25 / 3.40 ms |
| 单用户 366 天，组织 10/50/200 人 | 6.96 / 7.18 / 9.33 ms |
| 200 人单用户 366 天，修复前 | 154.7 ms |
| 50 人×90 天全组织 stats | 148.9 ms |
| 200 人×366 天全组织 stats | 1.303 s |
| 50 人×366 天 matrix | 84 ms |
| 200 人×366 天 matrix（无护栏对照） | 348 ms，JSON 12.41 MiB |

200×366 的事实模型约含 292,800 条日事实和 153,600 条小时事实，SQLite 文件集约 93.4 MiB。全组织结果仍随“成员×日期×维度”增长；事实层只解除了对原始 `logs` 总量的依赖，并没有让大返回体免费。

400 用户×366 天×8 维的近似日事实测试中，daily/group/model/daily-model/matrix 冷查询分别约 149/345/367/469/137 ms。400×366 的最简矩阵约 16.2 MiB，现已被 20,000 格服务端护栏挡住。

不同 key 无缓存并发曾出现 32 个单用户 366 天查询 P50/P95=399/454 ms、RSS 约 196 MiB；8 个全组织 366 天冷查询 P50/P95 约 11.13 s。相同 key 有缓存/singleflight 时，32 并发单用户只 fill 一次，P50/P95=18/20 ms。本轮增加的 facts 读取闸门解决的是并发放大，不会缩短单个大查询本身。

### 4.2 来源 MySQL 对照

所有结果均来自本机临时 MySQL 或合成数据，不代表线上实测：

- 本轮目标规模源包含 10,000 用户、200 个关注成员、366 天和 1,468,800 条 logs。代表性最繁忙小时使用现有 `(created_at,type)` 索引，25 次 P50/P95/最大为 1.863/2.349/4.179 ms，执行计划扫描该小时全局 2,019 行并返回 389 个聚合维度；
- 临时增加 `(user_id,created_at,type)` 后，同一 SQL 的 25 次 P50/P95/最大为 1.268/2.431/6.603 ms，执行计划只在 200 个成员范围内返回 389 行。中位数改善约 32%，但 P95 和最大值没有改善；索引总空间从 752,648,192 B 增至 818,364,416 B（+65,716,224 B，约 +8.7%），50,000 行写入探针从 584.309 ms 增至 609.851 ms（约 +4.37%）。候选索引随后已从临时库删除；
- 200 万条 `logs` 的旧 Portal overview 约 4.79 s，累计约扫描 1000 万行；候选单小时事实批次约 4.34 ms、扫描约 925 行；
- 100 万条/30 天/1 万用户样本中，200 成员单小时事实 SQL 使用现有 `(created_at,type)` 索引，扫描该小时全局 1,389 行、约 11.5 ms；
- 临时增加 `(user_id,created_at,type)` 后只扫描匹配的约 30 行、约 0.29 ms，约 40 倍改善；
- 该索引结果只说明值得在目标规模本地克隆上评估，不授权修改线上索引。还需衡量 `logs` 写放大、索引体积、真实小时峰值密度和执行计划稳定性。

旧原始日志读取仍有边界：日志首屏已取消无条件 COUNT，CSV 预检改成最多 50,001 行的有界扫描；`content`/token name 包含搜索仍可能宽扫，因此新增关键词最小长度和日期硬上限，并在来源 SQL 前拒绝。目标合成源的 200 成员、7 天 token 包含搜索 60 分钟黑盒 P50/P95/最大为 365.987/404.732/434.616 ms；其中一条 MySQL 服务端样本检查 1,176,051 行、返回 51 行。

只读计划对照表明，保留 `ORDER BY id DESC` 而强制现有日期索引可把同一合成样本降到约 154 ms/251,410 行；改成纯 `created_at DESC` 可约 25 ms/35,959 行，但会破坏现有 ID 游标在同秒多行下的稳定分页。该优化对单成员、小组和真实时间分布也可能反向变慢，因此本轮没有把分布敏感的 hint 或排序变更写进生产 SQL。该接口按设计仍读 `logs`，必须与 facts 聚合零回源分开记账，也不能仅凭合成数据决定线上索引/游标改造。

## 5. 对中转站与 Monitor 的影响

### 中转站数据库

- Shadow 阶段会同时承受旧页面宽聚合与后台回填，压力短期上升，正好可以解释“Monitor 显示不出来但 DB 压力增加”的现象；
- `read_active=true` 后，聚合页面不再访问 `logs`，数据库压力由不可预测的页面访问变为按上表可计算的后台小时 SQL；
- 后台来源查询串行、每次最多 200 成员、单条默认 20 秒超时，并在交互查询等待时让路；所有用量来源泳道共享最多 2 条查询预算；
- 关闭 `READ_ENABLED` 会恢复旧宽聚合，不是数据库高压时的安全回滚；本地 facts 故障应 fail-closed，先恢复事实库。

### Monitor 本地资源

- 小时 proof 台账是主要磁盘增长项：200×366 约 1,756,800 行、约 308 MiB；成员日语义 proof 另有 73,200 行。连同约 93 MiB 事实数据，运行库量级超过 400 MiB，尚未包含 WAL、在线备份和 7 份保留；
- 目标集 live facts 为 414,384,128 B（约 395 MiB），`VACUUM INTO` 后单份约 392,000,000 B（约 374 MiB）。按 7 份保留并计入正在生成的下一份临时备份，facts 单项约需 3.3 GiB，尚未包含 WAL、主库备份和文件系统余量；200 人规模建议至少按 5 GiB 可用空间验收，不能只按 live DB 配盘；
- 400×366 为 3,513,600 条 proof。本地 warm SQLite 对照：全窗 Count 164 ms、group-by-member 199 ms、等价逐成员扫描 165 ms；原实现每分钟重复 gap/status 可扫描约 17.6M 索引项、消耗约 1.2 s CPU/分钟；
- 本轮把 status 覆盖进度改为按成员连续游标 O(成员数)计算，`coverage_basis=contiguous_member_cursor`；不再扫描小时 proof。gap 审计改为每小时最多轮转 10 个成员，200 人最长约 20 小时覆盖一轮；Tail/reconcile 和发布刷新不再重复执行大型 status；
- 新候选发布前的 200×366、4 维/成员日全量业务语义审计约 809 ms；累计分配约 506 MiB，但 14 天分批释放，结束时 Go live heap 约 9.65 MiB、HeapSys 约 27.34 MiB。稳态 14 天分片约 31 ms、累计分配约 19.4 MiB；366 天约 27 小时轮完，最近完整日和当前日每小时都检查；
- 256 MiB v3 容器 60 分钟混合负载共采样 593 次：内存 P50/P95/峰值为 82.3/106.7/128.2 MiB，前/后 5 分钟均值为 72.5/88.4 MiB；峰值未继续抬升且末段多次回落。CPU P50/P95/峰值为 2.95%/57.67%/126.57%（单核百分比），高点对应冷矩阵/统计 JSON；无 OOM、restart 或 non-running 样本。容器累计 Block I/O 约 701 MB 读/9.36 MB 写，3.88 GB 内部发送量主要来自每 500 ms 返回约 379 KB 的极端成员请求和 179 次约 3.91 MB 矩阵响应，不是数据库回源；
- 合成 MySQL 在同一小时内存 P50/P95/峰值约 2,338.8/2,375.7/2,385.9 MiB（5 GiB 本地限制，主要为 MySQL buffer pool/合成表），前/后 5 分钟均值 2,347.0/2,342.4 MiB；CPU P50/P95 为 0.45%/1.26%。45.16% 的单点峰值包含验收人员额外执行的只读 `EXPLAIN ANALYZE`，不能算作业务 SQL；无 OOM/restart。

### 7.1 隔离容器端到端烟测

在不连接网络的前提下，用本机模块缓存交叉编译当前 Linux/arm64 二进制，并覆盖到已缓存的本地验收运行镜像；随后启动独立的 Monitor/MySQL/Redis 三容器。该镜像只用于开发黑盒，不等同于最终 Dockerfile/CI 不可变镜像：标准 Dockerfile 的 `go mod download` 在 `--network=none` 下因本机构建层缺少一个 module 而按预期失败，本轮没有为此放宽网络限制。

- 网络：独立 `internal` Docker 网络，无外网出口；MySQL 使用 tmpfs，Monitor 使用单独的临时 bind 目录；未复用现有 `newapi-monitor-local-data`；
- 数据：1 个合成用户、1 个合成令牌、2 条日志（1 次 $1 消费、1 次 $0.2 退款）；Monitor 连接固定的 `monitor_ro` 只读账号；
- 回填：1 天窗口、5 秒/小时安全节流，最终 `24/24` member-hour 均为 `complete`，成员游标到达右界，`published_at/range_start/through` 和发布成员表均生成；
- 守恒：小时事实为 1 行、1 次消费请求、`consume_quota=500000`、`refund_quota=100000`，与合成来源完全一致；用户/令牌快照各 1；`PRAGMA quick_check=ok`；所有 fact/profile failure 时间均为 0；
- 日 proof：这个 1 天窗口的左右边界都在中午，没有一个可由自然日查询完整服务的闭合日，因而日事实/日 proof 为 0，当前范围由 24 个小时 proof 严格核验；这是预期边界而非漏数；
- 稳态来源计数：把 Tail/profile 临时加速到 1 分钟，在 65 秒 general-log 窗口内准确出现 2 轮 Tail，即 6 条 facts `logs` SQL，以及 `users`/`tokens` 各 2 条；没有历史游标重复 SQL。采样器自己的 2 条小窗口 SQL 单独出现，不计入 facts；
- 资源：Monitor 启动约 48.4 MiB/256 MiB，回填中约 46.5 MiB，完成后约 16.2 MiB；重启 0、OOM=false，日志无事实同步错误；
- 清理：临时 Monitor/MySQL/Redis、internal 网络、本地镜像、MySQL general log、合成 SQLite/SQL 和构建目录均已删除且不可恢复；既有 `newapi-monitor-local-acceptance` 与 `newapi-monitor-local-redis` 容器 ID/运行状态保持不变。

## 8. 尚未通过的上线阻断项

1. **真实分布与来源容量仍未知。** 10,000 用户/147 万 logs/200×366 已完成，但全是确定性合成数据。仍需经批准的本地脱敏克隆或等价统计分布，覆盖真实峰值小时密度、维度基数、晚到比例、写入并发和慢盘；在此之前不新增/强制任何中转站索引，也不把 2.35 ms 合成 P95 外推到线上。
2. **冷长尾和真实浏览器未签字。** 20,000 格热 P50 约 80 ms、返回约 3.91 MB，但混合负载冷 P95 约 1.81 s；366 天全组织 breakdown P95 约 2.18 s，均略超原建议。接口无错误且资源安全，但若总监坚持原时延门槛，需要进一步做矩阵分页/列式返回或预聚合，不能继续抬缓存/内存上限。当前环境没有可用的应用内浏览器实例，20,000/20,001、长用户名、不可用提示和低配客户端白屏仍缺真实 UI 黑盒。
3. **原始模糊搜索/CSV 仍是独立来源风险。** token 7 天黑盒 P95 约 405 ms，但服务端样本仍检查约 117.6 万行；content 搜索和 50,000 行 CSV 并发尚未在真实脱敏分布上验收。它们不属于 facts 聚合，不得用“聚合零回源”掩盖。
4. **最终 CI 交付物未验收。** v3 是当前源码在 internal 网络、只读本机 module cache 中编译后固化的本地不可变测试物，不是标准 Dockerfile/CI 产出的 SHA+digest。最终 CI 镜像必须重跑至少镜像身份、启动、恢复、20,000/20,001 和核心回归；不得为此连接线上。
5. **业务与运维口径仍需签字。** 普通延迟 10～75 分钟、3 小时外晚到最坏约 94.5 小时、8 天外须人工补数；Shadow 会短期加压，关闭 `READ_ENABLED` 会恢复旧宽扫。须明确补数审批人、来源重新承压的批准条件、磁盘告警与至少 5 GiB 容量预算。
