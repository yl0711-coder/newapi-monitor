## 3. 关键实现边界

### 3.1 Redis 正确性与资源上限

- Redis 仍是可选优化，不参与鉴权，故障不会让页面直接返回缓存错误。
- 逐键保护最多保留 4096 项，每项只有 1 字节值并由 LRU/TTL 淘汰；不会形成无界 map。
- 远端 `SET`/`DEL` 失败后，当前实例不会在保护期内读回该键旧值；下一次成功写入或删除会解除保护。
- 多键删除按完整键排序后取得闸门，避免锁顺序反转；源聚合只取得单键闸门，不形成循环等待。
- 仍只使用程序已知的完整键，不使用 `KEYS`、`SCAN` 或前缀批量删除。
- Redis 客户端最多 8 个活动连接，不在客户端内部重试；超时后继续走现有回源和查询并发闸门。

### 3.2 Portal 同页一致性

- 缓存口径版本仍为 `agg:v2`，没有让全部管理端聚合在上线时集体冷失效。
- Portal 新载荷使用此前不存在的 `overview` kind，因此旧 `matrix`/`stats` 键不会被读取，按原 TTL 自然淘汰。
- 首次正常打开仍执行原有矩阵与统计聚合；随后 breakdown 复用同一结果，不增加正常页面流程的日志扫描。
- 用户名、邮箱、余额、累计消耗和 Token 当前资料仍不进入聚合载荷，每次按既有逻辑实时补回。
- 本轮没有新增 SQL、索引、表或生产写操作；只改变已有聚合结果的缓存组织方式。

### 3.3 前端日期切换

- 选定新范围后，旧 breakdown、成员/令牌明细和日志请求立即 abort，旧响应也会被序列号丢弃。
- 新总览成功后才把该范围记为“最后成功范围”；失败则恢复日期控件，避免长期显示“新日期 + 旧数据”。
- Monitor 与 Usage Portal 都保持纯日期语义：开始日 00:00:00 至结束日次日 00:00:00 的左闭右开查询范围。
