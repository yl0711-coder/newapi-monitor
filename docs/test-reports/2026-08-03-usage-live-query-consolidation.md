## 1. 范围与边界

本批次只合并 Monitor 管理端和 Usage Portal 用户详情中对 `users` 表的重复轻量查询：

1. 管理端单用户：用一次主键查询同时读取用户名、邮箱、余额和累计消耗。
2. Usage Portal 单用户：令牌元数据补全时复用本地用户快照，最终仍由原有实时 `users` 查询校准，删除一次必然会被覆盖的查询。
3. 管理端组织汇总：余额合计和累计消耗合计从两条 SQL 合并为一条 SQL。

本批次没有修改：

- `logs` 聚合 SQL、查询闸门和日期口径；
- Token 查询的归属条件、脱敏、删除状态或累计消耗逻辑；
- Redis 键、TTL、本地缓存和强制刷新语义；
- API JSON 字段、前端页面和日期控件；
- NewAPI 数据库表结构、索引和数据；
- hostagent 及其他容器。

## 2. 实际 SQL 往返验证

修改后的数字由透传真实 SQLite 驱动的计数连接直接测得：测试不伪造 SQL 返回值，只统计运行时的 `users` / `tokens` SELECT。修改前的数字来自对基线 `c4f6df5` 调用链的逐条静态核对，未将旧代码与新代码同时编译运行：

| 路径 | 基线代码静态核对 | 修改后运行实测 | 结果 |
|---|---:|---:|---|
| 管理端单用户 | `users` 3 + `tokens` 1 | `users` 1 + `tokens` 1 | 通过 |
| Usage Portal 单用户 | `users` 2 + `tokens` 1 | `users` 1 + `tokens` 1 | 通过 |
| 管理端组织汇总 | `users` 2 + `tokens` 0 | `users` 1 + `tokens` 0 | 通过 |

合并后仍只使用 `users.id = ?` 或 `users.id IN (...)` 主键条件，没有 JOIN `logs`、没有模糊匹配、没有新增全表扫描。

## 3. 功能与边界兼容性

以下场景均有自动化用例直接构造数据或注入故障，并对返回结果做断言：

- 用户名为空时使用邮箱作为令牌 owner；
- 用户名和邮箱都为空时回退到 `#ID`；
- 负余额保留负数，不被误当成空值或零；
- `quota` / `used_quota` 为 NULL 时保留原有 `COALESCE(...,0)` 语义；
- 真实零值返回数值 0，不误返回 `null`；
- 主站用户已删除时，管理端金额返回 `null`、owner 回退 `#ID`，日志聚合仍可从缓存返回；
- Usage Portal 主站用户已删除时仍使用最近自愈快照，金额显示 `—`；
- 直接删除测试库 `users` 表注入 SQL 失败后，管理端、Usage Portal 和组织汇总均不中断历史统计，实时金额按约定降级；
- 组织内部分用户缺失时只汇总存在的行；全部缺失时仍返回合计 0；
- Token 查询仍独立失败、独立报错，不会因 users 查询合并而返回部分令牌结果；
- 强制刷新和缓存命中后，实时用户资料仍会立即取到新值。

核心边界用例连续运行 20 轮，全部稳定通过。

## 4. 技术总监视角

- 生产代码只改动 `monitor/usage.go` 和 `monitor/portal.go`，没有扩大范围。
- 用单一 `userLiveUsage` 表达单用户实时资料口径，消除余额、累计消耗和 owner 三条查询之间的重复。
- 令牌补全函数通过显式 `*string` 参数表达“已有 owner / 需要自行查询”，避免隐式全局状态。
- 旧的四个重复金额查询函数已删除，无残留调用。
- `gofmt`、`git diff --check`、`go vet ./...` 与全量 `golangci-lint` 全部通过。

## 5. 运维总监视角

- 本批次没有连接线上 MySQL，没有对线上服务发送查询或写入。
- 没有新增表、索引、迁移、定时任务或常驻内存。
- 每次查询仍受 5 秒 context 超时保护，请求取消可正常向下传递。
- 单次查询扫描范围没有增大：单用户仍为一行主键命中，组织仍只扫描名单 ID 对应行。
- 对主站数据库的改善是减少网络往返、连接占用和语句调度次数；不改变重查询并发闸门。
