## 1. 总体结论

**结论：本批功能、正确性、并发、故障降级、安全与本地容器验证通过，未发现阻断提交或人工验收的代码缺陷。**

本批达到的目标：

1. Monitor 和 Usage Portal 的昂贵日志聚合可以复用 Redis，减少相同权限域、相同筛选条件和相同日期范围的重复扫描。
2. 包含今天的活跃区间缓存 60 秒；已经闭合的历史区间缓存 10 分钟。
3. 管理端重新选择日期会携带 `refresh=1`，绕过旧缓存并以新结果覆盖缓存。
4. 用户名、邮箱、当前余额、当前累计消耗、当前 Token 元数据每次仍从权威数据源读取，不受聚合 TTL 影响。
5. 原始日志列表、CSV、Session 和完整 Token 不进入 Redis。
6. Redis 断线、超时、密码错误或记录损坏时，业务接口自动降级，不把缓存故障变成页面 500。
7. 本机 L1 最多 32 项、8 MiB、单项 2 MiB、最长 10 秒，并且不会把 Redis 记录的绝对过期时间再延长。

当前代码满足本地提交前门禁；尚未执行 commit、push、远端 CI、生产 Redis 配置或线上部署。

## 2. 已确认的数据新鲜度规则

| 数据类别 | 缓存策略 | 最坏可见延迟 |
|---|---|---:|
| 包含今天的矩阵、每日、分组、模型、Token 日志聚合 | Redis 60 秒；本机不超过 10 秒且不越过 Redis 绝对过期时间 | 正常打开最多约 60 秒 |
| 已闭合历史日期的上述聚合 | Redis 10 分钟 | 最多约 10 分钟 |
| 管理端重新选择日期 | 强制回源，成功后替换两级缓存 | 本次请求即为新结果 |
| 用户名、邮箱、余额、累计消耗、当前 Token 名称/分组/脱敏 key/删除状态 | 不进入聚合缓存，每次实时读取 | 当前数据源结果 |
| 原始使用日志、分页、筛选、CSV | 不缓存 | 当前查询结果 |

这套口径是性能、准确性和时效性的折中：高成本且可重算的聚合允许短时延迟，影响身份、权限和余额判断的实时字段不缓存，排障所需的原始日志不缓存。

## 3. 实现边界

### 3.1 缓存内容

- 管理端矩阵、每日/分组/模型聚合。
- Usage Portal 整组矩阵、每日/分组/模型聚合。
- 单用户和单 Token 的日志侧数字聚合。
- 硬删除 Token 的日志名称只作为历史日志回退字段保留；当前 Token 元数据不缓存。

### 3.2 明确不缓存

- 用户名、邮箱、备注和当前分组资料。
- 当前余额、当前累计消耗。
- Token 明文、当前 Token 名称、当前 Token 分组、当前删除状态和当前累计消耗。
- 管理端 Session、Portal Session 和任何认证信息。
- 原始日志详情、日志分页结果与 CSV 内容。

### 3.3 Key 与权限隔离

Key 包含：

- 口径版本 `agg:v2`；
- 管理端或 Portal 作用域；
- Portal 组织 ID；
- 服务端成员 ID 指纹；
- 起止时间；
- 用户 ID、Token ID；
- 聚合类型。

成员新增、移除或换组后，服务端成员指纹自然变化，旧权限域无法被新请求命中。删除只使用程序明确知道的完整 key，不使用 `KEYS` 或 `SCAN`。

### 4.2 缓存专项

已验证：

- 冷缓存计算一次，热缓存不重复执行聚合。
- 两个 Monitor 实例可以通过同一 Redis 复用结果。
- 同进程同 key 并发冷请求由 singleflight 合并。
- 普通请求与强制刷新并发时，较早开始的旧查询不能在刷新后覆盖新值。
- 刷新先执行时，随后普通请求复用刷新值，不再做一次旧计算。
- 等待同 key 计算的请求可以随 HTTP Context 取消，不会无期限占位。
- 刷新失败不缓存错误，也不删除上一份成功结果。
- 超过 2 MiB 的结果正常返回但不驻留；强制刷新得到超大结果时会删掉旧小结果，后续不会倒退。
- Redis 记录损坏或版本不符时只精确删除该 key 并重建。
- Redis 的剩余 TTL 小于 10 秒时，本机 L1 只使用剩余 TTL，不二次延长。
- 活跃区间 60 秒和闭合历史区间 10 分钟的边界按 CST 自然日判定。
- 关键缓存、管理端、Portal 与跟进复用路径重复执行 5 轮通过。
- 三个强制刷新并发顺序/取消用例重复执行 20 轮通过。

### 4.3 真实 Redis 故障注入

使用只绑定 `127.0.0.1:17379` 的本地 `redis:7-alpine`：

| 场景 | 结果 |
|---|---|
| 正常 SET/GET、跨实例命中 | 通过 |
| 错误密码 | 快速回源，业务结果正常 |
| 无监听端口 | 150ms 级快速降级，业务结果正常 |
| 上述集成组合连续 10 轮 | 通过 |
| Redis 记录损坏 | 精确删除并重建 |
| 本批此前执行的前缀最小 ACL 用户验证 | 10 轮通过，临时用户已删除 |

Redis 故障后有 5 秒远端退避和限频日志；本机短缓存继续承接已有结果。Redis 长时间不可用时，缓存命中能力会下降，但统一查询闸门仍保证同一时刻最多一条昂贵用量聚合访问 NewAPI 日志库。

### 4.4 数据正确性与权限

已验证：

- 冷缓存与热缓存返回相同统计口径。
- 当日志数据变化后，普通请求仍按 TTL 读取，管理端主动刷新立即看到新增数据；刷新后的普通请求继续得到新值。
- 矩阵缓存只保存稀疏消费格，用户资料与余额在响应阶段实时组装。
- Stats 缓存不影响组织余额、个人余额、累计消耗与 Token 当前资料。
- Token 聚合命中后，Token 名称、分组、脱敏 key、删除状态和累计消耗仍能反映数据源变化。
- Portal 越权用户返回 404；管理端 Session 不能用于 Portal。
- 缓存 key 覆盖权限、成员、时间、用户、Token 和口径维度。
- Redis 序列化载荷检查未发现用户名、邮箱、完整 Token、Session 或原始日志。
- CSV 公式注入防护和日志字段权限回归测试继续通过。

## 5. 发现并修复的问题

| 等级 | 问题 | 修复与证据 | 状态 |
|---|---|---|---|
| P2 | 普通冷查询和强制刷新使用不同 singleflight key，极端并发下较慢的旧普通查询可能在刷新成功后覆盖新缓存 | 新增同业务 key 的可取消计算闸门；先写失败回归用例稳定复现，修复后三类顺序/取消用例连续 20 轮通过 | 已修复 |
| P2 | Redis 命中后，本机 L1 若重新给完整 10 秒，理论上可能超过 Redis 原过期时刻 | Redis 载荷记录绝对过期时间，L1 使用 `min(剩余 TTL, 10 秒)` | 已修复 |
| P2 | 强制刷新得到超过缓存上限的新结果时，旧小结果仍可能留存，下一次普通请求倒退 | 超大刷新结果不缓存并精确删除旧结果 | 已修复 |
| P3 | 注释仍承诺未经容量测试的“100-200 人没事”以及固定 60 秒 TTL | 删除容量承诺；改为活跃 60 秒、历史 10 分钟的真实规则 | 已修复 |

未发现 P0/P1 级数据泄漏、越权、写入生产数据、无界内存或主服务不可用问题。
