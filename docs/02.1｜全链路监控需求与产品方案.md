# 02\.1｜全链路监控需求与产品方案

**状态：** 可进入研发分析
**维护时间：** 2026\-08\-25
**版本：** v2\.0

---

## 1\. 产品定位

Monitor 是文本渠道的真实流量观测和 Incident 管理平台。它负责发现异常、说明影响面、关联证据、通知值班和跟踪恢复，不进入用户请求链路，也不自动修改 NewAPI。

共享 fault class、evidence level、状态和指标以 [01\.3｜共享数据、状态与 Monitor\-Eval 联调契约 v1](https://scn7buedwig4.feishu.cn/wiki/UfbbwAnsyiEDRQkpabzc3lbIn4d) 为准，本文件不维护枚举副本。

## 2\. 用户与核心任务

|角色|核心任务|
|---|---|
|值班运维|发现异常、确认影响、ACK、执行人工止损和恢复|
|平台研发|定位入口、NewAPI、上游、资源或协议问题|
|渠道负责人|查看渠道趋势、容量、故障和恢复记录|
|测试负责人|从 Incident 创建 Eval 复现与恢复任务|
|管理员/审计|查看审批、配置快照、证据访问和操作轨迹|

## 3\. 目标与非目标

### 3\.1 目标

- 在持续流量下及时发现 SEV0/SEV1；

- 区分业务故障、监控盲区和低样本异常；

- 展示渠道、模型、协议、分组、节点和用户影响；

- 形成从告警、ACK、复现、处置、恢复到复盘的 Incident；

- 支持 24 小时事故、7 天趋势和 30 天基线；

- 为 NewAPI 人工处置提供可执行建议和回滚依据。

### 3\.2 非目标

- 不替代 NewAPI 权威使用和计费数据；

- 不凭单条日志或单次失败禁用渠道；

- 不在客户端证据缺失时确认 retry 或 compact；

- 不保存提示词、响应正文或密钥；

- 不自动写生产配置。

## 5\. 核心用户流程

### 5\.1 发现与确认

1. 系统按连续窗口、最小样本、相对基线和确定性硬错误生成 Incident；

2. Incident 展示当前严重度、治理状态、影响面和 evidence level；

3. 值班人员查看多源时间线并 ACK；

4. 数据源异常单独显示为监控盲区，不把业务状态显示为健康。

### 5\.2 Eval 复现

1. 在 Incident 中选择目标渠道、模型、协议和场景；

2. Monitor 按共享契约创建受控 Eval Run；

3. 页面跟踪排队、执行、结果和无法复现原因；

4. Eval 结果回写同一 Incident，不生成平行事件。

### 5\.3 人工处置与恢复

1. Monitor 给出建议状态和 NewAPI 操作清单；

2. 运维审批后按 [04｜NewAPI 渠道配置与异常处置方案](https://scn7buedwig4.feishu.cn/wiki/VeotwpV0LixR8HklNMDcB3gonRe) 执行并记录变更前后配置；

3. Eval 达到主动恢复门禁后进入 `RECOVERY_PROBATION`；

4. Monitor 达到真实流量窗口和样本门槛后回到 `HEALTHY`；

5. 观察期复发直接回退并保留原 Incident 关联。

## 6\. 信息架构

### 6\.1 总览

展示：活跃 SEV0/SEV1、渠道状态分布、数据源健康、最近配置变更、失败率、终态率、TTFB/TTFE/TTFC/TTFT、流中断、429/5xx 和计费异常。

所有指标必须显示时间窗、样本量和基线。数据未接入时显示“不可用”，不显示为 0。

### 6\.2 Incident 工作台

必须包含：

- 首次/最近发生时间、严重度、Owner 和 ACK；

- 渠道、模型、协议、分组、节点和用户影响；

- 主 fault class、伴随 fault class 和 evidence level；

- NewAPI、Nginx、reject、主机、边缘、Eval、客户端证据时间线；

- observed/recommended/approved/applied 四层状态；

- Eval Run、人工操作、回滚和恢复记录；

- 相关配置变更与去重说明。

### 6\.3 渠道详情

展示 24 小时、7 天、30 天趋势；按模型、协议、分组和节点下钻；显示备用渠道、最近 Eval、最近 Incident、配置变化和恢复复发率。

### 6\.4 数据源健康

展示每个 source/node 的最后成功、最后事件、lag、游标、丢弃、解析失败、凭证到期、版本和覆盖状态。

### 6\.5 检索与导出

支持时间窗、渠道、模型、协议、分组、fault class、严重度和状态检索。精确 request/user 查询使用 POST body 且不回显原值。导出默认脱敏、限量、限时并审计。

## 7\. 功能需求

### M0

|ID|需求|验收重点|
|---|---|---|
|MON\-001|多源统一事件|使用 observability\.v1，不出现私有枚举|
|MON\-002|数据质量|水位、覆盖、lag、丢弃和 telemetry gap 可见|
|MON\-003|Incident 去重|滚动窗口不重复建 Incident|
|MON\-004|连续窗口规则|最小样本、基线、硬错误和低样本分开|
|MON\-005|影响面|渠道、模型、协议、分组、节点和用户|
|MON\-006|状态机|四层状态和审批轨迹完整|
|MON\-007|SEV 通知|outbox、ACK、升级、静默和恢复通知|
|MON\-008|Eval 联调|创建 Run、回写结果、重放和 DLQ|
|MON\-009|人工处置包|建议动作、风险、回滚值和观察人|
|MON\-010|24h/7d/30d|事故、趋势和基线口径一致|

### M1

- WAF/CloudFront/CloudWatch 异步证据；

- 经验证的请求级 HMAC 关联；

- 授权后的客户端事件；

- 通知双通道、容量和灾备持续优化；

- 分区域视图和配置漂移告警。

## 8\. 告警与状态规则

|严重度|典型场景|连续性原则|
|---|---|---|
|SEV0|全站不可用、安全事件、严重错路由、大面积重复计费|硬信号可立即触发，其他需双源|
|SEV1|主渠道/主模型多用户持续失败、无备用|两个连续窗口或一源\+Eval/另一源|
|SEV2|单渠道退化但有备用、持续慢或 429|最小样本和至少三个窗口|
|SEV3|单请求、低样本、采集延迟或配置漂移|观察或工作时间处理|

初始阈值仅用于 shadow，至少运行 7 天后校准。`client_gone`、单次 429/5xx/timeout、语义质量和低样本比例不得单独产生隔离建议。

## 9\. 数据、安全与权限

- 只读采集和最小权限；采集、管理、敏感检索身份分离；

- 不采集 Authorization、Cookie、API Key、正文、thinking 或工具参数；

- `raw_error` 只保存脱敏摘要，结构化错误码单独保存；

- request/user/IP 使用带 key id 的 HMAC 标识；

- 管理操作、证据查看、导出和审批全量审计；

- 不直接挂载 Docker socket；使用受限代理或导出指标。

## 10\. 非功能要求

|方面|要求|
|---|---|
|旁路安全|Monitor 全停不影响 NewAPI 文本请求|
|可用性|月可用性设计目标 ≥99\.5%，外部探针测量|
|性能|核心页面和查询目标 P95 ≤2 秒，低样本/大查询降级|
|幂等|采集、Incident、通知和 Eval 结果均可安全重放|
|可回滚|数据迁移、规则和页面能力均有 feature flag|
|可观测|采集、规则、队列、通知、备份和数据新鲜度可监控|

## 11\. 产品验收

1. 数据源断开时产生监控盲区，不误报渠道健康；

2. 同一故障在连续窗口中只维护一个 Incident；

3. 状态和 evidence level 与共享契约一致；

4. SEV0/SEV1 告警包含影响面、样本、基线、证据和建议动作；

5. Monitor 与 Eval 的重复、乱序、超时和重放用例通过；

6. 敏感查询、导出、权限和审计通过安全验收；

7. 所有生产处置只生成工单/操作清单，自动 NewAPI 写入为 0；

8. 至少 7 天 shadow 后再评审正式阈值。
