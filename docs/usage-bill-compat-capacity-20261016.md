# Usage 账单：范围、历史兼容与容量第一轮

## 边界

只修改本机 `feat/usage-bill-export-r1-20261015`，未提交、未打 tag、未部署，不写生产数据库。
普通 CSV 的字段、类型筛选和 5 万条确认机制保持不变。账单不能截断。

## 本轮修改

- 账单保留日期、成员、模型、分组、令牌等筛选，但固定查询 type=2；不跟随页面错误/退款等类型选择，不局限于当前页。
- 将原始扣费是否存在与 Token/计费证据是否完整分离。旧日志缺少 billing_source、其他元数据或 Token 时，原始 quota 仍能导出；未知 Token 不填零，参考价格不能核验时留空。
- 原始 quota 缺失或负值仍阻断整份账单，不产生部分 CSV。真实零收费保留零。
- 明确订阅来源或订阅标识仍拒绝按钱包收费导出；这不是订阅兼容已完成，更不能静默漏掉订阅行。
- 账单路径不再先调用普通 CSV 格式化，再丢弃结果。金额仍以原始 quota / 500000 精确计算，未修改扣费规则。
- 对已支持 NewAPI 阶梯文本日志的默认 OpenAI 计量语义增加兼容：要求完整原始事实、wallet、已识别表达式格式、无歧义缓存关系、现有完整计费核验通过；零创建字段省略可表示 0。未知格式、Claude 歧义、TTL 冲突、显式 null 和核验失败不套用。
- 增加历史兼容接口回归与本机容量验收；正常 CI 跳过 opt-in 容量测试，不接触线上。

- Usage `TestPortal*`、金额内核测试通过；已保存 10 笔真实样本通过完整 HTTP 导出后与确认的 14 列逐格比较。
- 31 项前端日志及导出协议测试通过。
- 新增空元数据、无来源、异常元数据、NULL Token、NULL quota、真实零、订阅证据和页面选择退款时账单仍只取消费的测试。

## dx01 生产只读初查

通过既有 `dev/ai-production-readonly-access.sh raw-email` 核对邮箱对应 user_id=102。
仅读取北京时间 2026-10-15 14:00—15:00，一个闭合小时；单连接，每页 1,000 条，每轮最多 3 页，两轮之间和分页主动间隔；无写操作，结束后已关闭隧道。

- 两轮各取得 3,000 条，均未读完整小时，内容哈希一致。
- 每轮最大单页耗时分别 973ms、970ms；轮次总耗时包含主动节流等待，不能当成数据库纯处理时间。
- 工具是既有用量事实探针，包含 type=2/6 且有内部流量排除，不等同于 Usage 导出的全部字段/筛选协议；没有原始 other 解析或 CSV 生成，不是该账号完整导出性能验收。
- 不据此推算准确日/月数量。它已经说明不能假设“改成按月即可满足 5 万条限制”。

随后通过审阅后的本机私有工具，仅从同一闭合小时取得最新 1,000 条消费必要字段。强制用户时间索引并核对 EXPLAIN、2 秒查询预算、单连接只读事务设置、检查只读授权；不读取 content/Prompt/密钥，不保存管理员字段，仅保留计费边界标志。读取约 1.44 秒，结束后关闭隧道。

样本位于被 Git 忽略的 `local-data/dx01-export-readonly/source.json`，权限 0600；工具也在忽略目录，未加入产品代码。

- 1,000 条均为 wallet + tiered_expr，涉及 5 个 GPT 模型。
- 放入本机临时 SQLite 后，两个完整导出均通过逐行时间/模型/Request ID/扣费及总额核对；普通明细约 47ms / 564,249 字节，账单约 43ms / 146,525 字节。这不是生产数据库端到端耗时。
- **发现并部分修复的兼容缺口：全部 1,000 条省略 usage_semantic 和 cache_creation_tokens，原实现普通输入/缓存写入全为空。** 本轮补充受现有核验闸门约束的默认阶梯语义后，923 条可展示普通输入和缓存写入，实际收费、排序及条数全部保持不变。修正后样本账单 151,434 字节，本机生成约 57ms。
- 剩余 77 条按保护规则暂不推导：60 条零 Token 待核验，8 条附加计费/边界标志，9 条浮点舍入边界。这是当前 Token 推导与计费核验仍有关联的限制，后续要进一步区分计量证据与价格证据，不能为了覆盖率直接绕开保护。
- 1,000 条参考原价仍因模型覆盖不足留空。金额可导出不代表账单已完整可用，不能仅凭模型名猜测历史官方价格。
- 保留这份固定样本用于回归，不再次重复查询线上。大月量级仍需本机放大回放和后台任务验收。
