# 稳定性监控职责优化——技术要点与验收约束

> 版本：v1.0
> 日期：2026-09-02
> 状态：已评审，供技术设计、开发评审和测试验收使用
> 说明：本文不规定代码结构、数据库表结构、SQL、接口路径或部署命令，只定义技术事实、边界和必须满足的约束。

## 1. 技术目标

稳定性系统必须从“按日志行计算结果”升级为“按事实粒度和证据强度分类后计算结果”，并同时支持：

- 平台逻辑请求级结论；
- 实际渠道尝试级结论；
- 用户体验观察；
- 用户使用异常；
- 责任归属与置信度；
- 数据覆盖和口径版本。

技术方案可以自行选择，但不得破坏这些概念之间的独立性。

## 2. 事实粒度

### 2.1 逻辑请求

定义：用户认为自己发起的一次业务请求。平台发生多少次内部路由、重试和渠道切换，都只能形成一个平台最终结果。

约束：

- 同一个逻辑请求在平台结果中最多出现一次；
- 必须保留它与多个渠道尝试的关联；
- 无法可靠确认多个记录属于同一请求时，不得按时间接近强行合并；
- 逻辑请求标识缺失时，应降低置信度或进入未知。

### 2.2 上游尝试

定义：平台实际向某个上游渠道发起的一次尝试。

约束：

- 每次真实尝试独立记录结果；
- 尝试总数允许大于逻辑请求数；
- 只有实际渠道证据才能进入渠道可靠率；
- 被列为候选但未调用的渠道不产生尝试事实。

### 2.3 路由前事件

定义：在选择实际渠道之前发生的鉴权拒绝、参数错误、模型不支持、无可用路由等事件。

约束：

- 不得伪造实际渠道；
- 应保存当时请求分组、请求模型和可证明的服务承诺上下文；
- 候选渠道只能作为排障参考，不参与渠道稳定率。

## 3. 正交分类维度

任何事实都不应只保留一个模糊的 `status`。技术设计至少需要表达以下彼此独立的维度：

| 维度 | 建议状态 | 说明 |
|---|---|---|
| 事实粒度 | logical_request / upstream_attempt / pre_route_event | 防止请求数和尝试数混算 |
| 路由阶段 | pre_route / selected / upstream_attempted / edge_completed / client_confirmed | 说明请求走到哪一层 |
| 渠道归属 | actual_channel / candidate_channel / no_channel / unknown | 区分实际与候选 |
| 用户体验结果 | success / slow / partial / interrupted / failed / unknown | 描述用户可能感知 |
| 平台结果 | success / degraded_success / platform_failure / user_rejected / unknown | 用于平台口径 |
| 尝试结果 | success / failed / timeout / canceled / not_attempted / unknown | 用于实际渠道口径 |
| 责任类别 | user / platform / upstream / network / unknown | 与体验结果分离 |
| 证据来源 | newapi / nginx_access / nginx_error / upstream / client | 说明结论依据 |
| 置信度 | observed / high / medium / low / unknown | 防止推断冒充事实 |
| 覆盖状态 | complete / delayed / incomplete / unavailable / unknown | 控制报表可用性 |
| 分类版本 | versioned | 保证历史可解释和可重算 |

这些是数据契约要求，不代表必须集中存入单表。不同保留周期、权限和事实粒度的数据可以物理分离，但语义必须统一。

## 4. 指标口径约束

### 4.1 平台稳定率

正式分母仅包含能够确认是有效业务请求的：

- 成功；
- 降级成功；
- 平台失败。

用户拒绝和未知必须单列，不得通过排除未知后只展示一个高百分比。页面需同时显示：

- 有效分母；
- 用户拒绝数量；
- 未知数量和占比；
- 数据覆盖率；
- 分类版本。

### 4.2 渠道可靠率

仅基于实际渠道尝试。候选渠道、未选中渠道、路由前拒绝和渠道 ID 为 0 不得进入任何具体渠道分母。

取消与未知默认单列。若后续要纳入分母，必须有明确、版本化并经过业务评审的规则。

### 4.3 用户体验指标

用户体验与责任归属不得绑定。系统必须允许以下组合存在：

- 体验失败 + 责任未知；
- 体验降级 + 平台最终成功；
- 客户端断开 + 上游已失败；
- 服务端完成 + 客户端结果未知。

### 4.4 用户使用异常

必须独立于平台/渠道稳定率。异常数量、受影响用户数、连续发生和最近发生时间需要可查询、可聚合、可告警。

## 5. 请求关联与重试约束

- Request ID 或等价的稳定请求标识是关联首选依据；
- 同一逻辑请求的多次尝试必须保留顺序和最终结果；
- 仅凭用户、模型和相近时间不得合并为同一请求；
- 重试成功时，平台结果是成功或降级成功，失败尝试仍归属对应实际渠道；
- 同一请求最多产生一个平台主告警，但可以产生多个渠道子问题；
- 内部探测、自动测试和业务请求必须能区分，内部探测不进入用户业务稳定率。

## 6. 渠道归属约束

### 6.1 实际渠道

实际渠道只接受强事实：真实请求/尝试记录中明确的渠道 ID 或等价证据。历史渠道后来被删除、停用或改名，不得因此丢失历史实际尝试。

### 6.2 候选渠道

候选渠道只能用于回答“当时可能有哪些路由选择”，不能回答“哪个渠道导致了失败”。

候选渠道不得用于：

- 渠道成功率/失败率分母；
- 渠道故障排名；
- 渠道告警归责；
- 自动禁用建议；
- 历史责任定论。

### 6.3 当前配置与历史事实

当前配置不能作为历史时刻的确定事实。历史路由前问题至少需要判断：

- 当时是否对该用户/分组承诺提供该模型；
- 配置有效时间；
- 用户/令牌权限范围；
- 分组特殊可用规则；
- 模型映射或别名；
- 渠道是否当时可用。

在无法证明上述事实前，只能给出“当前配置上下文”或“历史责任未知”。

## 7. 服务承诺历史

为区分“用户请求未提供模型”与“平台承诺但无可用路由”，需要可审计的服务承诺历史。

其语义至少覆盖：

- 有效起止时间，采用无歧义的半开区间；
- 用户/令牌/分组适用范围；
- 对外可用模型及模型映射；
- 特殊可用分组；
- 配置版本或摘要；
- 来源和采集时间。

注意：该历史用于责任判定，不得直接用当前快照回填全部过去时间。缺少历史时必须归为未知，而不是批量判用户错误。

## 8. 证据等级与冲突规则

### 8.1 证据来源边界

- NewAPI 日志：说明平台记录了什么，不等于客户端实际收到什么；
- Nginx access：说明入口/边缘观察到的请求和响应状态；
- Nginx error：补充连接、上游、超时和协议异常；
- 上游日志：说明上游接收、处理或计费事实；
- 客户端遥测：在受控且可信时，才可确认客户端开始、终止、失败或成功。

### 8.2 结论措辞

- 强事实使用“观察到/记录为”；
- 推断使用“推断/疑似/候选”；
- 无证据使用“未知/不可判定”；
- 不得用服务器成功替代客户端确认；
- 不得用错误文本单独证明某一具体渠道责任，除非同时存在实际渠道证据。

### 8.3 冲突处理

多来源冲突时不得静默选取有利于稳定率的结果。需要：

- 保留冲突；
- 标记结论暂定或未知；
- 显示主要证据与反向证据；
- 允许后续规则版本重新分类；
- 对可能影响大量统计的冲突发出数据质量告警。

## 9. 特殊异常分类注意事项

### 9.1 不存在模型/无可用渠道

不能仅凭当前候选渠道是否存在判断责任。正确顺序是：

1. 确认请求模型、用户/令牌分组和请求时刻；
2. 确认当时服务承诺；
3. 判断是否进入路由、是否有实际渠道；
4. 再区分用户未被提供、平台承诺未履行或证据不足。

### 9.2 客户端提前断开

`client_gone`、`context canceled` 等不能一律判用户责任，也不能一律判渠道失败。需结合上游错误、边缘状态、输出进度和计费事实；无法判断时归未知责任。

### 9.3 流式交付

HTTP 200、服务端写出或出现计费记录均不等于完整交付。需要区分：

- 开始响应；
- 收到有效内容；
- 正常终止；
- 中断/裸 EOF/缺终止标记；
- 客户端确认（若有）。

### 9.4 零输出与计费

零 completion token 不能跨所有模型类型直接判异常。文本、图像、音频或其他协议需使用各自的有效输出证据。订阅、钱包或不同计费模式的“已扣费”定义也必须区分。

### 9.5 未知错误原因

新出现的错误码、错误文本或结束原因必须默认进入未知/待分类，不能默认成功。分类规则升级后，应能识别其版本和受影响范围。

## 10. 数据覆盖、封口与可重算

### 10.1 覆盖判断

每个时间窗口至少需要判断：

- 关键来源是否有数据；
- 数据是否晚于允许水位；
- 是否存在时间缺口；
- Request ID 覆盖是否满足逻辑请求统计；
- 分类规则是否覆盖主要状态；
- 是否仍有待补数据。

### 10.2 时间窗口封口

正式历史指标应以完成封口的时间窗口为主。未封口时间可实时展示，但必须标注“进行中/可能变化”。迟到数据到达后应按规则修正，不得永久丢失。

### 10.3 可重算与版本

- 分类规则和指标口径必须版本化；
- 历史结果应能解释使用了哪个版本；
- 规则升级后允许重算，但不得无记录覆盖旧结论；
- 页面应说明因规则升级发生的统计变化。

## 11. 数据守恒要求

任一完成封口的时间范围内，应满足：

> 平台逻辑请求总数 = 成功 + 降级成功 + 平台失败 + 用户拒绝 + 未知

正式平台稳定率的有效分母只取其中明确可判定的有效业务请求，但其他类别不得丢失。

同时应满足：

- 一个逻辑请求只进入一个平台最终结果；
- 一个逻辑请求可以有多个实际渠道尝试；
- 渠道尝试总数可大于逻辑请求总数；
- 每次实际尝试最多归属一个实际渠道；
- 未知单列，不以成功或失败补齐；
- 用户使用异常不进入平台/渠道稳定率，但仍包含在总体事件审计中。

## 12. 性能与线上保护

- 模型监控和稳定性报表刷新只读取 Monitor 本地事实/聚合结果；
- 页面操作不得触发生产 NewAPI 数据库、上游站点或 Nginx 文件的即时全量查询；
- 实时计算和历史重算必须有资源上限，不得挤压用户用量、Usage 日志、渠道同步等既有任务；
- 历史补算应支持限速、暂停、断点续作和失败恢复；
- 查询范围、导出规模和管理员明细访问应有边界；
- 同类采集数据应共用，避免模型监控、稳定性报表和客户排障重复采集同一日志；
- 数据延迟优先诚实展示，不得以加大生产源查询压力换取页面“实时感”。

## 13. 安全与隐私

- 原始请求、邮箱、令牌、IP、错误正文和客户端信息按敏感数据管理；
- 聚合报表默认脱敏，只有客户排障授权角色可查看请求级证据；
- 不记录完整密钥、Authorization 或可复用凭证；
- 导出和接口返回遵守最小必要原则；
- 请求级证据访问需要可审计；
- 不同来源的保留周期应与排障价值和隐私风险匹配。

## 14. 兼容、迁移与回退约束

- 不修改 NewAPI 源代码；
- 不假设必须修改 Nginx；若确有必要，需独立评审、双节点无感操作和回退方案；
- 新分类先影子运行，不能直接覆盖既有正式报表；
- 新旧口径在同时间窗口做总量、分类和样本对账；
- 旧指标在过渡期改名为“日志行稳定率/历史日志推断”，避免与新平台稳定率混淆；
- 正式切换前至少观察一个完整业务周期和一次高峰；
- 回退只能回退展示和分类版本，不得删除已采集证据；
- 任何迁移不得阻断 Monitor 用户用量、Usage 日志和渠道管理。

## 15. 告警技术约束

- 告警必须基于已封口或满足实时最小样本/持续时间的数据；
- 平台、渠道、用户体验、用户使用和可观测性告警分别计算；
- 同一事件应去重并维护首次、持续、升级、恢复状态；
- 数据采集失明时优先告警可观测性，不得误发“业务已恢复”；
- 告警应携带分类版本、覆盖状态和证据置信度；
- Monitor 只做观察、通知和建议，不直接控制 NewAPI 渠道状态。

## 16. 黄金样本与测试要求

研发前必须准备真实脱敏样本，至少覆盖：

1. 单渠道成功；
2. 多渠道重试后成功；
3. 多渠道全部失败；
4. 平台承诺模型但路由前无可用渠道；
5. 用户请求未提供模型；
6. 历史服务承诺无法确认；
7. 无效令牌、余额不足、权限不足、400、413；
8. 上游 429、500、502、503、超时；
9. 流式正常结束、裸 EOF、部分输出后中断；
10. 客户端提前断开；
11. 已计费零有效输出；
12. 非文本零 completion token 的正常请求；
13. Nginx 入口 5xx 但无 NewAPI 日志；
14. 内部自动测试请求；
15. 关键采集缺失、延迟和恢复；
16. 新出现的未知错误/结束原因。

每个样本需预先确认：平台结果、各渠道尝试结果、体验结果、责任、证据等级、是否进入各分母、预期告警。

## 17. 必须通过的验收门槛

### 17.1 正确性

- 重试链不会把一次请求重复计入平台分母；
- 候选渠道不会进入实际渠道指标；
- 用户误用不会降低平台/渠道稳定性；
- 平台承诺未履行不会被错误归为用户问题；
- 数据不完整和未知错误不会被归为成功；
- 实时和历史对重叠窗口使用同一版本时结论一致；
- 平台逻辑请求与各结果分类满足守恒。

### 17.2 性能

- 页面刷新不新增生产数据库慢查询；
- 不直接访问上游；
- 历史补算不影响既有同步和用户用量功能；
- 高峰期间 Monitor 资源消耗保持在批准范围内。

### 17.3 稳定性

- 新分类器异常时，旧功能仍可用且有明确降级提示；
- 采集断点后可从水位恢复，不重复或漏算已封口事实；
- 新未知类型不会导致任务崩溃或错误标绿；
- 告警具有恢复和去重能力。

### 17.4 安全

- 页面和接口不泄露完整令牌或密钥；
- 非授权角色无法查看请求级原始证据；
- 导出内容已脱敏；
- 不含对 NewAPI 源码的任何改动。

## 18. 研发评审问题清单

技术设计评审时必须逐项回答：

1. 逻辑请求如何唯一识别，缺失时如何处理？
2. 如何证明某渠道是实际渠道，而不是候选渠道？
3. 重试后成功在平台、渠道和体验三个口径中分别是什么？
4. 如何判断请求时刻的服务承诺，而不是读取当前配置？
5. 如何处理无法归责和证据冲突？
6. 客户端结果缺失时，页面使用什么措辞？
7. 新错误类型为什么不会默认落入成功？
8. 数据缺口如何阻止页面标绿？
9. 新旧口径如何对账、灰度、切换和回退？
10. 如何确保页面查询和补算不增加生产源压力？
11. 如何让三个模块共享同一分类，而不重复采集和重复实现？
12. 哪些请求不进入业务稳定率，是否仍能完整审计和告警？

上述问题任何一项无明确答案，均不得进入正式开发完成或上线验收状态。
