# 经营核算性能优化：实施顺序与验收边界

日期：2026-09-24。状态：第一版至第五轮已完成各自本机验收；均未上线。后续步骤是计划，不表示全部完成。

## 目标与现状

目标是让已核验报表可靠、快速地展示，后台持续同步和更新；金额、覆盖范围与核算配置保持一致。性能改善不会自动补齐缺失账单、赠送归属或 CUR 证据，这些仍按原回填计划推进。

当前隔离分支 `fix/finance-cold-read-v11714` 已有本地提交 `d2182b7`：默认关闭的事实只读隔离、短时快照快捷读取和等待诊断。它是本方案的基础，不应直接认定为完整性能修复。原工作目录中的其他改动不纳入本次发布。

实施前核实的代码限制（第一版完成情况见文末）：

- 事实库写入和现有多数读取共用单连接；新增只读连接只覆盖部分经营核算读路径，不解决主库全部争用。
- 普通路径在缓存查找前计算来源指纹；月组件缓存命中前也需要读取并核对输入。
- `fresh=1` 及事实变动后的重试会绕过月组件缓存。
- `financeReportRefreshRunning` 只约束后台刷新，按键合并并未限制不同区间的前台冷算总并发。
- 快捷快照超过三分钟回退前台核验；后台名额忙时没有待处理区间队列。
- 月度成本和日明细分别读取同一范围的经济事实；赠送核验独立于月基础组件，仍需读取起点以来的记录。
- 报表和月组件文件落盘共用锁，写入、同步磁盘期间可能阻塞文件读取。

已测本机副本的冷算约 3.1 秒、来源指纹约 0.11～0.23 秒、约 476 KB 快照读取约 1.75 毫秒。最后一个数值不包含鉴权、配置查询、HTTP 和渲染。线上历史 30 秒超时与 SQLITE_BUSY 只能证明存在超时和锁竞争，不能证明某个请求的具体等待占比。

## 第 1 步：建立可比较的基线

目标：区分 SQL 执行、连接排队、CPU 计算和快照发布耗时，并建立金额基线。

范围：使用闭合本机数据库副本；记录默认区间、历史月、当月的接口完整耗时、重算次数、缓存命中、回填提交速度、写事务时长、池等待、WAL 大小。测试端口只绑定本机，禁止接入真实上游或生产写库。

先用同一数据集、配置和资源限制运行优化前/后版本。至少覆盖无回填、有模拟回填，及 1/5/10 个客户端混合查询。保存响应中的金额、覆盖状态、区间和配置摘要用于逐项比较。

池等待增量是进程级累计指标，不能直接当成单个请求的耗时。阶段计时与池指标共同判断；日志不记录凭证、完整用户请求或报表金额。

完成标准：有可重复的基线与对比脚本，能区分缓存读取和冷生成；不以返回“正在生成”的速度冒充报表展示速度。

## 第 2 步：让页面读取与重计算分开

目标：多人打开或刷新页面时，已核验结果可快速展示，后台计算数量受控。

### 2A. 统一计算入口

- 前台冷读、普通刷新、后台核验共用经营核算调度器；初始最多一个执行任务，最多 16 个待处理的不同逻辑区间。具体上限为实施初始值，经本地压力测试调整。
- 按区间、核算配置和算法版本合并任务，来源版本变化不另外堆积同一区间任务；运行中发生新变更时最多保留一次后续核验意图。
- 排队采用有序、公平调度；任务启动时重新检查缓存和配置。已过时的配置任务不覆盖当前配置结果。
- 队列满时已有结果正常读取，无结果请求明确返回忙碌和重试建议；不创建无限 goroutine、无界队列或无限重试。
- 用户关闭页面只取消等待，不取消其他用户共享的后台生成。进程关闭取消任务；重启保留已发布结果，按后续请求重建必要任务。

### 2B. 页面行为与更新状态

- 相同核算配置、相同区间且校验通过的旧结果可先展示；“该核验了”不再等同于“必须让用户等待 SQL”。核验间隔仍以一分钟为起点，实际更新速度另受计算队列和上游同步影响。
- 区分查询区间、结果生成时间、最近成功核验时间，以及来源覆盖情况。前台只展示业务需要的更新时间和“更新中/更新失败”，技术详情放数据同步状态页。
- 旧结果展示沿用有限过期策略，初始保留现有 48 小时上限；核验失败不能续期。来源未变时允许更新成功核验时间，但不伪造新的生成时间或覆盖完整性。
- 配置变更、损坏快照、无匹配区间不复用金额。若沿用已存在的较早区间回退，必须保留其原始区间，明确当前区间尚在生成。
- 没有可展示结果时用明确的异步生成状态（例如 HTTP 202 配合结构化状态）；前端支持后才启用，空值不转零，失败不保留“成功”状态。
- 普通“刷新”要求尽快核验并更新，继续复用未变的月组件。保留现有一致性复核；源事实变化时重新核对组件版本，不能直接删除复核来避免重试。
- 失败退避、页面隐藏停止轮询、不同查询的迟到响应不得覆盖当前查询。需要全量重建时走受限维护入口，不增加老板页面操作。

### 2C. 收尾只读连接与发布路径

- 保留默认关闭的事实只读隔离，确认所有改接路径纯读取，连接总量有上限；主库连接策略先保持现状，避免扩展到整个系统。
- 内存优先，持久文件负责重启后恢复；限制条数和总字节数。
- 临时文件准备与磁盘同步不占用读路径的长锁；发布时原子替换，按版本阻止较旧任务覆盖较新结果。处理清理与读取同时发生、满盘、写失败、进程退出等情况。
- 来源无变化时避免每分钟重写整份报表。核验状态可先保存在有界内存中；进程重启后重新核验，不把未经持久确认的状态当作仍然有效。

完成标准：同区间重复请求合并，不同区间最终得到处理；前台后台合计重算并发不超过一；配置切换、失败、重启和跨小时显示正确。当前旧补丁的测试需随上述语义更新，不能只修改断言迎合结果。

这一轮可单独构成性能修复版本，不等待第 4 步。

## 第 3 步：减少每次计算的工作量

目标：缩短冷算和后台更新，同时减少 SQLite 扫描及磁盘写入。

- 优先在一个月组件内部复用同一份已发布经济事实，供月汇总、日明细使用，保持原有只读计算和最终版本复核。
- 保留历史月份缓存；源版本和核算口径未变时继续使用，不因普通刷新全部失效。
- 当月先复用现有日/小时事实，仅在测量确认收益后增加可复用日组件。暂不一次性建立月、周、日、小时四层缓存，以免增加失效维护成本。
- 事实版本核验先合并重复读取，保留现有检测能力；不使用单个最大时间戳代替对历史修改、删除和覆盖状态的检测。
- 对比实际查询计划后再决定是否需要索引；任何新增索引须测写入成本和迁移时长。

完成标准：同一数据集金额与覆盖逐项一致，重复查询数下降，持续回填期间的写入吞吐没有明显退化。若第 2 步已经满足上线目标，本步作为后续小版本，无需捆绑。

## 第 4 步：按证据决定是否做增量核算

目标：控制数据持续增长后的历史重算成本。本步单独设计、单独发版，不阻塞前面可用性修复。

候选方向：赠送分摊检查点、按受影响范围失效的已核验组件、发布事务中的持久修订号。每项先证明收益再实施。

关键准确性约束：

- 五月赠送变化可能影响其后各月的赠送余额与扣减，不能仅更新五月。
- 内部账号和分组口径变化可能影响整个查询历史；倍率修改按生效范围处理。
- 新数据与对应修订标记必须一起提交；删除、修正、重复回填、崩溃恢复均不能漏掉失效。
- 主库和事实库不能假设具有同一事务。保留两侧版本复核，不能通过拿长时间写锁保证报表一致。
- 新增量结果先与完整重算并行比对；影子阶段不发布新金额。

## 联合验收与发布

验收均先在本机闭合副本及隔离容器完成：

1. 金额、日/月合计、覆盖状态逐项一致；缺失数据仍为缺失，不能由缓存提升完整性。
2. 有缓存的常用报表接口 P95 目标不超过 1 秒，浏览器目标 1～2 秒显示；分别记录缓存返回、首次生成和更新完成时间。
3. 1/5/10 客户端同区间、不同区间、反复刷新，加持续模拟回填；稳定运行至少 30 分钟。包含跨小时、历史修正、配置切换、写失败和重启。测试规模是本机负载，不是生产压测。
4. 在同样本地工作负载下，回填吞吐不持续下降超过 10%；持续超过该门槛时停止扩大范围并定位原因。此值是初始验收阈值，不是生产容量承诺。
5. 计算队列有界、无区间饥饿，连接与内存不持续增长；WAL 能在读写结束后恢复合理水平，缓存文件遵守容量上限。
6. 数据同步状态可以区分来源未补齐、报表待更新、更新失败；老板页面保持简洁。

发布沿用既定顺序：提交本轮运行代码、必要测试及文档 → 新 tag → CI → 固定版本镜像部署 Monitor → 分开启用只读隔离与新报表读取/调度 → 验收稳定后合入 main。经范围核对，已有离线赠送修复工具源码保留版本管理，但 `cmd/financegiftlocal` 不进入生产镜像构建上下文，不新增线上入口或自动运行任务；私有备份、证据和工具执行产物不进 Git。其他功能及原工作树未提交改动不混入。此次方案本身不执行生产发布。

线上先低频只读检查约 30～60 分钟，观察缓存响应、同步延迟和错误；随后覆盖一个业务高峰验证。单个短窗口通过不等于长期容量问题已解决。配置回退需同时定义未完成队列任务的取消/清理，必要时恢复原版本镜像；保留原事实库，不依赖删库恢复。

## 第一版实施记录

本版仅处理读路径、排队和缓存发布，不改财务公式、不增加 Redis、不改 NewAPI、不启动生产补数。

- 复用默认关闭的 `MONITOR_FINANCE_FAST_SNAPSHOT_ENABLED`，开启时全部页面报表请求进入同一后台队列。一个运行任务、最多 16 个待处理区间、最多 32 条完成状态；同键合并，FIFO 调度。
- 自动核验同区间最短间隔一分钟；手动成功核验最短五秒，失败仍退避一分钟。重复请求不延长失败状态或生成无界任务。无结果返回 202；队列满时不假装已排队。
- 快读优先用有界内存，再用经过格式、哈希、区间及时间校验的文件；文件旧结果最多使用现有 48 小时窗口，始终保留实际生成时间与区间。
- 无缓存时前台只等待轻量配置读取和排队；不在 HTTP 请求内计算历史来源指纹。首次生成仍需实际计算时间，不以 202 耗时冒充有数据耗时。
- 后台先核验配置和事实版本，无变化则不重写报表文件；变化时执行原先完整计算和发布前版本复核。普通刷新及事实竞争重试复用仍匹配的月份。
- 已有事实只读隔离仍是独立默认关闭开关。长查询不再必须与事实写入共用同一连接；主库策略、其他模块连接策略未改。
- 文件使用已有原子替换；读者不再等文件写锁。整份报表由统一队列写入，月组件仍沿用原有影子持久化方式；其进一步调度治理不扩入本版。
- 前端支持排队、完成、失败和忙碌；切换区间隐藏上一区间金额，迟到响应不能覆盖新查询。来源覆盖、金额缺失保持原义。
- 数据同步状态新增报表运行/排队和近五分钟失败区间数，与来源回填分别展示。具体故障原因仍看脱敏服务日志，不伪造预计完成时间。

本版是按请求触发更新，不增加无人访问时的周期预热器。运行中发生新变化由原有发布前复核处理；若最终失败，下一次页面核验在退避后重试，不宣称持久任务恰好执行一次。

### 性能对照与限制

同一闭合快照，模拟每 100 ms 一个短事务，三个区间轮换，包含手动刷新。处理器测量不包含外部鉴权、网络与浏览器绘制。

| 并发客户端 | 原路径缓存 P95 | 第一版缓存 P95 |
| --- | ---: | ---: |
| 1 | 121 ms | 1.6 ms |
| 5 | 238 ms | 13.8 ms |
| 10 | 453 ms | 27.7 ms |

这些为短阶段观测，每阶段 3 秒；首次全范围计算约 3.02 秒。不能推导出线上等比例提升，更不能表示冷算和历史回填时间已消除。

另做 1 分钟、10 客户端的更严格比对：1,190 次成功响应、0 读写错误、0 金额/明细/覆盖差异，P95 26.94 ms；599 次模拟提交，647 个响应已更新至新生成的报表。此轮同时比较完整日/月结构、成本明细、配对审计与 CUR 成本，并断言发生了实际后台重算，避免只展示旧数据也被误判为通过。阶段结束时主动取消的请求不计入正常请求错误；测试日志中的相应 configuration canceled 提示不代表线上故障。

30 分钟持续读写验收通过：10 客户端，35,990 次响应，17,999 次模拟写事务，0 读取错误、0 写入错误、0 金额及原覆盖比较差异，P95 26.41 ms；采样到的报表运行任务峰值为 1（精确并发边界另由队列 barrier 用例验证）。写提交速率约 10 次/秒，没有低于 writer-only 基线的 90%；WAL 末段约 4.13 MB，结束后 TRUNCATE 检查通过。此轮使用相同运行代码；随后添加的更严格明细/覆盖及实际更新断言，在上面的独立 1 分钟测试中通过。

本轮独立预览入口：`http://127.0.0.1:8126/#tab=finance`。业务容器 `finance-v1-acceptance-20260924`，代理 `finance-v1-preview-20260924`，仅回环端口发布；原有 8112/8114 等容器没有替换。预览使用离线副本，不代表线上最新状态。

优先依据慢阶段诊断减少日/月重复事实扫描，再评估赠送全历史扫描、主库连接争用及月组件影子写入调度。新增索引、持久修订号或增量赠送检查点需独立设计和验证，不与第一版捆绑。

### 本版配置与回退边界

新异步读取依赖已有两项持久快照开关，启动校验保持 fail-closed：

```dotenv
MONITOR_FINANCE_REPORT_SNAPSHOT_SHADOW_ENABLED=true
MONITOR_FINANCE_REPORT_SNAPSHOT_READ_ENABLED=true
MONITOR_FINANCE_FAST_SNAPSHOT_ENABLED=true
```

事实读隔离单独控制：`MONITOR_FINANCE_FACTS_READ_ISOLATION_ENABLED=true`。它只适用于独立文件型、WAL 模式事实库；不满足时沿用原连接并记录提示，不擅自改 SQLite journal mode 或建立新业务数据源。

## 第四轮：复用月账单输入，并补齐历史活动边界的缓存依赖

### 范围与准确性修复

本轮只处理单个月组件构建内的账单桶、充值版本和上游生效边界。月汇总、日明细、已闭合自然日的兼容投影共享一次读取的输入；不跨请求、月份或重试共享，不增加持久缓存层、数据库结构、索引或 Redis，不改变金额、折扣、内部测试剔除或覆盖计算公式。

分析发现一个既有缓存缺陷，并先用测试复现：若选定月份之前的历史回填使某上游首次活动时间提前，即使本月原始账单没有变化，本月需要核验的小时范围也可能扩大。原整表来源指纹和月组件键未包含这一依赖，可能继续沿用旧的“账单完整”结论。

修复方式：整表指纹包含截至区间末端的历史活动起点；月组件键包含按本月和账单粒度归一化后的有效起点。命中缓存前检查一次，冷建发布前再检查一次。构建期间发生边界变化会拒绝发布并沿用现有重试流程，不把混合状态写进缓存。历史记录删除导致起点后移也会被识别。快捷快照仍按既有“显示已核验旧结果、后台更新”的有限时效策略运行，不承诺历史变更后瞬间消除旧显示。

子区间投影严格沿用原 SQL 的取行边界，包含区间起始自然日的重叠账单桶；不能将日账单按小时摊分，也不能通过丢弃重叠桶绕过区间冲突检查。原有独立读取入口保留，供其他调用与新旧投影对照。
