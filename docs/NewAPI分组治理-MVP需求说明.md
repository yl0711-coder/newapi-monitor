# NewAPI 分组治理——MVP 需求说明

> 版本：v1.0
> 日期：2026-09-04
> 状态：MVP 已实现，待生产灰度验收
> 范围：Monitor 只读治理页面
> 优先级：P1
> 产品原则：先看清、再治理；本期不修改 NewAPI 生产配置

## 1. 背景

NexusAPI 当前使用 NewAPI 的“分组”同时表达线路、价格档位和用户权限。部分分组名称直接带有倍率，例如 `claude-0.5x`。上游价格和平台倍率会变化，名称中的倍率可能逐渐失真；与此同时，分组字符串还被用户、令牌、渠道、自动分组、订阅和日志等多个模块引用，不能随意改名。

当前主要问题：

1. 分组数量较多，命名规则不统一，临时、旧版和在用分组混在一起。
2. 部分分组只存在于某一项配置，缺少倍率、展示说明或可用渠道，容易造成权限或计费异常。
3. NewAPI 没有独立的“分组实体”和一键重命名能力，分组实际是分散在多处的字符串标识。
4. 管理员无法直观看到一个分组被多少渠道、用户和令牌引用，无法安全判断是否可以删除。
5. 每次人工核对和修改耗时较长，且容易遗漏关联配置。
6. 历史日志需要保留请求发生时的实际倍率和计费事实，不能因为当前倍率变化而重算历史。

因此先在 Monitor 增加一个轻量、只读的“分组治理”页面，把当前配置和引用关系看清楚。第一版不提供修改按钮，不直接治理生产数据。

## 2. 已确定的方案

采用“一个仓库、两个运行边界”的长期方案：

1. **Monitor 分组治理页面**：长期运行，只读审计，负责发现缺失、冲突、孤儿和命名问题。
2. **独立 GroupOps 执行工具**：后续另立需求，按需运行，只通过 NewAPI 官方管理 API 修改配置。

本需求只实现第 1 项。GroupOps 不在本期开发和验收范围内。

不单独建设新的 Web 管理系统，避免重复部署、鉴权和维护。

## 3. 目标

### 3.1 核心目标

- 在一个页面中查看全部 NewAPI 分组及其主要引用关系。
- 自动发现高风险的分组缺失和配置不一致。
- 找出名称包含倍率、没有渠道、没有用户或长期无流量的分组。
- 为后续制定“旧分组 → 新规范分组”对应关系提供可靠依据。
- 降低人工逐页搜索、复制和核对的工作量。
- 所有结论都能说明依据，不把“可能无效”显示成“可以安全删除”。

### 3.2 成功标准

管理员进入页面后，可以回答：

- 当前一共有多少分组？
- 哪些分组缺少倍率或展示配置？
- 哪些分组没有启用渠道？
- 哪些分组仍被用户或令牌使用？
- 哪些分组最近仍有真实请求？
- 哪些名称包含倍率，后续应该进入规范化名单？
- 哪些分组只是清理候选，为什么暂时不能直接删除？

## 4. 非目标与红线

本期明确不做：

- 不修改 NewAPI 源代码。
- 不修改 NewAPI 数据库结构。
- 不对 NewAPI 数据库执行 `INSERT`、`UPDATE`、`DELETE` 或 DDL。
- 不在 Monitor 中保存 NewAPI 管理员、超级管理员或 Root 写权限凭证。
- 不提供“删除分组”“重命名分组”“批量迁移”按钮。
- 不自动修改渠道、用户、令牌、倍率、自动分组或订阅。
- 不改写历史日志、历史任务和历史倍率。
- 不把候选项自动判定为“可安全删除”。
- 不在本期实现完整订阅关联分析；现有只读数据不足时显示“未核验”。
- 不为了本页面新增高频或无界的生产日志查询。

如果开发过程中发现必须修改 NewAPI、扩大生产数据库权限或增加生产写能力，必须停止并单独评审。

## 5. 用户与权限

### 5.1 使用角色

| 角色 | 使用场景 |
|---|---|
| 技术/运维负责人 | 判断配置风险、确定治理顺序 |
| Monitor 管理员 | 查看异常、导出清单、交给负责人确认 |
| 研发人员 | 根据只读结果修复 Monitor 识别规则 |

### 5.2 权限要求

- 沿用 Monitor 当前登录鉴权。
- 页面仅对 Monitor 管理员开放，不对公开状态页和 Usage Portal 开放。
- 页面不得展示令牌 Key、渠道密钥、用户密码、邮箱等无关敏感信息。
- 令牌只展示聚合数量，不展示令牌明细或 Key。
- 用户主分组是治理的关键引用；管理员可在行展开后查看用户 ID、用户名、显示名、状态和角色，不展示邮箱、余额、密码或 AccessToken。
- 不新增 NewAPI 生产写权限。

## 6. 数据来源与边界

### 6.1 可使用的数据

复用 Monitor 已有只读能力和本地数据：

| 数据 | 用途 |
|---|---|
| `options` 只读数据 | `GroupRatio`、`UserUsableGroups`、`AutoGroups` 等当前配置 |
| `channels` 只读数据 | 渠道所属分组、渠道启用状态 |
| `users` 只读数据 | 当前用户主分组数量 |
| `tokens` 只读数据 | 显式指定分组的令牌数量 |
| Monitor 本地历史数据 | 最近 7 天、30 天分组请求量和最后请求时间 |

### 6.2 读取原则

- 浏览器打开页面时只读取 Monitor 本地结果，不直接查询生产数据库。
- 分组审计由后台低频刷新，建议每 5～10 分钟一次；优先复用现有采样周期和快照。
- 令牌只做按分组聚合，不读取或存储令牌 Key。
- 用户只读取分组核对需要的 ID、用户名、显示名、状态和角色，脱敏快照由 Monitor 本地分页查询。
- 历史请求量优先读取 Monitor 本地 SQLite/事实数据，不新增对生产 `logs` 的大范围扫描。
- 数据不完整、采集延迟或某个来源不可用时，必须显示“未知/未核验”，不得按 0 处理。
- 页面显示数据更新时间和数据完整性状态。

### 6.3 NewAPI rc4 解析规则

1. `GroupRatio` 的 JSON Key 作为当前已定义分组集合。
2. `UserUsableGroups` 的 JSON Key 作为全局可选/可用分组集合，Value 作为显示说明。
3. `channels.group` 是逗号分隔字符串，必须按逗号切分、去除首尾空格后进行完整名称匹配。
4. `users.group` 是用户当前主分组。
5. `tokens.group` 为空时表示继承用户分组，不得把空字符串当成独立分组或缺失分组。
6. `tokens.group` 非空时视为显式分组引用。
7. `default` 和 `auto` 是特殊标识，不得进入自动清理建议。
8. 分组名比较默认区分大小写；页面可额外提示仅大小写不同的疑似重复项。
9. 当前倍率只读取配置值，不能从名称中的 `0.5x`、`1.2x` 反推。

## 7. MVP 功能范围

### 7.1 页面入口

在 Monitor 管理端导航中增加：

```text
分组治理
```

页面定位为只读审计页。页面标题附近固定显示：

```text
只读审计，不会修改 NewAPI 配置
```

### 7.2 顶部摘要

展示 4 个摘要卡片：

1. 分组总数
2. 高风险问题数
3. 无启用渠道分组数
4. 清理候选数

任一数据来源不完整时，摘要区域显示明显的数据不完整提示。

### 7.3 分组列表

MVP 表格至少包含：

| 字段 | 说明 |
|---|---|
| 状态 | 高风险、待处理、观察、正常 |
| 分组标识 | NewAPI 实际使用的完整分组字符串 |
| 展示说明 | `UserUsableGroups` 中的描述；缺失时显示“未配置” |
| 当前倍率 | `GroupRatio` 当前值；缺失时显示“缺失”，不得显示默认 1 |
| 渠道 | 启用数 / 禁用数 |
| 用户 | 主分组为该分组的用户数 |
| 显式令牌 | `tokens.group` 明确等于该分组的令牌数 |
| 最近使用 | 最近 7 天、30 天请求数和最后请求时间 |
| 主要问题 | 本行命中的问题标签 |
| 建议 | 补齐、核对、规范命名、观察、清理候选 |

默认排序：高风险在前，其次待处理、观察、正常；同级按分组名排序。

### 7.4 筛选和搜索

只实现以下基本功能：

- 按分组名/展示说明搜索；
- 按状态筛选；
- 只看“名称包含倍率”；
- 只看“无启用渠道”；
- 只看“最近 30 天无请求”。

不做复杂的自定义筛选器和保存视图。

### 7.5 行展开信息

点击一行后展开，不跳转新页面。展示：

- 启用和禁用渠道名称/ID；
- 该分组出现在哪些配置中；
- 用户总数、启用/禁用数量，以及实际 `users.group` 关联的本地分页用户清单；
- 显式令牌的聚合数量；
- 最近一次请求时间；
- 状态判定依据；
- 尚未核验的依赖，例如已有订阅或历史任务。

除上述分组核对所需的用户 ID、用户名、显示名、状态和角色外，不得展示渠道密钥、令牌 Key、邮箱、余额或其他用户隐私信息。

### 7.6 导出

支持导出 UTF-8 CSV，字段至少包含：

```text
old_group
display_name
current_ratio
status
enabled_channels
disabled_channels
user_count
explicit_token_count
requests_7d
requests_30d
last_request_at
issues
suggested_new_group
notes
```

`suggested_new_group` 和 `notes` 默认留空，供负责人离线填写对应关系和备注。

本期不做页面内编辑和保存映射表。

## 8. 状态判定规则

### 8.1 高风险

满足任意一项：

- 启用渠道、用户或显式令牌引用了某分组，但该分组不在 `GroupRatio` 中；
- 分组被全局设置为可用，但没有任何启用渠道；
- 关键数据源不可用，导致无法判断当前分组是否可用。

说明：倍率缺失时页面必须显示“缺失”，不能按 NewAPI 运行时可能回退的倍率 1 展示。

### 8.2 待处理

满足任意一项：

- 名称包含倍率，例如 `0.5x`、`1x`、`1.2x`；
- 名称中的倍率与当前 `GroupRatio` 数值明显不一致；
- 只有显示配置，没有倍率配置；
- 只有倍率配置，没有显示说明；
- 仅大小写、横线或下划线不同的疑似重复分组；
- 在自动分组中存在，但没有启用渠道。

名称倍率只作为问题提示，不能替代真实倍率。

### 8.3 观察

可标记为观察或清理候选，但不能标记为“可安全删除”：

- 已定义倍率；
- 没有启用渠道；
- 没有用户引用；
- 没有显式令牌引用；
- 最近 30 天没有请求；
- 不是 `default` 或 `auto`。

页面提示：

```text
清理候选：仍需人工核对订阅、历史任务及长期未使用令牌，不能直接删除。
```

### 8.4 正常

- 存在倍率配置；
- 配置引用关系没有发现缺失；
- 至少存在一个启用渠道；
- 没有命中高风险或待处理规则。

“正常”只代表当前已检查数据内未发现分组配置问题，不代表上游渠道稳定。

## 9. 页面状态与异常处理

- 后台同步成功：显示“数据更新于 YYYY-MM-DD HH:mm:ss”。
- 部分来源失败：保留最后一次成功结果，并显示“数据可能过期”。
- 从未同步成功：显示错误原因和“暂无可靠审计结果”，不得显示全为 0。
- Monitor 本地历史不足 30 天时，显示实际覆盖范围。
- 配置 JSON 无法解析时，将对应配置标记为高风险，并显示配置 Key；不得导致整个页面 500。
- 单个异常分组不得影响其他分组展示。

## 10. 性能和安全要求

- 页面请求不得触发生产库全表日志扫描。
- 后台聚合查询必须有超时和串行/有界并发控制。
- 不记录完整 `options` 敏感配置，只处理明确允许的分组配置 Key。
- 日志中不得输出 Cookie、管理员会话、令牌 Key、渠道 Key 或完整数据库连接串。
- CSV 导出不得包含用户身份、令牌内容、渠道密钥和上游凭证。
- 分组审计失败不得影响 Monitor 其他采集、报警和页面。
- 本功能可通过独立配置开关关闭；关闭后不启动新增的分组审计任务。

建议配置：

```text
MONITOR_GROUP_GOVERNANCE_ENABLED=false
MONITOR_GROUP_GOVERNANCE_SYNC_MINUTES=10
```

生产首次上线保持关闭，完成本地和只读验收后再显式开启。

## 11. 验收场景

开发和测试至少覆盖以下场景：

1. `GroupRatio`、渠道、用户和令牌引用完全一致，页面显示正常。
2. 渠道引用不存在于 `GroupRatio` 的分组，显示高风险。
3. 用户引用不存在于 `GroupRatio` 的分组，显示高风险。
4. 显式令牌引用不存在于 `GroupRatio` 的分组，显示高风险。
5. 令牌分组为空时不产生空分组，也不报缺失。
6. 分组存在于可用配置，但没有启用渠道，显示高风险。
7. 分组只有倍率、没有显示说明，显示待处理。
8. `claude-0.5x` 被识别为“名称包含倍率”。
9. 名称写 `0.5x`、实际倍率为 `0.7` 时，显示可能不一致。
10. 分组无渠道、无用户、无显式令牌、30 天无请求时，只显示清理候选，不显示可安全删除。
11. `default` 和 `auto` 永远不进入自动清理候选。
12. 渠道分组字符串含空格和多个逗号分隔项时，能够正确按完整名称解析。
13. 两个分组仅大小写或连接符不同，显示疑似重复。
14. 某项配置 JSON 损坏时，页面其余数据仍可用，并显示高风险。
15. 生产数据源暂时不可用时，页面显示最后成功时间和数据过期状态，不显示错误的 0。
16. 页面和 CSV 均不包含令牌 Key、渠道 Key、邮箱、余额等无关隐私信息；CSV 不包含用户明细，页面用户展开仅包含第 5.2 节允许的核对字段。
17. 关闭功能开关后，不执行新增后台同步，不影响现有 Monitor。

## 12. MVP 完成定义

以下条件全部满足才算完成：

- 管理端存在“分组治理”只读页面；
- 能展示分组配置、渠道、用户、显式令牌和本地历史使用量；
- 能按本需求规则识别高风险、待处理、观察和正常；
- 能搜索、基础筛选、展开查看依据并导出 CSV；
- 页面明确显示数据更新时间、覆盖范围和未核验项；
- 没有任何生产写能力；
- 没有新增 NewAPI 高权限凭证；
- 不修改 NewAPI 代码和数据库；
- 单元测试和关键异常场景通过；
- 本地验收通过后，以功能开关方式灰度上线。

## 13. 后续阶段（不在本期）

根据第一版审计结果再决定是否开发 `newapi-groupops`。如果开发，必须遵守：

- 独立命令行程序，不作为 Monitor Web 功能部署；
- 默认只生成计划，必须二次确认才执行；
- 只调用 NewAPI 官方管理 API，不直写数据库；
- 修改前导出原配置和回滚计划；
- 单线程、小批次执行，逐项验证，失败即停；
- 不尝试修改官方 API 不支持的历史日志、历史任务和其他记录；
- 高权限凭证只在运行期间使用，不进入 Monitor 环境和持久存储。

是否开发、具体支持哪些修改操作，以本期输出的真实审计结果为准。
