# 经营核算第一轮：口径一致性（本地）

## 边界

本轮仅修改 Monitor 经营核算与测试，不上线、不改生产配置、不修改 NewAPI、不启动历史全量补采。保留已有非本轮工作区修改。本轮不是整个经营核算功能的最终上线验收。

## 已实现

1. 经营结果采用：可核验经营收入 − 修正上游总成本（包含内部测试支出）− AWS 成本。客户贡献与平台整体结果分开，内部测试成本作为“其中项”，不重复扣除。
2. 赠送钱包按用户连续计算。非业务分组消费仍消耗赠送余额，但不作为客户赠送扣减；退款按业务/非业务范围恢复赠送，不跨范围抵消。沿用赠送优先的估算政策，不声称能逐请求还原退款资金来源。
3. 客户消费与渠道贡献统一业务分组范围。纯测试小时可严格识别成本；客户与测试混合小时不按请求数分摊成本，不混入已配对客户贡献。原始账单、修正总成本和不可变配对事实保留。
4. 历史赠送依据变化会使后续报表缓存失效。单月基础缓存不包含赠送分摊，不因无关的期初赠送变化重建；配置/缓存版本已更新，防止复用旧口径。

## 兼容限制

- 赠送明细新增 `grp`、`group_known`，仅属 Monitor 事实库；NewAPI 只读查询新增原有 group 字段。
- 旧记录保持原校验哈希，不把未知分组冒充默认分组。启用测试分组排除且旧赠送记录缺分组依据时，相关收入不发布，页面提示依据待补；其他已知金额继续保留。
- 没有自动清空或重建历史事实。下一轮需设计限速、可暂停、幂等的定向补采及旧库迁移验收。
- 当前成本严格识别存在固有限制：混合客户/测试账单不能凭本地消费比例证明实际上游成本。本轮不将其伪装为精确分摊。

### 验收中发现并修复

1. 月明细存在账单但没有充值修正依据时，修正总成本被错误标为“已知 0”，而总计为空。统一为空，新增回归先复现失败再通过。
2. 月明细账单原值已完整，但报表合计错误依赖充值修正覆盖，导致单月查询的合计为空。拆开原值账单和修正成本的完整性条件，保留未配置来源的阻断；新增回归先复现失败再通过。

1. **历史赠送分组依据仍缺失**：样例区间 220,028 条相关事件未知分组，经营收入和利润不发布。下一轮定向补采，不在本轮触发全量生产回填。
