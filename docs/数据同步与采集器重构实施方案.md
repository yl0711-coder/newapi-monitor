# 数据同步与采集器重构实施方案

## 1. 会审结论

本次工作拆成两条独立发布链，不能一次性大改：

1. **同步状态整合**：只调整状态读取、页面归属、权限和展示，不改变任何采集 worker、租约、游标、发布签名、重试退避或业务 API。
2. **采集器优化**：在第一阶段稳定并建立性能基线后，再优化生产 MySQL 调度、上游任务公平性和已经证实的重复读取。

用户用量的统计、成员管理、分组、日志和 Usage 客户站保持不变；只把历史补数进度、任务阶段、游标、重试、单日修复等运维信息移到「数据同步状态」。客户排障代码不在本次改造范围内。

## 2. 第一条发布链：同步状态整合

### 2.1 业务页边界

- 用户用量保留：统计范围、实际数据截止时间、消费矩阵、成员与公司管理、使用日志。
- 用户用量移除：补数百分比、成员任务阶段、分页水位、校验任务、失败原因、下次重试、重试和单日修复按钮。
- 渠道与成本保留：渠道配置、倍率、余额、区间上游消费、成本和利润结果。
- 渠道与成本移除：Tail、历史补数、退避、熔断、游标等详细运维过程；只保留健康徽标和「查看同步详情」入口。
- 服务质量、运行与容量只保留数据截止时间和完整性边界，不重复解释采集任务。

### 2.2 统一状态接口

新增只读本地状态接口：

```text
GET /sync/overview
GET /sync/workloads?domain=&health=&phase=&cursor=
GET /sync/workloads/{workload_key}
```

接口要求：

- 只读 Monitor 本地状态、游标和水位；
- 不访问生产 MySQL；
- 不访问任何上游 API；
- 不计算完整渠道业务报表；
- 不写库、不续租、不改变 retry 时间、不唤醒 worker；
- 摘要有短时缓存，明细分页且默认只返回异常任务；
- 单响应建议小于 512 KB。

当前同步页每 30 秒调用完整 `/channels/report?hours=24`，应优先替换；`/usage/facts-history` 也不应每 30 秒返回全部成员和全部任务。

### 2.3 统一状态语义

不能用一个 `status` 同时表示是否启用、运行阶段和健康情况。状态投影至少分开：

| 维度 | 建议值 |
| --- | --- |
| `enabled` | true / false |
| `schedule_state` | disabled / idle / running / retry_wait / paused / blocked |
| `phase` | tail / backfill / verify / repair / migration / backup |
| `health` | ok / warning / error / unknown |
| 进度 | cursor / target / lag / coverage / backlog |
| 时序 | last_started / last_success / last_failure / next_retry |
| 控制 | lease_owner / backpressure_reason / circuit_state |

`disabled`、`not_configured`、`warming`、`stale`、`failed`、`complete` 必须明确区分。零成员、未启用和未知值不能显示为异常或 100%。页面必须显示各链路自己的 `as_of`/`updated_at`，不能用浏览器刷新时间冒充数据更新时间。

第一阶段优先使用适配器从现有领域状态表生成只读投影，不新建一张会与真实游标漂移的“万能任务表”。

### 2.4 前端故障隔离

- 各状态分区独立请求和渲染，单个接口失败不能拖垮整页。
- 使用 `Promise.allSettled` 或等价机制，禁止单点失败后所有卡片停止更新。
- 每次请求有超时和取消；切换 Tab 时取消在途请求。
- 用请求序号防止旧响应覆盖新响应。
- 上一轮未完成时不启动下一轮，避免轮询堆积。
- 401 只触发一次登录处理；500、超时和坏 JSON 仅将对应分区标为不可用。

### 2.5 权限和操作

- admin：只读状态。
- root：可执行白名单内的 retry、repair、pause、resume 和备份操作。
- 写操作必须保留确认串、幂等请求 ID、原因和审计记录。
- 页面不得向服务端传任意 SQL、任意 URL 或无边界时间范围。

## 3. 第二条发布链：采集器整理与优化

### 3.1 已经正确复用的数据，不重做

- 模型监控与容量规划共用 `metric_samples`。
- 服务端监控与容量规划共用 `infra_samples`。
- 历史稳定性与渠道质量共用 `stability_hour_samples`。
- 近期稳定性小时数据从本地分钟事实滚动生成。
- Monitor 用户用量与 Usage 客户站共用用量事实库。

### 3.2 必须保持独立的采集

- 用户用量事实需要成员级、小时/天窗口和签收校验，不能由全站分钟指标代替。
- 稳定性问题采样需要错误正文脱敏归类，不能由计数事实反推。
- 客户排障是有界、按需的明细查询，不应改为全量复制生产日志。
- 上游余额、消费账单和计价证据来自不同接口和协议，不能由本站日志替代。

因此不能把所有生产日志查询粗暴合成一个大 SQL，也不能新增全量原始日志 SQLite 镜像；这会增加生产库扫描、隐私风险、磁盘占用和本地写放大。

### 3.3 已确认可消除的重复采集

NewAPI 类型上游的消费账单与计价证据会对同一 `/api/log/self` 时间窗重复分页读取。

目标实现：

```text
上游页面读取一次
       │
       ├── 消费账单解析器 → 独立事务、独立游标、独立健康状态
       └── 计价证据解析器 → 独立事务、独立游标、独立健康状态
```

共享的只是短生命周期传输结果，不能共享提交事务或游标。一个解析器失败不能阻止另一个已验证结果提交；不得把响应长期缓存为第二份原始日志库。Sub2API、AICodeWith 协议不同，不强行合并。

### 3.4 资源级调度，而不是全局单队列

建议按远端资源建立独立预算：

- `prod_mysql`
- `upstream_api:{host}`
- `sqlite_main_write`
- `sqlite_facts_write`
- `backup_io`

工作优先级：

1. P0：用户用量近期 Tail、主分钟采样、稳定性问题 Tail。
2. P1：用户资料、渠道快照、上游消费 Tail、余额。
3. P2：校验、对账、本地小时汇总。
4. P3：历史补数、计价历史、分类迁移。
5. P4：清理、压缩等维护任务。

迁移前备份和到期双库备份拥有独立维护预算，不能长期被低优先级任务饿死。

现有生产 MySQL 单活租约、高低优先级闸门和上游持久熔断先保留。后续仅在测试证明安全后增加加权公平、SQL/API 次数预算和背压信号，不直接重写现有正确性协议。

### 3.5 上游同步公平性

当前余额、消费和计价任务按固定顺序串行，账户增加后容易互相拖延。验证阶段后可逐步调整为：

- 全局并发 2；
- 同主机并发 1；
- 同账户并发 1；
- 保留每主机至少 1 秒启动间隔；
- 余额、消费 Tail、计价 Tail 轮转；
- 历史补数只使用剩余预算；
- 429 严格尊重持久化 `Retry-After`，进程重启不能绕过熔断。

## 4. 实施顺序

### 阶段 0：冻结基线

- 固化用户用量、Usage、渠道、稳定性、容量和客户排障的关键 API 响应。
- 记录生产 SQL 次数/耗时、上游请求/429、SQLite busy/WAL、worker 时效。
- 建立“打开同步状态页不会访问任何来源”的自动测试。

### 阶段 1：只读状态 V2

- 建立统一 DTO 和轻量状态接口。
- 替换 `/channels/report` 和全量成员轮询。
- 完成部分失败隔离和有界分页。
- 此阶段不从业务页删除旧入口，先做新旧状态并行比对。

### 阶段 2：运维信息搬家

- root 先灰度看到新同步中心。
- 再开放 admin 只读。
- 状态一致后，从用户用量移除补数任务、阶段、重试和修复。
- 渠道页只保留业务结果与状态跳转。

### 阶段 3：导航整合

- 模型监控 + 稳定性报表 → 服务质量。
- 服务端监控 + 容量规划 → 运行与容量。
- 渠道管理 → 渠道与成本。
- 保留旧 hash 路由到新二级视图。

### 阶段 4：采集调度优化

- 先收敛 NewAPI 上游重复页面读取。
- 再改上游任务公平调度。
- 最后依据测量数据决定是否需要继续协调生产 MySQL 窗口。

每个阶段单独测试、单独发布、可以只切回旧 Monitor 镜像；不改 NewAPI、Nginx 或 Caddy。

## 5. 验收门槛

- 同步状态页连续刷新时，生产 MySQL 和上游 API 增量请求数为 0。
- 同一 SQLite 快照下，用户用量、Usage、渠道、稳定性和容量业务结果与改造前逐字段一致。
- 客户排障代码、SQL、接口和页面零变更。
- 状态摘要本地 P95 小于 200 ms、P99 小于 500 ms。
- 单个状态源 500、超时、断连或坏 JSON 不影响其他分区。
- worker 游标只单调前进；除显式 repair 外不能回退。
- 进程重启、租约切换、分页中断、429、SQLite busy、磁盘高水位和双库恢复均通过故障注入。
- root/admin/customer/匿名权限矩阵通过。
- 全量 Go 测试、race、vet、浏览器 E2E 和双库备份恢复通过。
- 同步 worker 吞吐和延迟相对基线不得退化超过 5%。

## 6. 当前不做

- 不修改用户用量统计与 Usage 业务逻辑。
- 不修改客户排障。
- 不重新同步全历史。
- 不新建全量生产原始日志副本。
- 不引入 Redis、Kafka 或分布式队列。
- 不在同一版本同时修改页面、状态存储、采集调度和业务读取。
