## 修复范围

1. 空成本小时：旧版本留下的零请求、零控制额、零证据额、零行且 matched 的空单位状态可以重新观察；任何非空或未对平状态继续严格校验历史单位。新空小时写入有效单位，两次观察后核验；空小时不会给后续迟到的非零消费冻结错误单位。
2. 缓存依赖：内部账号事实按主键顺序参与指纹，防止总金额相同但渠道分配改变时漏失效；状态按查询区间截断，区间外的新小时不无故刷新历史月。月度输入同时包含内部成本证据与完成状态。
3. 强制刷新：用户主动刷新跳过月度缓存并替换结果，与普通后台重建使用不同的 singleflight key；后台仍可复用未变化月份。旧月度缓存 schema 失效，磁盘月度缓存增加 7 天时间上限。
4. 配置隔离：功能开关、核算起点、AWS 接入和计算语义版本参与配置 hash；关闭经营核算时 HTTP 入口直接返回 disabled，不读取旧缓存。
5. 汇总完整性：账单、原始修正成本、业务修正成本、贡献分别继承每个月的完整性；部分金额不能被合计升级成完整值。另修复月度内部测试成本切片：已证明无内部测试时可以完整，来源未完成时即使已有严格匹配片段也不能完整。
6. AWS 日成本：要求所纳入时间桶连续覆盖整个查询区间。部分边界日保持未知，缺口不能按零处理，重复/重叠桶拒绝发布。
7. 留存保护：在稳定性清理前保护核算起点以来仍依赖的三类小时汇总/覆盖记录；已有财务事实时，即使暂时关闭功能仍保护。问题详情、拒绝日志等维持原清理规则。无效核算起点阻止删除依据。
8. 页面更新：后台轮询耗尽明确提示保留旧结果、稍后刷新；新查询重置轮询预算。前端资源版本 v41。

留存保护是本阶段的防误删措施，不是长期财务归档系统。后续仍需在独立迭代中用经对账的财务日/月事实替代稳定性维度依赖，并评估汇总表体积；本次没有永久保留全部原始日志、没有增加业务数据库结构。

## 真实只读同步下的并发刷新修复

本机切换 SSH 只读来源后，用户反馈“经营核算事实在报表生成期间已变更，请重试”。原实现的结束版本校验正确拒绝了变化中的事实，但未自动重试，手动刷新也无法保留旧结果。离线快照验收不能覆盖持续写入场景。

修复边界：仅 Monitor 财务缓存及测试，未关闭版本校验，未暂停生产或本机同步来制造通过结果。

- 一次生成冲突最多自动重试一次，沿用原请求超时；重试重新取得来源版本，不将新结果放入旧版本缓存键。
- 月度组件写缓存前再次验证来源版本，变化中的组件不入缓存。
- 同范围、同核算配置的最后成功结果以有界内存别名保存，仍共享原有条目和字节上限；同步冲突或超时可返回 stale，页面保留结果并后台更新。
- 强制刷新失败可回退到未过期的已校验结果；不会跨日期、跨核算配置回退，不延长旧结果有效期。
- 初次版本探测失败不能让新报表跳过一致性检查；缓存查找前和重建前均允许重新探测。
- 缓存语义 v4，月度 schema 4，旧月度计算缓存失效。

确定性临时 SQLite 测试覆盖：一次并发发布后恢复、持续发布时有/无旧结果、不同区间/配置不得回退、过期结果不得回退、配置变更仍报错、月度混合版本不入缓存。新增 4 个测试函数，含 5 个回退边界子用例。最终财务普通测试 6.191 秒、竞态测试 63.811 秒通过；静态检查、前端刷新行为测试、1548 项分片覆盖与补丁格式检查通过。
