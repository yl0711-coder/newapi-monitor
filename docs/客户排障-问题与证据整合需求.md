# 客户排障·问题与证据整合需求

## 1. 结论与范围

将稳定性报表中现有的「问题与证据」整合进「客户排障」，避免两个页面同时提供错误查询、用户不知道该从哪里开始。

本次只整合展示和排障流程，不更改 NewAPI，不更改 Nginx，不新增生产数据采集，不改动已有客户排障查询口径。

## 2. 功能定位

客户排障统一回答两类问题：

1. **问题聚合**：最近有哪些异常，哪些分组、渠道、模型受影响，何时开始，是否仍在持续。
2. **请求明细**：某个客户、令牌或 Request ID 的单条请求走了哪个渠道，上游返回了什么，有哪些客观证据。

「问题聚合」用于发现范围性问题，「请求明细」用于回应具体客户投诉。两者同属一个排障流程，但数据粒度和安全边界不同。

## 3. 页面结构

保留左侧唯一一个「客户排障」入口，页内增加二级视图：

- **请求明细**：保留当前已开发的客户排障页，现有筛选、表格、请求详情和判定口径不变。为降低回归风险，首次整合后仍作为默认视图。
- **问题聚合**：迁入稳定性报表现有的脱敏问题签名聚合能力，展示错误码/来源、规范化摘要、数量、占比、首次/最后发生时间、受影响分组/渠道/模型以及实际可排查的证据时间范围。

「问题聚合」验证通过后，再从稳定性报表移除「问题与证据」按钮和重复页面。不允许长期保留两个可用入口。

## 4. 数据与接口边界

### 4.1 问题聚合

- 第一阶段复用 `GET /stability/problems`，仅读 Monitor 本地 SQLite 中的 `stability_problem_samples` 及其完整性状态。
- 页面刷新不得访问生产 NewAPI 数据库。
- 仅显示脱敏、规范化后的问题签名，不在聚合列表返回上游错误原文或客户敏感信息。
- 第一阶段不改表结构，不重跑历史数据。
- 后续可增加 `/logchain/problems` 语义化别名，但不应在首次整合时同时重写存储和采集链路。

### 4.2 请求明细

- 继续使用现有 `GET /logchain/requests` 和 `GET /logchain/filters`。
- 只有管理员主动查询时才读取来源 `logs`；不自动刷新，不在问题聚合页预加载原始请求。
- 保留当前的日期范围、行数上限、超时保护和 `no-store` 响应。
- 错误原文仅在请求明细中显示，不回写到脱敏聚合表。

## 5. 两个视图的关联

问题聚合行提供「查看候选请求」操作，将下列已知条件带入请求明细：

- 时间范围；
- 分组；
- 渠道；
- 模型；
- 错误代码或错误来源。

现有脱敏问题签名与来源 `logs` 的原始文本之间没有稳定的请求级主键，因此第一阶段必须显示「候选请求」，不得宣称已精确关联或已证明根因。不得把脱敏摘要直接当作原文关键词使用，否则会造成漏查或假匹配。

如果某类问题只有前置拒绝小时汇总，没有 Request ID、用户或令牌级证据，则展示聚合数据，但禁用「查看候选请求」并明确说明证据粒度不足。

## 6. 必须保持的口径

- 问题分类是证据整理，不是根因判定。
- `client_gone`（客户端中断）不得计入渠道稳定性失败；但请求明细仍应单独展示，便于回应客户感知。
- 没有客户端结果证据时，不得用服务端日志推断「客户已成功接收」。
- 问题聚合页只显示实际可排查的证据时间范围；数据不完整时不得把缺失时段当成零问题。采集器、补数、水位、迁移、失败与重试细节统一归「数据同步状态」，客户排障只提供跳转链接。
- 请求明细的直读查询只代表当次查询结果，不宣称历史数据已全量采集。

## 7. 异常、权限与降级

- 两个视图均仅对 Monitor 管理员开放。
- 本地快照模式下，「问题聚合」可正常展示；「请求明细」应显式提示未连接来源库，不得将空结果表述为「无问题」。
- 来源库查询超时、取消或失败只影响当前请求明细，不影响 Monitor 其他页面。
- 所有文本必须按现有规则转义，不得把上游错误原文直接拼接为 HTML。

## 8. 并行开发边界与合入顺序

### 客户排障开发者负责

- 在现有客户排障页增加「请求明细 / 问题聚合」二级视图。
- 复用 `/stability/problems` 完成问题聚合展示，并实现到请求明细的候选筛选跳转。
- 不在客户排障中新建同步进度或 worker 健康面板；证据范围不完整时只提示影响范围并跳转「数据同步状态」。
- 保证现有 `logchain` 筛选、翻页、错误详情、责任方提示和已知盲区不回归。
- 增加页面结构、权限、数据源边界、筛选跳转和安全转义测试。

### 后续集成者负责

- 待上述功能验收通过后，移除稳定性报表中「问题与证据」的按钮、重复容器和仅为该容器服务的前端逻辑。
- 第一个发布版保留 `/stability/problems` 兼容路由，不在同一次发布中删除后端数据能力。
- 由于 `monitor/page.html` 是共享文件，客户排障开发者的改动先合入，再由集成者删除稳定性重复区域，不并行修改同一段 HTML。

## 9. 验收标准

1. 现有客户排障请求明细的默认行为、筛选结果和查询保护全部不变。
2. 同一时间范围下，新「问题聚合」与原稳定性「问题与证据」数量、占比、时间和受影响维度一致。
3. 只刷新问题聚合时，不产生对生产 NewAPI 数据库的请求。
4. 只有点击查看明细或主动查询时才读来源库，并且日期、行数、超时和 `no-store` 限制生效。
5. 问题聚合可带时间、分组、渠道、模型、错误条件打开「候选请求」；界面不宣称这些候选已与脱敏签名精确关联。
6. `client_gone`、前置拒绝、无客户端回传和数据部分覆盖的口径符合第 5‑7 节。
7. 本地快照、未登录、非管理员、来源库超时和恶意错误文本均有自动化测试。
8. 最终侧边栏只有「客户排障」入口，稳定性报表不再重复展示「问题与证据」。
