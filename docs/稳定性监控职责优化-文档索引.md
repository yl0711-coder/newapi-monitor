# 稳定性监控职责优化文档索引

> 版本：v1.0
> 日期：2026-09-02
> 状态：已完成需求评审，待研发设计与实施
> 最高优先级：P0——稳定性统计口径纠偏

## 1. 文档目的

本组文档用于指导 Monitor 中“模型监控”“稳定性报表”“客户排障”三个模块的职责梳理和稳定性能力优化，目标是让系统同时做到：

- 真实反映平台、分组、模型和实际渠道的服务稳定性；
- 不把用户请求不存在的模型、无效令牌等使用问题错误计入平台稳定性；
- 不隐藏确实影响用户使用的问题，而是放入正确的问题类别、页面和告警通道；
- 对无法确认责任或证据不完整的情况明确显示“未知/证据不足”，不以成功数据补齐；
- 为实时运营、历史分析和单次请求排障分别提供清晰入口，避免功能和口径重叠。

## 3. 本次有效决策

- “模型监控”名称保持不变，不改名为“服务质量”或“实时质量”。
- “模型监控”“稳定性报表”“客户排障”继续作为三个独立模块，不在本阶段合并页面。
- “服务端监控”是另一项独立能力，不与“模型监控”混名。
- 第一优先级是修正稳定性统计与责任归类，不是页面改版。
- “稳定性报表”的问题明细不再发展成第二套排障系统；它只做问题聚合，并跳转到“客户排障”查看请求级证据。
- “客户排障”由其他开发工作负责，本项目只定义其应接收的数据、链接和职责边界，不直接改造该模块。
- 各类同步任务的进度、重试、补数和维护状态统一归入“数据同步状态”；业务页面只展示数据截止时间、完整度和证据等级。
- 不修改 NewAPI 源代码。若未来确需变更 Nginx 或入口采集配置，必须作为独立变更评审，不视为本需求的默认授权。

若本组文档与《Monitor功能与采集整合分析.md》等较早文档中的“模型监控改名/模块合并”建议冲突，以本组文档为准。

## 4. 推荐实施顺序

1. 冻结指标词典、分类状态和验收样本。
2. 修正现有稳定性展示口径和不严谨文案，引入“未知/证据不足”。
3. 建立逻辑请求与渠道尝试的双层统计能力，并以影子结果完成对账。
4. 完成模型监控、稳定性报表和客户排障之间的职责与跳转闭环。
5. 在指标稳定后启用分级告警、事件聚合和通知闭环。

## 5. 明确不在本次范围内

- 不修改 NewAPI 的请求、路由、计费或日志代码；
- 不直接自动禁用、启用或调整线上渠道；
- 不改造 Usage 客户站；
- 不将“模型监控”与“服务端监控”合并；
- 不以当前配置反推历史事实并作为确定结论；
- 不在证据不足时宣称“客户端已收到完整结果”；
- 不在本组文档中规定具体代码结构、数据库表、SQL 或部署命令。
