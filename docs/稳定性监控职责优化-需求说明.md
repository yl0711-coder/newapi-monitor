# 稳定性监控职责优化——需求说明

> 版本：v1.0
> 日期：2026-09-02
> 状态：已评审，待研发
> 范围：Monitor
> 优先级：P0 稳定性口径纠偏；P1 职责闭环；P2 告警与运营增强

## 1. 背景

Monitor 当前已具备模型监控、稳定性报表、客户排障、服务端监控和多类日志采集能力，但不同模块对“稳定”“失败”“异常”和“用户感知”的定义尚未完全统一，存在以下业务风险：

1. 一次用户请求可能在多个上游渠道间重试。若按每条日志直接计算，前两次失败、第三次成功会被同时计入平台失败和成功，无法真实反映用户最终是否获得服务。
2. 用户请求不存在的模型、使用无效令牌、余额不足、权限不足等问题可能降低分组或渠道稳定性，但这些并不是模型或渠道故障。
3. 将上述问题从稳定性中排除后，如果没有独立展示和告警，又会导致用户已经无法使用，而运营侧“看起来一切正常”。
4. 当前部分结论依赖现时渠道配置推断历史责任；配置变化后，同一历史请求可能得到不同结论。
5. 部分页面用服务器日志推断客户端是否成功收到结果，结论强度超过了现有证据能力。
6. 数据缺失、采集滞后或分类不确定时，系统仍可能显示正常百分比，容易形成虚假安全感。
7. 模型监控、稳定性报表与客户排障都展示错误信息，但实时运营、长期衡量和单请求取证的职责边界不够清晰。

本需求优先解决“统计是否真实、责任是否合理、问题是否可见”三个问题。在口径纠偏完成前，不应以页面美化或功能合并替代核心修复。

### 1.1 当前现状审计基线

以下是本次评审已识别的高风险点。接手研发必须先逐项核对现有代码和真实样本，确认仍存在的项目后纳入 P0；不能只修改页面名称或文案：

1. **平台稳定性可能仍按日志行/尝试统计。** NewAPI 重试可能产生多条失败日志和一条成功日志。若直接按日志行汇总，会把用户最终成功的一个请求同时算成多次平台失败。
2. **实时和历史口径可能不一致。** 实时健康/SLO 与历史稳定性对“失败日志”“异常消费”“流式异常”的纳入范围不同，同一时段可能出现不同结论。
3. **使用当前渠道快照判断历史责任不可靠。** 当前是否有候选渠道不能证明历史请求时刻是否提供该模型，也不能证明候选渠道被实际调用。
4. **用户拒绝与服务失败可能混算。** 若所有错误日志都进入平台失败，不存在模型、无效令牌、用户余额不足、400/413 等会错误降低服务稳定率。
5. **客户端断开可能被重复或错误归因。** `client_gone` 既可能来自用户主动停止，也可能是平台、上游或网络先出现异常；不能再由“零输出”等单一规则自动归责。
6. **当前启用配置可能遮蔽历史事实。** 以当前启用、可选渠道过滤历史记录，会让后来停用或删除的故障渠道从历史报表中消失。
7. **部分展示文案强于证据。** “上游明确报错”“自动禁用已止损”“用户未收到”等表述必须有对应证据，否则只能写“观察到错误日志”“疑似交付异常”或“结果未知”。
8. **未知错误可能在不同模块得到不同处理。** 新错误码、未知结束原因或未识别流状态必须统一采取保守分类，不能一个模块计异常、另一个模块计成功。
9. **边缘证据可能未进入最终归责。** 只有 Nginx 入口/边缘记录的 5xx、连接异常或超时，不能因为缺少 NewAPI 使用日志而从平台问题中消失。
10. **客户排障的结论可能早于完整证据。** 若先完成责任判定、后补 Nginx 或上游证据，最终结论需要重新评估；不能保持过时结论。

上述项目是验收检查清单，不代表允许扩大修改范围。发现需要变更 NewAPI 或线上 Nginx 时必须暂停并单独评审；默认仍以 Monitor 自身采集、事实整理和展示优化完成本需求。

## 2. 目标

### 2.1 核心目标

- 平台稳定性按“逻辑请求最终结果”计算，一次用户请求最多进入平台统计一次。
- 渠道稳定性按“实际渠道尝试”计算，重试过程中的每次真实上游尝试分别归属实际渠道。
- 用户使用异常不降低平台和渠道稳定性，但必须独立统计、展示并在达到阈值时通知。
- 用户真实感知问题单独呈现，包括慢响应、流式中断、部分返回、连接中断、已扣费但未交付等。
- 证据不足或数据不完整时显示未知、暂定或不可判定，不得归为成功。
- 三个模块职责清晰、指标同源、结论一致，并能从聚合问题跳转到请求级证据。

### 2.2 业务成功标准

- 管理者能准确回答：平台是否稳定、哪个分组/模型异常、哪个实际渠道不稳定、多少用户受到影响。
- 运维人员能区分：平台问题、上游问题、网络问题、用户使用问题和证据不足。
- 客户支持能从聚合异常进入请求级证据，解释用户为什么失败或为什么无法下结论。
- 同一请求在不同页面中的最终结论不互相矛盾。
- 数据采集异常不会被显示为绿色正常或 100%。

## 3. 非目标

- 不修改 NewAPI 源代码或业务路由行为。
- 不通过 Monitor 自动改变渠道线上状态。
- 不保证在没有客户端遥测的情况下判断客户端真实接收、解析和落盘成功。
- 不把所有错误合并成一个“稳定率”。
- 不把客户排障重新开发成稳定性报表的内嵌功能。
- 不在本次需求中调整 Usage 站的用户用量和日志功能。
- 不更改“模型监控”名称。

## 4. 用户角色与核心问题

| 角色 | 核心问题 | 主要入口 |
|---|---|---|
| 技术负责人 | 当前平台真实稳定性如何，是否需要立即处置 | 模型监控、稳定性报表 |
| 运维人员 | 异常集中在哪个分组、模型、渠道或入口节点 | 模型监控、服务端监控 |
| 渠道运营 | 哪个实际上游渠道持续失败、变慢或被重试绕过 | 模型监控、稳定性报表 |
| 客户支持 | 某个用户、令牌或 Request ID 的完整请求链是什么 | 客户排障 |
| 数据维护人员 | 统计是否完整、采集是否落后、是否需要补数 | 数据同步状态 |

## 5. 模块职责

### 5.1 模型监控

定位：实时或准实时运营视图，建议关注最近 15 分钟至 24 小时。

负责：

- 分组、模型和实际渠道当前 RPM、错误率、延迟、重试和流式异常；
- 突发故障、短时抖动、单渠道持续异常和恢复状态；
- 真实上游尝试的实时质量与当前流量影响；
- 提供进入稳定性历史趋势或客户排障证据的快捷入口。

不负责：

- 90 天长期 SLO 结论；
- 单个客户请求的完整证据审计；
- 服务器 CPU、内存、连接数等容量指标；这些属于服务端监控/容量规划。

### 5.2 稳定性报表

定位：历史服务质量与趋势分析，建议覆盖近 24 小时、近 7 天、近 15 天、近 30 天和近 90 天。

负责：

- 平台逻辑请求稳定性；
- 实际渠道尝试可靠性；
- 用户体验异常趋势；
- 用户使用异常趋势；
- 数据覆盖率、证据等级、未知占比和口径版本；
- 按分组、模型、实际渠道和问题类型聚合；
- 展示问题聚合并跳转客户排障。

不负责：

- 展示完整原始日志全文；
- 在报表内复制客户排障的请求链和证据时间线；
- 根据当前候选渠道配置给历史失败强行归责。

### 5.3 客户排障

定位：面向单一请求、用户、令牌或时间窗口的证据工作台。

负责：

- 入口访问、鉴权/前置拒绝、路由、渠道尝试、上游结果、服务端/边缘结束状态和可选客户端结果的时间线；
- 同一逻辑请求的多次上游尝试及最终结果；
- 原始证据、证据来源、证据置信度和缺失项；
- 对稳定性报表中的问题聚合提供明细承接。

边界：本需求只定义客户排障的承接要求和数据契约，具体页面由对应开发工作完成。

### 5.4 数据同步状态

统一承接：

- 各采集器、同步器、补数任务的状态和水位；
- 失败原因、重试计划、人工修复入口；
- 数据缺口、延迟、覆盖率和维护任务。

业务页面只显示“数据截至何时、是否完整、结论可信度”，不得重复展示任务队列和补数运维操作。

## 6. 核心业务口径

### 6.1 四类必须分开的结果

| 类别 | 回答的问题 | 是否降低平台稳定性 | 是否降低渠道稳定性 |
|---|---|---:|---:|
| 平台逻辑请求结果 | 用户发起的一次有效请求最终是否完成 | 视最终结果 | 否，不能直接替代渠道口径 |
| 渠道尝试结果 | 每次真实调用某个上游渠道是否成功 | 仅在导致最终失败时影响平台 | 是 |
| 用户体验观察 | 是否慢、部分返回、中断、疑似未交付 | 按证据和最终结果 | 仅有实际渠道证据时 |
| 用户使用异常 | 不存在模型、无效令牌、余额/权限不足、参数错误等 | 否 | 否 |

不得再用一个统一百分比代替上述四类口径。

### 6.2 平台逻辑请求

- 一次用户请求，无论内部发生几次路由和重试，平台层只统计一次。
- 最终成功但经历失败重试，可标记为“降级成功”，平台仍视为交付成功，同时保留体验变差和渠道失败事实。
- 最终未成功且责任属于平台、上游或平台网络链路时，计入平台失败。
- 明确属于用户使用问题的请求单独统计，不进入平台稳定性分母。
- 不能可靠合并或判断最终结果的请求进入“未知”，不得计入成功。

### 6.3 实际渠道尝试

- 只有日志或链路证据明确记录的实际渠道，才能进入该渠道的请求量、成功率和失败率。
- 候选渠道仅表示当时可能参与路由的上下文，不得作为实际渠道归责。
- 未选中渠道、路由前拒绝或渠道 ID 为 0 的请求，不得分摊给任何候选渠道。
- 一次逻辑请求可对应多个渠道尝试，所以渠道尝试总数允许大于平台逻辑请求数。

### 6.4 用户使用异常

至少包括：

- 请求平台未提供或从未承诺提供的模型；
- 无效、过期或未授权令牌；
- 用户余额不足或额度不足；
- 用户无权访问分组/模型；
- 请求参数错误、请求体过大、协议不支持；
- 用户主动取消且没有更强的平台或上游失败证据。

处理原则：

- 不计入平台、分组、模型或渠道的服务稳定性；
- 保留分组、请求模型、用户、令牌、入口和错误原因；
- 达到次数、连续性或受影响用户阈值后通知运营/客户支持；
- 页面必须说明“不影响服务稳定率，但会影响该用户正常使用”。

### 6.5 用户体验异常

至少包括：

- 响应明显过慢；
- 流式响应中断或不完整；
- 已返回部分内容后失败；
- 客户端连接提前断开；
- 正常计费请求零有效输出；
- 已扣费但未能证明完成交付；
- 经重试后成功，但用户等待明显增加。

体验异常与责任归属是两个维度。即使暂时无法确认是客户端、平台、网络还是上游责任，也必须显示体验异常；不得为了保持稳定率而隐藏。

### 6.6 证据不足与未知

以下情况必须归为未知或暂定：

- 数据采集器停止、延迟超阈值或存在缺口；
- 缺少 Request ID，无法可靠关联多条日志；
- 只有当前配置，无法证明历史时刻是否承诺提供该模型；
- 只有服务端完成日志，没有客户端结果证据；
- 新出现且尚未纳入规则的错误状态或结束原因；
- 多个证据相互冲突，且无法确定优先级。

未知数据必须单列数量和占比。只要关键覆盖不足，页面就不能显示“正常/100%”。

## 7. 重点问题场景

### 7.1 渠道重试后成功

场景：渠道 A 返回 502，渠道 B 返回 429，渠道 C 成功。

期望：

- 平台：1 次成功或降级成功；
- 渠道 A：1 次失败；
- 渠道 B：1 次失败；
- 渠道 C：1 次成功；
- 用户体验：记录重试和额外延迟；
- 客户排障：展示同一请求下的三次尝试。

### 7.2 用户请求不存在模型

场景：用户请求 `gpt-5.4`，平台在该时刻从未对该用户/分组提供该模型。

期望：

- 不降低平台、分组、模型或渠道稳定性；
- 进入用户使用异常；
- 展示用户名、令牌、请求模型、请求分组、次数和最近发生时间；
- 连续发生或影响多个用户时产生提醒。

若平台在该时刻明确承诺提供该模型但无可用路由，则应视为平台服务失败，而不是用户错误。

### 7.3 无效令牌或额度不足

期望：不进入服务稳定率，进入用户使用异常；达到阈值后提醒客户支持联系用户或检查配置。

### 7.4 实际上游返回 5xx 或超时

期望：降低该实际渠道尝试可靠性；只有最终逻辑请求失败时才降低平台稳定性。

### 7.5 客户端提前断开

期望：默认显示为用户体验异常/责任待定，不自动判定为渠道失败；若存在更强的平台、上游或边缘异常证据，应按更强证据归类。

### 7.6 已扣费但未交付

期望：作为高优先级用户体验与资金风险问题；计入平台交付失败或未知责任，保留金额和影响用户；不得仅凭服务端“已写出”推断用户已收到。

## 8. 优先级与阶段

### P0：稳定性口径纠偏

- 冻结指标词典和状态枚举；
- 区分逻辑请求、渠道尝试、用户体验和用户使用异常；
- 停止用当前候选渠道作为历史实际渠道归责；
- 对无法证明的历史结论使用未知；
- 统一实时与历史页面对异常、失败和未知的定义；
- 修正文案，避免“明确上游报错”“用户一定未收到”等超出证据的表述；
- 数据不完整时禁止显示绿色正常或 100%。

### P1：职责与证据闭环

- 稳定性报表只保留问题聚合；
- 客户排障承接请求级证据；
- 模型监控专注实时异常；
- 三个模块共用分类口径和版本；
- 建立聚合问题到客户排障的筛选跳转。

### P2：运营与告警增强

- 按影响范围、持续时间和错误预算消耗分级告警；
- 对用户使用异常建立独立通知；
- 建立首发、持续、升级和恢复的事件生命周期；
- 完善跨页面趋势、问题对比和责任待定的运营流程。

## 9. 告警原则

| 级别 | 示例 | 主要接收人 |
|---|---|---|
| P0 | 平台承诺服务但全局无可用路由；大面积 5xx/超时；关键采集全面失明 | 技术负责人、运维 |
| P1 | 单分组/模型/实际渠道持续错误；批量流式中断；已扣费未交付 | 技术负责人、渠道运营 |
| P2 | 用户异常请求持续增加；特定令牌反复无效；局部慢响应 | 客户支持、运营 |
| P3 | 孤立用户误用、偶发主动取消 | 页面留痕，不强通知 |

同一事件按“原因 × 分组/模型 × 实际渠道/上游”聚合，避免逐条日志轰炸。告警应包含首次发生、持续、升级和恢复状态，并明确唯一主要负责人。

## 10. 约束与依赖

- NewAPI 源代码零修改。
- Monitor 的查询、刷新和报表不得增加生产数据库高负载查询。
- 没有 Request ID 时不得用相近时间强行合并请求。
- 历史责任判定依赖带有效期的服务承诺信息；在其建立前必须保守归为未知。
- 客户端真实结果只有在受控客户端主动上报时才可确认；否则只能描述平台或边缘观察结果。
- 原始敏感日志只允许管理员在客户排障中查看，聚合页面默认脱敏。
- 所有分类结论必须带口径版本，以便规则升级后可解释历史差异。

## 11. 交付物

- 指标词典与状态定义；
- 典型问题黄金样本集及预期结果；
- 模型监控、稳定性报表和客户排障的职责调整；
- 平台逻辑请求和实际渠道尝试的独立统计结果；
- 用户体验异常和用户使用异常的独立视图；
- 数据覆盖率、未知占比和口径版本展示；
- 告警分级和事件聚合能力；
- 新旧口径对账、灰度和回退报告。

## 12. 总体验收标准

- 一次逻辑请求在平台口径中只出现一次；
- 重试失败准确归属实际渠道，最终成功不被统计为平台失败；
- 用户请求不存在模型等使用问题不降低服务稳定性，但可查询、可聚合、可通知；
- 平台承诺服务却无可用路由时，不能被归类为用户问题；
- 候选渠道不进入实际渠道排名和稳定率；
- 证据不足、采集滞后或数据缺口明确显示未知/不可判定；
- 三个模块对同一请求的分类结果一致；
- 页面刷新不直接查询生产源，不明显增加生产数据库负载；
- 本需求上线不影响用户用量、Usage 日志及既有同步功能。
