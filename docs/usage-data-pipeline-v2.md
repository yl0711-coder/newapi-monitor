# Monitor / Usage 用量数据管道 v2

状态：核心用户用量管道已实现，等待真实只读来源性能验收；使用日志明细本地化另行实施。

## 1. 目标

这次改造是数据管道重构，不是针对某个用户或某条 SQL 的特例优化。
系统必须在“所有被跟踪成员都是高量成员”的情况下仍满足：

- Monitor 与 Usage 的 HTTP 请求只读本地已发布快照，来源 MySQL 不在请求链路中。
- 单次来源 SQL 的用户数、时间范围、返回行数、执行时间都有硬上限。
- 实时 Tail、历史补齐、审计修复拥有独立水位和错误域；历史积压不能阻断最新数据。
- 每个成员公平获得来源时间片。任何成员的热点小时都只能消耗一个有界 turn，随后必须让出。
- SQLite 写入、分页游标和校验信息原子提交；超时、进程退出、主机重启后从最后一页继续。
- 未通过独立来源控制和本地内容哈希的数据不能发布；损坏后按最小成员/时间分片自动重建。
- 一个成员失败只撤销该成员的新快照，不关闭其他已验证成员。
- 管理页能分别说明实时新鲜度、历史覆盖、发布状态、审计状态、重试/熔断和 ETA。

## 2. 明确不做的事

- 不按用户名、邮箱、用户 ID、公司名配置“大客户专用逻辑”。
- 不在来源 MySQL 对大范围日志做高维 `GROUP BY`。
- 不通过提高并发把压力转移给中转站数据库。
- 不用一个全局百分比代表实时、历史、发布和审计四种不同状态。
- 不因 Redis 或来源暂时不可用而回退到 HTTP 直查来源。
- 不把“查询成功”当作“数据完整”；完整性必须有持久证明。

## 3. 总体结构

```text
                      单一来源调度器
NewAPI logs  ──>  ┌──────────────────────┐
                  │ live: 最新闭合小时   │ 高优先、保留配额
                  │ cold: 历史补齐       │ 低优先、自适应分片
                  │ audit/repair: 复核   │ 低优先、独立退避
                  └──────────┬───────────┘
                             │ 有界原始页 + 第二遍有界复核
                             v
                  SQLite staging + durable cursor
                             │
                    本地按小时聚合/内容哈希
                             │
                    成员级 verified publication
                             │
              ┌──────────────┴──────────────┐
              v                             v
        Monitor 管理读面                Usage / Portal
        本地快照、可见 partial          仅已发布成员/范围
```

所有来源任务共享以下硬限制：

- 全局来源并发为 1。
- 相邻后台来源 SQL 启动间隔不小于 2 秒。
- 单条 SQL 服务端执行上限 5 秒，客户端超时不大于 8 秒。
- cold 与 audit 受 duty/circuit/disk gate 约束；live 保留调度机会。
- HTTP 请求产生的来源查询数恒为 0。

## 4. 通用自适应分片

### 4.1 分片不是客户配置

分片只由可观测工作量决定。初始 cold 分片最多覆盖一个 CST 自然日：

1. 读取第一页，最多 1000 条，游标为 `(created_at, type, id)`。
2. 如果第一页已满且分片大于 1 小时，不写本地事实，按 `24h -> 6h -> 3h -> 1h` 缩小后重试。
3. 如果第一页未满，继续按相同游标协议完成该分片。
4. 每个 turn 最多读取 3 页；未完成时持久化游标并让出调度权。
5. 第一遍结束后从头执行第二遍同样有界的分页复核；两遍的事件数、请求/退款、tokens、quota 和原始事件滚动指纹完全一致才完成。

因此：

- 空/低量成员最多用一个较宽分片覆盖多个小时，消除逐小时固定查询成本。
- 高量成员自动收缩到 1 小时，每页有界，不会形成大范围慢聚合。
- 如果未来所有成员都高量，吞吐按真实事件页数增长，但来源单次风险、成员公平性和页面可用性不变。

### 4.2 持久分片状态

每个状态至少包含：

- `user_id`, `from_ts`, `through_ts`, `source_epoch`, `tracked_revision`
- `lane`（live/cold/audit/repair）、`status`
- `(cursor_created_at, cursor_type, cursor_id)`
- 第一遍和复核遍各自的 cursor/pages/source_rows 与 tokens/quota/request/refund 累计
- 两遍独立的原始事件滚动指纹
- `content_hash`, `attempts`, `next_retry_at`, `last_error`
- `query_ms_last/max`, `last_served_seq`, `completed_at`, `updated_at`

页内事件在本地按自然小时和业务维度聚合。页产生的事实增量、累计控制数和下一游标必须在同一 SQLite 事务提交。不能出现“游标已前进但事实未写入”或相反状态。

### 4.3 完成与小时证明

第二遍有界分页验证整个 `[from_ts, through_ts)`。验证成功后，在同一受控本地提交中为分片覆盖的每个小时生成独立小时证明：

- 真实零流量小时也生成空内容哈希，区别于未读取。
- 每小时证明包含行数、请求数、tokens、quota、内容哈希和 source epoch。
- 日终签名只消费 24 个已验证小时，不能从全局最大时间推断。
- 两遍不一致时只重置该成员的该分片；必要时缩到 1 小时重新证明。

## 5. 三条独立队列

### 5.1 Live Tail

- 目标为 `now - finalize_delay` 之前的连续完整小时。
- 持久 `live_through`，只允许连续推进，不能跨过缺口。
- 优先处理最老 live 缺口，但热点小时每 turn 同样最多 3 页。
- live 延迟、最近成功、失败和待处理页独立展示。
- cold、审计或某个成员失败不得让 live scheduler 停止。

当前完整小时事实的新鲜度为 10–70 分钟（10 分钟安全延迟叠加小时边界）。
真正的 10–15 分钟展示需要另加可替换的当前小时临时层，不能把未闭合小时
冒充完整事实；该层未通过晚到日志覆盖与原子换代测试前，不写入已发布小时水位。

### 5.2 Cold History

- 从每成员 `source_floor_hour` 向当前已验证边界推进。
- 使用 `24h -> 6h -> 3h -> 1h` 自适应分片和成员轮转；分片不跨 CST 自然日。
- 只消耗低优先来源配额；slow circuit、磁盘压力或生产指标触线时持久暂停。
- 恢复后从分片游标继续，不突发补偿请求。

### 5.3 Audit / Repair

- 本地哈希审计不访问来源，可以独立快速运行。
- 来源审计按成员/小时抽样，复用同一双遍有界分页协议。
- 证明不一致时先撤销受影响成员对应发布授权，再创建最小范围 repair。
- repair 成功后重新签名并恢复该成员；其他成员继续服务。
- 来源超时与数据不一致必须区分：超时退避，不得伪称“已证明数据错误”。

## 6. 公平调度与背压

调度器采用 lane 配额加成员轮转：

- live 有硬保留配额，不能被 cold 借完。
- cold 与 audit 按固定比例轮换，repair 优先于普通 cold 但不能无限占用 live。
- 同一成员完成一个 turn 后领取持久单调 `last_served_seq` 并排到同优先级队尾；
  不依赖秒级时间戳，系统时钟回拨或同秒多轮也不会让成员饿死。
- 每个 turn 同时受页数、来源 wall time 和本地事务耗时限制。
- gate busy、租约冲突和进程取消不消耗业务失败次数。
- 3024/超时按 `1/2/5/15/30m` 持久退避；达到阈值进入 paused，人工或半开探针恢复。

如果所有成员都高量，轮转仍保证每个成员持续前进；不会由最小 ID 或最早历史成员长期占用来源。

## 7. 发布与读取

### 7.1 成员级发布

- 每个成员 revision 独立拥有 `source_floor`, `verified_through`, `content signature`。
- 新成员完成后可单独发布，不要求另一个高量成员先完成。
- 已发布成员重建时保留 last-good；只有确定性不一致才撤销该成员。
- 组织级总计若成员集合不完整，必须明确返回 partial/unavailable，不能把未发布成员当 0。
- 管理端可以查看已完成成员；Portal 只可查看授权集合与已发布集合的交集。

所有读请求绑定同一个不可变 publication snapshot：成员清单、范围、serving generation、fingerprint 一致；请求前后发生变化则丢弃结果并有限重试，不能提交旧缓存。

### 7.2 本地明细投影

聚合事实与使用日志明细分层：

- 聚合事实长期保存，用于 Monitor / Usage 图表、统计和跟进。
- 最近明细采用独立本地表，按 `(user_id, created_at, id)` 索引、有限保留，用于 Usage 日志和导出。
- 明细导入复用已读取的原始页，不再增加来源 SQL。
- 明细查询、导出和翻页只读本地；过期历史明确不可用，不回源。

## 8. 完整性与自动恢复

一份数据可发布必须同时满足：

1. source epoch 与当前配置一致；
2. 分片页游标连续，且最后一页少于 LIMIT（恰好为 LIMIT 整倍数时再用空页确认）；
3. 两次独立有界分页的事件累计与原始事件滚动指纹一致；
4. 本地小时事实的指标和内容哈希一致；
5. 日终 24 小时证明完整；
6. 成员 revision 在导入前后未变化；
7. publication generation 与读取边界原子一致。

恢复规则：

- 页事务失败：游标不前进，重试同页。
- 重启：按持久 cursor、lane waterline、retry time 恢复。
- 晚到/修订日志：最近小时轮换审计发现后，仅重建受影响成员小时/日。
- SQLite 行损坏：本地哈希审计撤销最小发布范围并创建 repair。
- 来源断开：所有 cursor 保留，last-good 继续只读；恢复时 live 先行，cold 不突发。
- source epoch 变化：旧签名整体失效，但旧快照保留给受控回滚；新 epoch 重新证明后发布。

## 9. 同步状态页

管理页必须分开显示：

- 实时：target/live_through/lag、最近成功与失败、当前成员/分片/页。
- 历史：总成员小时、已完成、剩余、最近吞吐、ETA、当前 span、页数和来源行数。
- 发布：已发布成员/总成员、每成员 floor/through/revision、partial 原因。
- 审计：本地/来源审计水位、repair 数量、paused 原因。
- 来源保护：并发、相邻启动间隔、duty、slow circuit、next retry、最近/P95/max SQL 时长。
- 本地资源：SQLite/WAL、磁盘水位、备份与恢复演练年龄。

`coverage` 只能表示历史覆盖；不能用它替代 live 新鲜度、publication readiness 或 audit health。

## 10. 容量边界

本方案不能消除读取真实事件的成本，但能把成本变成可预测的页数，并确保网站不依赖历史完成：

- 来源复杂度约为 `2 × 事件数 / 1000 + 低量分片探测数`；第二遍是完整性成本，但每条 SQL 始终有界，不再是成员小时上的无界聚合。
- 高维聚合与核对转移到本地，来源数据库只做同一索引上的有界范围页，不再执行标量全窗 `COUNT/SUM`。
- SQLite 单写者通过批量事务和分层表承担当前规模；持续监控写延迟、WAL 和行数。
- 当本地明细或写入超过实测阈值时，迁移目标是独立 OLAP/列存，不把压力退回来源 MySQL。

## 11. 实施顺序

1. 保留当前按小时分页协议作为兼容层，新增通用分片状态与纯本地单元测试。
2. cold backfill 切到自适应分片；live 仍走已验证 1 小时协议。
3. live 接入独立连续水位与统一公平调度。
4. 发布改为成员级，组织聚合增加明确 partial 契约。
5. 完成故障注入、全员高量压测和真实只读来源 pilot 后才允许用户用量事实切换。
6. 最近明细本地投影属于后续“使用日志”项目，不作为本次用户用量事实发布的隐含改动。

旧按小时状态必须可被新引擎读取或安全重签，升级不得清空已发布事实。

## 12. 验收门槛

代码与合成压测：

- 50/200/500 个成员全部为高量，单热点小时跨 20 页；每个成员在有界轮数内获得进展。
- 低量/空历史以不跨 CST 自然日的 24 小时分片完成，每个稳定分片恰好两条
  有界来源查询（导入、独立复核），相对逐小时模型显著下降。
- 任意页提交前/后崩溃、双遍 mismatch、SQLite 写失败、source timeout、lease busy 均可恢复且不重复累计。
- live 持续推进时 cold 热点成员反复超时，live 仍满足新鲜度目标。
- HTTP matrix/stats/followups/logs/export 的来源查询数为 0。
- 一个成员损坏时其他成员持续可读；组织不完整时不返回假 0。
- 普通、race、vet、lint 与确定性调度测试全部通过。

真实只读来源 pilot：

- 来源并发始终 1，相邻后台 SQL 启动间隔不小于 2 秒。
- 每条页查询不超过 1000 行；慢 SQL/3024 不形成一分钟固定脉冲。
- 完整小时 live 延迟稳定在 10–70 分钟契约内；若启用当前小时临时层，另行证明
  其 10–15 分钟新鲜度、晚到覆盖和切换到完整小时不重不漏。
- 本地聚合与真实来源抽样逐成员逐小时完全一致。
- 页面读取 P95、SQLite/WAL、来源 CPU/连接/慢查询、NewAPI P95/5xx 均在停止线内。
- 重启后 cursor 连续、无重复事实、无需人工清理即可恢复。

这些证据全部通过后，才能把“本机功能可运行”升级为“可生产发布”。
