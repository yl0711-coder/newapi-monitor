# Monitor 统一日志系统设计记录

> 状态：已记录、待评审，未开发、未部署。本文不改变当前 Monitor、NewAPI、Nginx 或任何采集器的运行方式。

## 1. 目标与当前盲区

目标不是把所有文本日志无限复制到 Monitor，而是建立“一次请求在各层发生了什么”的完整、可检索、可核对证据链，便于管理员根据用户提供的 Request ID 或时间快速定位。

当前数据分散在：

- Nginx access/error：能证明请求是否到达入口及入口状态，当前规划只上报脱敏分钟聚合。
- NewAPI 进程日志：包含选渠前拒绝，但管理后台使用日志无此记录。
- NewAPI `logs`：包含已进入渠道的交付与计费事实，但无法覆盖选渠前失败。
- `newapi-reject-collector`：已补上部分前置拒绝的聚合数，但目前不是可按 Request ID 查询的请求级日志。
- Monitor 采样库：主要保存聚合结果，不是全链路日志库。

## 2. 必须覆盖的请求阶段

1. 请求到达 Nginx。
2. 认证、限流、分组/模型校验和选渠前拒绝。
3. 选中分组、渠道和模型。
4. 请求上游、重试、流式中断及上游响应。
5. 用户最终收到的 HTTP 状态与延迟。
6. 进入 NewAPI `logs` 的用量与计费事实。

“事实展示”不自动修改错误原文，不把推测当成根因。可能原因和沟通建议必须放在独立的“建议”区域，并标明知识库规则版本。

## 3. 统一事件模型

每条请求事件至少保留：事件时间与收到时间、来源节点、来源层、请求阶段、请求方法与归一化路径、分组、请求模型、渠道 ID/快照名称、HTTP/上游状态、错误代码、脱敏后的错误原文、总耗时/上游耗时、流式标记、实际交付结果及采集批次。

Request ID 采用可查询的 HMAC 索引：各采集端对原值使用同一专用密钥计算 HMAC，Monitor 查询时对管理员输入的 Request ID 做相同计算。这样可以跨层关联，又无需在采集通道和日志库中保存 Request ID 原值。

## 4. 采集和性能边界

- 所有采集都是旁路异步 tail + 批量上报，不得成为 Nginx/NewAPI 请求成功的前置依赖。
- 不允许 Monitor 页面为了日志检索扫描生产 NewAPI 数据库；采集使用增量游标和有界批次。
- 采集器必须有 CPU、内存、PID、批次大小、重试和本地队列上限；中心不可用时不丢游标、不阻塞业务。
- 每个来源必须上报心跳、游标、待读字节、丢弃计数和最新事件时间；页面必须明示数据缺口，不得把缺失时段当成零错误。
- 成功请求只保留最小结构化元数据；错误、前置拒绝和中断保留脱敏后的完整错误事实。

## 5. 安全与留存

禁止采集 Authorization/API Key/Cookie、密码、完整 Token、请求/响应体、客户端 IP、完整 query 和其他可识别用户的自由文本。错误消息必须先执行密钥、账号、URL 凭据和 Header 脱敏规则，再入库。

建议分层留存，最终数值需经实际日增长压测确定：

- 热检索：请求级最小元数据 7～14 天。
- 排障留存：错误/拒绝/中断事件 30～90 天。
- 长期报表：脱敏的小时/日聚合 180～365 天。
- 需要更长追溯时，使用压缩、加密、有生命周期的对象存储，不无限占用 Ubuntu-1 本地磁盘。

在没有完成日增长、索引体积、查询 P95 和磁盘水位压测前，不在 Ubuntu-1 盲目部署 Elasticsearch 等重型组件。

## 6. 页面与排障流程

第一阶段在稳定性报表的分组/渠道/问题详情中增加“查看关联日志”，并自动带入当前时间、分组、模型和渠道条件。数据完整后再设置独立的“日志中心”入口，支持：

- Request ID、时间、分组、模型、渠道、节点、阶段、HTTP/错误代码检索。
- 同一请求按时间排列的入口→前置校验→选渠→上游→交付→计费证据链。
- 每条事实标明数据源；关联不完整时显示“未采集/未关联”，不自动补齐。
- 复制脱敏后的用户回复材料和内部排障材料，不暴露管理员专属字段。

## 7. 分阶段实施顺序

1. 确定事件字段、脱敏规则、Request ID HMAC 方案、容量基线与验收样本。
2. 将前置拒绝从“只有聚合计数”扩展为有界的脱敏请求级事件，保留现有聚合报表。
3. 按既定滚动流程接入 Nginx 专用日志和 nginxcollector，先验证完整性、脱敏和资源上限。
4. 增量引入 NewAPI 请求级最小事实，完成跨层 Request ID 关联和重复去重。
5. 开发日志详情/日志中心页面，再接入知识库建议；先完成事实，后做推断。
6. 完成容量压测、故障注入、断网/轮转/重试/幂等测试后，按单节点、可回滚方式上线。

## 8. 上线验收门槛

- 采集不可用、中心不可用或日志库满时，NewAPI/Nginx 用户请求不受影响。
- 用已知 Request ID 可关联同一请求；同批重试不翻倍，轮转和重启不跳过。
- 人工构造的六类阶段事件可全部查到，且错误原文不被自动改写。
- 密钥、Cookie、请求/响应体和用户隐私信息不出现在上报包、本地库、页面、导出或日志中。
- 查询 P95、日增长、磁盘水位、采集器 CPU/内存和积压恢复速度均通过上线预算。
- 完整性状态能明确区分“真实零请求”与“采集缺口”。
