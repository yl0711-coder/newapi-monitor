# 用户用量后台刷新可用性：本机第一轮验收

## 范围

- 基线：`v1.18.16`，`fc8633550e53fc37fd4dec27e21f0615d672ff3f`。
- 工作分支：`fix/usage-serving-availability-20261009`。
- 仅修复用户用量已发布事实在普通小时重采期间的读取核验，以及过期采集租约接手后的取消恢复。
- 不改金额口径、数据库结构、权限规则、渠道同步、经营核算或稳定性逻辑。
- 未连接或修改生产，未提交、打 tag、部署；发布工具的未提交修改保留在其他工作树，没有混入。

## 复现与原因

使用测试 SQLite、模拟来源和真实发布器，先发布两个成员的两个完整小时。
领取用户 88 的最后一个小时重采任务后，已有事实没有改变，但证明状态成为 `running`。
旧版全历史读取核验只接受 `complete`，因此误报小时证明 `got=1 want=2`，关闭全局读闸门；用户 152 的受保护查询也返回 503：

> 本地用量事实正在切换，请稍后重试

这个本机复现证明了一条可以产生线上同类报错的代码路径，不能仅凭相同错误文本断言线上所有瞬时 503 都来自该路径。

## 实现与安全边界

1. 只有**已经发布的区间**的读取核验允许检查重采中的旧证明。
2. 必须仍有完成时间、非空租约、内容哈希，并核对来源 epoch、实际行的指标和哈希。不是看到 `running` 就放行。
3. 新区间发布、回填游标推进、日终结算仍要求完整完成证明；采集状态仍为 `running`，原写入互斥不变。
4. 缺行、哈希不符、来源变更、成员撤权和修复暂停仍拒绝读取。
5. 旧租约过期后接手，若旧证明与实际内容吻合，保存其可恢复状态；接手任务被取消时不再误删有效旧证明。
6. 正常更新仍在原事务内替换事实和证明，并更新服务版本以失效缓存；相同数据重采不重复计入。

不绕过真正的完整性错误，不取消全局安全闸门，也没有将分页导入中的未完成候选事实标成可用。

## 验收结果

- 修复前：新增 HTTP 回归稳定复现 503。
- 修复后：后台刷新期间受保护查询返回 200；请求数、Tokens、消费金额不变。
- 关联回归：用户用量、Portal、全历史、原始分页、来源调度和旧发布状态保护，297 个测试项（含子测试）通过。
- 另补完整历史、首个非整日区间、过期租约、无有效租约四类边界并通过。
- 新增核心回归重复 5 轮 `-race` 通过；最后补充的边界测试另做 5 轮 `-race` 通过。
- `go vet ./monitor`、`git diff --check`、CI 分片唯一归属检查通过。
- Linux Docker 关联回归通过：断网、只读根文件系统、非 root、2 CPU/1 GB 内存；仅临时 SQLite、只读测试源码和本机编译产物。
- Linux 离线服务启动：`/health`、`/ready`、`/`、`/usage/users` 返回 200；零重启、无 OOM。没有生产来源连接。

容器验收最初漏挂页面测试夹具，随后临时目录容量上限过小触发了程序的磁盘保护。
补齐只读夹具、扩大临时目录容量上限后重新跑全套关联测试通过；没有降低代码中的磁盘安全阈值。
启动检查最初使用了未注册的 `/healthz`，对照路由后改用实际的 `/health` 与 `/ready`，均通过。

临时验收容器已结束或停止并自动删除；临时数据没有放入 Git。
产物位置：`/private/tmp/monitor-usage-availability.8Xq7AK`。
本次 Docker 验收复用已缓存的运行环境执行新编译二进制，不等同于正式发布镜像的构建和上线验收。

## 后续顺序及限制

本轮修复覆盖普通小时重采与中断恢复，不宣称四个模块均已完成，也不宣称已排除所有 503 来源。
原始分页首次重建若删除旧证明、真实完整性缺口、发布版本并发变化仍需分别按证据判断，不能用本补丁兜底放行。
后续继续检查渠道同步恢复及历史充值比例，再推进经营核算缺口与稳定性完整性问题。
正式发布前仍需对汇总后的候选代码执行发布验收、CI、精确版本镜像核对及回滚准备；当前没有发布授权动作。
