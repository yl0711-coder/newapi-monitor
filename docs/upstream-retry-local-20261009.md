# 渠道同步恢复：本机第二轮验收

## 边界

- 基线为 `v1.18.16`；与上一轮用户用量读取可用性补丁保留在同一隔离开发分支。
- 本轮仅修改共用上游请求层的 HTTP 503 冷却处理，未改变认证方式、金额口径、数据库结构或充值比例配置。
- 未连接生产、请求真实上游、修改线上数据、提交、打 tag 或部署。

## 已复现的问题

上游返回 `503 Retry-After: 3600` 时，旧代码只对 429 提取和持久化冷却时间。
新增回归在修复前确认：主机冷却截止时间和传给任务的重试截止时间均为零。
这会让任务按较短的本地间隔重新访问；手动恢复或进程重启也不能正确沿用该 503 冷却。
这是一条已复现的代码问题，不代表已经查明线上 a6api 的 403 原因。

## 修复

1. 503 明确携带 Retry-After 时，共用 JSON 请求错误保留截止时间，任务排期不得提前。
2. 共用主机保护器持久化相同冷却；其他任务及重启后的恢复探测不能绕过。
3. 503 未带此头时保持原有有限重试；已有普通熔断时间比头部更长时取较晚时间。
4. 秒数、HTTP 日期沿用现有解析；格式错误沿用已有保守默认值，最小间隔不变。
5. 401/403 不因携带此头而开启主机级熔断，仍由账户自身的认证/失败策略处理。
6. 不因失败清空已有余额、成功时间或其他已发布事实。

原有有限重试、递增探测间隔、达到上限暂停、手动只读探测恢复、重新配置凭据后的激活机制继续复用，没有再增加一套同步框架。
暂停任务不是无限自动重试；探测成功也不等于账单已同步完成，必须由真实同步成功后重置失败预算。
