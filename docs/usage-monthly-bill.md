## 功能边界

这是客户用量门户的账单功能，不是财务系统。组织管理员按需选择已结束的北京时间自然月，触发后台生成；核验完成后保存账单，可重复查看并下载原生 Excel。不支持当月正式账单，不在客户访问时扫描生产日志，也不自动生成所有历史月份。

账单包含组织汇总、逐账号收支、账号下逐令牌消费。Excel 有「月度账单」「账号收支」「令牌消费」三个工作表，与页面读取同一已保存版本。已有使用日志及其导出入口保持独立。

后续优先级调整为先闭合自助路径，再继续剩余四个历史月份验收，不再仅靠手工增加月份文件推进“功能完成度”。修改按三个小步骤实施：

1. **权限及月份策略**：正常模式复用 Usage 授权和真实注册时间，明确区分旧精确灰度配置。验证新月跨界无需配置/重启、新组织正常开通 Usage 后可用、当月及注册前拒绝、新成员与撤权仍隔离。此步不改金额计算或已保存账单。
2. **正常资料按需接入**：后台使用有界只读来源、已保存依据与既有核验规则自动形成输入，不要求每组织/月提供 scope/history 文件。不能删除源身份、余额/消费/资金完整性核验，也不能补零、猜余额或搬用其他客户资料；历史异常按已确认统一规则内部处理，来源故障有界恢复，真正冲突保留原账单并告警。
3. **实际产品入口验收**：从空账单/空准备目录，经正常产品启动和客户登录点击完成新组织首月、同组织新月、跨年、零消费月、新增成员/令牌、重复/并发点击、失败恢复及重启下载。禁止在测试前用操作员工具或内部直接注入逐月准备输入；页面、逐用户、逐令牌及 Excel 金额必须与独立原始依据一致。通过后再与剩余历史样本联合验收，不能用合成样本覆盖真实历史缺口。

这是同一账单需求的必要收尾，不增加 ERP、批量自动出账、充值管理或其他模块功能。本轮核对及合成回归不连接线上、不部署，也不把尚未实现的策略描述为已经启用。

## 本次收尾的固定范围与完成门禁（2026-10-28）

业务负责人已明确：**客户起始月是客户在 NewAPI 平台的注册月份**，不是首次消费、首次充值、Monitor 录入组织的月份或最早留存文件月份。只处理客户自己点击生成的月份，不做定时批量出账，不新增 ERP、定价、资金调拨或其他模块功能。下面是尚待全部实现的收尾约定，不表示对应功能已经完成或具备上线条件。

### 月份与客户范围

- 单账号从其真实平台注册月开始，到服务端北京时间上个自然月截止；当月、未来月及注册前月份不允许生成。注册当月只有结束后才能生成；当月新客户提示首份账单可生成的月份，不留一个无法理解的禁用按钮。
- 注册时间读取主站 `users.created_at`；现有 `CustomerGroup.CreatedAt` / `TrackedUser.AddedAt` 是 Monitor 元数据，用户名缓存也未同步注册时间，均不能替代。旧账号注册时间缺失时只能复用或提取真实原始注册依据，不以首次消费/充值冒充注册，不套用其他用途的“注册与最早日志取较早值”逻辑。
- 组织内按账号各自注册月份处理，可选起点取所属账号最早注册月；后来注册的账号不要求注册前消费资料，也不能把其注册赠送提前到旧账期。月份范围不改变既有成员授权与归属规则，已保存账单仍冻结原成员和金额，不因新增账号重写。
- 注册后无消费的封闭月份可生成零消费账单，资金和余额照常核验；取数失败、账号不存在及来源缺失不是零消费。页面与服务端使用同一范围，未授权客户不能通过改请求扩大范围。全部月份入口仅查看已保存账单，生成请求必须指定月份。

### 一条客户操作链，不再以分段测试替代完成

1. 正常服务启动时安装按需准备器，复用现有连接、查询限流和运行生命周期。先核验当前 Usage 权限及注册月份范围；不要求逐个手填组织/月白名单才能正常使用。灰度开关可以保留，但不能冒充通用客户能力。
2. 合法月份首次读取状态应允许客户提交；只有已经显式接入且通过准入的按需准备器可以把未准备状态转换为尚未申请。只读状态查询不采集、不入队、不重试。直接读旧预制资料模式、撤回、权限变化及未支持范围不因此放行。
3. 客户点击一次，后台取得完整账号范围，复用已有有效资料，按需补取资金、用户/令牌消费及余额重建所需的确切区间。历史来源定位不能长期依赖 AI 或人工为每个组织/月制作包。
4. 现有固定起点连续展示规则只约束该客户注册后确实需要的内部计算资料；不能要求客户先生成所有前月账单。准备缺失依赖、复用已核验结果，仅保存客户申请月份。已发布金额不因顺序、倒序、重试或补资料改变；不为分位展示重复采集所有历史日志。
5. 核验后事务保存，页面与三个 Excel 工作表读同一保存版本。已保存结果不依赖生成线程持续运行，不因重复申请再次计费或出另一份账单。
6. 临时来源故障冷却且有界恢复，资料补齐后有明确继续路径；真正金额冲突暂停对应任务，其他组织可继续。不能靠客户反复点击清空失败预算，也不能让一次失败永久锁住合法月份。源端 SQL 限时、连接限流及保护现有业务的边界不放宽。
7. 按账号/日期工作量验证步骤、记录及字节容量；现有 4096 步、32 份输入/封存请求、256 条准备记录是开发保护，不是正式业务承诺。必须补齐实际规模下的任务推进及保留/归档方式，不能仅调大常量或删除已采用来源、已保存账单腾空间。

### 上线前必须通过的整体验收

| 场景 | 必须取得的结果 |
|---|---|
| 当月新注册客户 | 无可生成的已结束月份，明确提示首份账单时间；伪造当月/注册前请求也被拒绝 |
| 上月注册但无消费 | 上月可点击，生成零消费账单；不要求注册前资料，正常保留当期赠送/充值 |
| 多账号、不同注册月份 | 用户各自账期正确，晚注册成员不阻挡历史月份，不跨账号冲抵 |

| 未知令牌、同名令牌、改名和退款 | 按账号/令牌 ID 独立汇总，与原日志金额及退款口径一致 |
| 金额与跨月 | 原始整数金额核对，分位显示可闭合，相邻账单边界一致；不能为凑数改消费 |
| 重复点击、响应丢失、重启 | 同一结果恢复，无重复任务/重复校正，保存后查看和下载不变 |
| 临时故障、补齐资料和真正冲突 | 可恢复故障能继续，永久冲突不伪造成功，其他组织不受阻 |
| 大组织及重复使用多个月 | 不触发任意开发上限，耗时/内存/磁盘/SQL 压力有实际测试记录 |
| 安全与回退 | 跨组织、撤权、撤回不可读；停止生成仍能读取已有账单；原 Usage 和 Monitor 功能不受影响 |

前后端必须使用同一实际状态契约测试：后端返回未准备、前端却只模拟尚未申请不能算通过。必须增加从真实首次 GET、按钮提交到保存/下载的联合路径，最终复用留存真实数据验证；合成测试、直接 POST 或预制完整文件各自通过，均不能替代这一门禁。

实施顺序固定为：月份范围与首次点击 → 必要资料与跨月依赖 → 正常服务接线、恢复及容量 → 真实数据整体验收。发现新的真实阻塞须归入上述范围并记录，不增加新业务目标；全部门禁通过后再准备提交、发布，不承诺绝对无缺陷，也不能用局部通过宣称功能已完成。

## 金额和权限

### 新系列的整分展示（本机候选，尚未上线）

具有完整逐令牌依据、且尚无已发布账单的新注册范围系列，使用 `monthly-cent-bill-v1`。原始金额与客户展示计划分别保存于现有账单载荷，不增加表或列，不修改钱包、消费日志或资金记录。

- 组织的消费、退款分别按十进制四舍五入到分；净消费为两者之差。用户及令牌按确定性的整分分配保持逐层合计一致；原始零额仍为零，不为全额退款制造净消费。
- 组织及用户月末展示余额按展示收支计算，并结转至下一月展示期初。充值、赠送及其明细同样保持合计一致。页面与 Excel 共用保存时固定的计划，不在访问或下载时重新分配。
- 发布事务重新校验完整来源、组织权限、已有账单及计划。旧格式系列沿用旧策略；不混用、不覆盖、不自动迁移已发账单。升级前已固定任务绑定的旧任务，只有重建结果与原绑定完全一致时才按旧格式继续。
- 现有 `display_balances` 结转和历史尾差规则仅适用于旧格式。新格式客户视图直接使用已固定的整分值，不新增技术尾差行；后台核验仍读取原始精度的来源值。
- 旧版本无法读取新载荷时必须拒绝，不得当作旧账单显示。回滚旧程序前须停止月度账单生成并关闭不兼容的账单入口，保留所有原件及账单库；不得删除新记录来强行回退。完整部署/回滚演练仍属于上线前门禁，不能以单元测试代替。

本机回滚操作顺序：先停止生成服务并等待在途操作排空，使用 `MONITOR_PORTAL_MONTHLY_GENERATION_ENABLED=false` 重启为只读账单服务；此时已保存的兼容账单仍可查看及下载，但不得接受新月份任务。如需退回不支持此格式的程序，再设置 `MONITOR_PORTAL_MONTHLY_STATEMENT_ENABLED=false` 并关闭账单入口，切换旧程序前对最新接收库、资金资料和原件做一致性备份。默认保留最新数据库，不用发版前的旧库覆盖已生成的新账单。恢复候选程序时先以生成关闭方式校验已保存账单及下载版本，核对通过再恢复生成；不重置任务预算或重发已保存月份。

2026-11-01 本机合成数据演练：候选程序保存两个新格式月份；用本地 `v1.18.36` 原始代码（仅额外加入验收测试）打开同一数据库，验证登录页、已认证主页面及静态资源可用，月度账单路由均不可访问，原账单未改写；再切回候选程序，账单记录、详情响应与 Excel 字节均保持一致。另通过实际生成服务的停止、已保存结果复用、禁止新任务及只读路由回退测试。此结论限于本机合成资料及该基线，不替代待发布镜像和实际部署环境检查。

- 金额展示使用十进制整数舍入，半分钱向绝对值增大的方向进位，例如 `1.005000 → 1.01`、`-1.005000 → -1.01`；不使用二进制浮点数或银行家舍入。舍入结果为零时统一显示 `0.00`，不显示负零；这不改变原始小额负余额。页面格式化与页面对账共用整数分函数，Excel 遵守同一规则。
- 使用整数 quota 运算，500,000 quota 为 1 元；原始计费精度最多六位小数。账单列表、汇总、账号及令牌明细、额度变动和 Excel 金额均显示两位小数。原始金额先按原精度汇总，不逐请求舍入。账单展示的派生月末余额按已显示的两位金额，以整数分计算“月初 + 到账 + 扣减 − 消费 + 退款 + 已核实校正”，不再单列收支等式的四舍五入尾差。只有原始等式精确成立才进行此展示计算；冻结账单中的原始余额、实际钱包和扣费不变，不能用展示计算修复真实差异。账号、令牌独立分项与组织合计之间仍按原精度核验，必要的分项舍入差异另列。Excel 金额单元格写入两位小数，与页面所见及 SUM 运算一致。
- 跨月期初继承已冻结的前月展示结余，不再独立舍入原始余额。倒序补账以已冻结的后月期初反推展示边界。原始金额字段保持原精度，展示金额单独冻结；已发布账单不因再次访问、重试、重启或新增成员而重算。
- 每个账号独立核对：期初余额、到账、其他已核实变动、消费、退款和期末余额。负余额不截成零，转出和转入不跨账号抵消；逐令牌消费必须与所属账号核对。
- 用户与令牌消费明细默认展开并直接展示，客户可自行收起；收起/展开不重复渲染、不查询上游，也不重新计算金额。无令牌消费时明确显示空记录提示，旧账单无此明细时不虚构。
- 来源完整性、余额依据和差异处理均须核实。文件摘要只能证明文件身份，不能证明上游日志没有丢失，不能用非空复核字段代替真实核验。
- 已保存账单保留当期冻结的成员和令牌明细，不因后续成员变动重算。新生成须核对当前完整成员范围及权限版本。
- 跨组织、撤权及撤回版本不允许访问。客户响应不包含数据库路径、私有证据、内部复核详情、凭据或管理员专属诊断信息。
- 重复请求复用同一任务或已保存版本。重启后可恢复；不能因为重试或下载再生成另一份金额不同的账单。

### 跨月展示结转（本机已接入，尚未上线）

`monthlyPlanDisplayChain` 是不含读写的金额规划函数。发布时由 `monthlyFreezeDisplayBalances` 在原有账单事务中读取同组织前后相邻月份并校验，再把 `display_balances` 可选字段与账单一起冻结保存。该字段只含版本、组织期初/期末及逐账号的期初/期末，不向客户暴露内部来源、摘要或校验细节，不增加 SQLite 表或列。

第一次规划以原始期初余额舍入到分为锚；顺序生成时继承前月已确定的展示结余；倒序补账时以已确定的后月期初反推前月的展示边界。仅展示金额结转，原始消费、充值、退款和余额不变。页面与 Excel 都读取冻结字段，并验证每个账号和组织的展示变化量与原始消费、到账等分项舍入后的变化量一致。

已保存的结转计划必须幂等复用，不重算覆盖；原账单内容变更、真实余额边界不一致、组织/账号混用、损坏摘要或两端已冻结而中间无法衔接时，返回明确冲突，不通过修改消费或移动账号资金来强行对平。新增零余额账号可正常衔接，非零余额的成员迁入/迁出须另行核实。分位记录的摘要只证明身份，不替代原始依据与权限核验。

旧账单没有该字段时保留原有独立两位展示，不在 GET 时写库或改已存数据。新账单衔接旧账单时使用其现有展示边界；两个已冻结端点相互冲突时拒绝发布中间账单，不覆盖两端。新冻结字段包含在原有载荷摘要和发行版本中，保持原有撤权、撤回及下载最终版本复核。新发行 ID 带格式标记，若冻结字段丢失，即使外层摘要被重新计算也不允许退回旧展示规则。对含冻结字段的账单，客户端必须发送 `X-Monthly-Display: cents-chain-v1`，否则返回刷新提示，避免已打开的旧页面使用不同显示规则。

本机已验证顺序/倒序、跨年、重复、账号隔离、事务失败回滚、相邻月份并发及数据库重新打开后金额与 Excel 不变；浏览器交互和最终发布门禁仍须单独完成。旧版本回滚时须关闭月度账单入口，避免不认识该可选字段的旧前端继续显示新账单；不删除或改写账单、原始余额及使用日志，其他 Usage 功能保持独立。

### 小额余额差异的统一处理

所有组织复用 `automatic-wallet-v1`，不为单个客户另设计算公式或账单格式。原始充值、消费和退款不变，不能调低消费来凑余额。

- 自动校正仅适用于余额高于原日志推算、对客户有利的差异；单账号单月须同时不超过 5 元和当月日志净消费的 0.01%。金额小不等于已经通过核验。
- 使用同一账号、同一月份、同一消费及资金范围的两份独立留存依据，间隔至少 5 分钟，反推的月末余额与净用量须一致。来源缺失、差额仍变化或无法确认月份归属时，不伪造这些字段，也不绕过原有核验。
- 通过核验的差异使用已有“余额校正”项单独列示，页面和下载保持一致；不伪装成充值、退款或消费，不修改 NewAPI 实际余额和原始日志。
- 校正随已保存账单冻结，重复生成不能再计一次；相邻月份承接上月期末余额，不能每个月重复补同一历史差额，不得跨账号抵消。

历史累计差额不能仅凭大小直接归到所选月份，不因此自动切换为另一种客户账单或把当前余额标为历史月末余额。

### 已确认无法追溯的历史小额差异

对已经排查、由业务负责人明确接受的历史小额正差异，使用独立的 `historical-wallet-recognition-v1` 处理决定，不再重复追查丢失事件。确认账期是处理归期，不声称已经证明差额实际发生月份或根因；不能伪造普通自动校正需要的两份当月观察。

- 决定按账号、组织、确认账期和明确金额留存，绑定独立来源文件及其摘要；仅由私有资料准备链路提供，客户不能通过请求参数指定校正金额或依据。
- 仍须核验完整消费、资金变动及余额衔接区间，余额差额和累计用量反向差额必须等于同一已确认金额。缺失数据、未稳定采样、可能多扣、较大或新增差额不因本规则而自动放行；小额上限保持不变。
- 在首次受影响且可完整重建的确认账期单列一次“余额校正”，原始充值、消费和退款不变；后续月份将其承接到期初余额，不再新增校正。来源和处理决定保存在内部证据中，页面和 Excel 使用同一金额版本。
- 保存时按账号核验已有历史处理决定，即使中间月份尚未生成、或账号归属组织发生变化，也不得换一个账期再次校正。已保存账单仍不可覆盖，正常账号不启用本规则。

业务接受历史处理方式不等于已证明所有月界余额。资料准备必须保留“重建及历史处理”的真实依据，不能将处理决定改称原始余额快照或已证实的 NewAPI 故障。

若账期后的留存采样正处于活跃扣费、不能核对结算截点，可在本处理路径中显式选择账期内已独立核验的安静采样，并用完整尾部消费、退款及资金流水前推月末余额（`bridge_direction: forward`）。必须保留对应原始部分区间查询和完整账期资料；不能以“已接受历史差额”为由忽略尾部缺口，也不能把当日金额或 Token 按时间比例分摊。原有后置快照反推方式不变，不存在失败后的自动回退。

没有历史差额的月份也可显式使用 `forward`，但要求输入保留对应原始余额及累计用量快照，且消费/退款区间在观察时刻有精确边界，观察后直到月末的资金覆盖完整。上下文中的尾部金额必须与这些留存区间逐项一致，不能仅有整月汇总后用余额或计数器残差反推尾部。任一来源、边界或双向金额不符仍阻止出单；不增加历史校正、不改写已有账单。已确认差额的原处理路径保持不变。

完整核验过的整月请求数、Token 数可通过私有准备输入的 `month_statistics` 独立留存（账号、月份、请求数、Token 数、原始来源）。它仅补充细分金额窗口中未知的统计，不改变任何消费、退款、余额或资金记录，且与已知区间统计不一致时拒绝出单。历史目录筛选会保留对应来源；有原始用量观察时，请求数仍按原观察重新核对。没有整月来源时继续显示未知，不按时间或金额比例猜测尾部 Token 数。省略该可选字段不改变旧输入的行为和序列化。

组织内后来注册的成员不应阻挡更早月份，也不能被悄悄移出组织。自动准备仅在其原始零基准晚于该月、完整原始用量观察确为空、原始注册赠送与无更早活动依据齐全时兼容该月份；不插入注册前消费区间、不前移原始余额或赠送。注册依据使用私有来源引用加 RFC6901 路径（例如 `original_inventory#/accounts/7/first_funding/0`），从已校验指纹的原始 JSON 行重新走既有资金分类器，并逐项核对账号、ID、时间及额度。未来赠送仅用于注册证明，仍由原月份过滤器排除，绝不记入更早账期。零价请求也属于真实活动，缺失窗口、缺证或任一不一致继续拒绝整个组织出单；正常已注册成员、当前授权及既有账单不可变规则不变。

## 简化生成模式（`simple`）

客户在门户点“生成”后进入单一后台队列，单次约 25～35 秒（其中 20 秒为两次余额读取的固定间隔，用于排除在途扣费），排队时页面显示前面还有几份及预计时间。

- **口径**：每月消费、退款、请求数、Token 数取 Monitor 本地已与 NewAPI 日志核验过的每日用量事实（`usage_daily_facts`）；充值、赠送、扣减取从库资金日志。余额从成员注册时的 0 按日志逐月前推：`月末 = 月初 + 充值赠送 + 调整 − 余额支付消费 + 退款`，结果与生成顺序无关，用过的月界冻结、后续复用。消费不因任何余额差额而改动。
- **内部对账**：每次生成用 NewAPI 当前钱包反推月末余额，与日志前推结果的差额只写入 `portal_monthly_simple_audits.wallet_residual`，不出现在客户账单；差额超过 5 元或钱包低于日志推算值时不出账，转人工复核（典型原因：线下改余额未留日志）。
- **订阅**：日志 `other.billing_source=subscription` 的用量（扣除 `wallet_quota_deducted`）计为“套餐内”，不进入余额；订阅开通当月在账单最前加“订阅服务账单”页，名称、售价取 `MONITOR_PORTAL_SUBSCRIPTION_PLANS`/`_OVERRIDES`。订阅部分保存在 `portal_monthly_simple_subscriptions`，其 SHA-256 写入账单证据的 `source_reference`（`;subscriptions=sha256:`），读取时校验。
- **Excel**：版式与业务已发给客户的模板一致（页序：账号收支 / 月度账单 / 令牌消费，样式表取自该模板 `monitor/portal_monthly_simple_styles.xml`）。有订阅时三页增加“其中套餐内”“其中余额支付”。导出前校验各余额等式与合计，不一致拒绝导出。
- **金额精度**：每个显示金额与真实值相差不超过 1 分，真实为 0 显示为 0，账单逐账号、逐组织精确平衡，相邻月份首尾相接。

权限依据固定为当前 `MONITOR_STORE_PATH` 对应的主库，不提供客户自选数据库入口。开启生成时，配置错误必须在开始服务前被发现；关闭生成时不打开或校验遗留生成路径。

接收循环只处理已准备且核验通过的资料，不负责自动修复缺失证据。白名单仅限制允许生成的范围，不证明其中每个月份已经具备生成条件。

### 按需自动准备第一轮（仅本机开发，未接入生产）

现有接收目录不能代替自动取数。本轮新增 `LocalRuntime.EnableOnDemandPreparation`，必须在启动前显式提供可信的准入策略和可恢复的分步准备器；默认关闭，不新增生产环境变量，不扩大现有组织/月白名单。

- 客户只选择月份；组织、权限版本及完整成员摘要由服务器读取。首次缺资料的申请写入独立 receiver 的 `portal_monthly_source_preparation`，HTTP 不采集资金或消费资料。读取进度不创建或重试任务。
- 相同组织、权限/成员版本和月份去重；每组织最多一个准备中任务，全局最多八个活动任务，记录总量上限 256。原始选择被撤回时，不自动重新启用旧资料。
- 单次准备步骤限时 20 秒，执行时不持有 receiver 事务；同一 receiver 最多一个活动准备租约（60 秒）。正常分步最多 4096 步、总历时最多 24 小时；失败退避 30 秒，最多三次，进程中断导致的过期租约也计入失败预算。客户重复点击不能清零失败次数。
- 准备器必须以稳定请求键保存自己的断点并响应取消。它报告完成后，队列仍重新核对当前授权及既有选择链，再交给原有生成和金额核验流程；任务入队或准备成功都不是已发布账单的证明。

### 容量收尾第三轮：分块原始用量的完整核验读取（仅本机）

本轮只增加显式的 `ReviewPartitionedCapturedUsage` 与 `VerifyPartitionedCapturedObservationSelection` 来源核验读取器，不改客户账单格式、金额或默认生成方式，也不做归档轮换。原 `ReviewUsageMonth` 仍拒绝超过 4096 对引用，旧捕获读取仍使用原限制；新格式不会被旧读取器默默当成可用证据。

新读取器要求调用方固定原选择文件 SHA256 和完整组织范围。所有块先按原摘要完整重组，再读取原始用户投影；缺块、增块、重复引用、串账号、范围或摘要变化均失败。分块摘要只证明资料身份，不能代替原件、令牌、资金、钱包或历史核验。显式完整选择读取器还继续运行原资金、钱包、恢复时间片形状检查；原令牌档案、独立历史资料及发布授权仍由后续原管线检查。

旧读取器和新读取器共用相同的观察对、独立间隔、窗口、来源分类、整数累计与溢出检查。新读取器在同一只读 SQLite 事务中读取全部块，不把不同时间点的快照拼起来。最多 512 对为一个读取小批次，每批保留三秒时限，原捕获核验三十秒总时限和 64 MiB 全局原件预算不按块重置；新增总窗口上限由原账号/日基础量和最多 128 个恢复根各 16 叶派生。最初按接近 4096 对单批执行，在竞态测试中触发三秒时限，已改成较小读取批次，而非放大单批时限。

新增六项顶层测试：200 账号三十一天共 6,200 对真实落库的合成用户观察逐项核验，金额刻意超过浮点安全整数；逐账号消费、退款、次数、覆盖秒数和原引用保持一致，关闭后按只读方式重开结果不变。与旧读取器的小样本报告逐项一致；缺原件、损坏、账号不存在、越界归属、时间缺口/重叠、正反差异抵消、整数溢出均不返回可用部分结果。另以本机 WAL 竞争写入验证共享快照，以共享累计器验证下一批不能重获字节预算。新读取器返回原有不可反序列化的过程内观察，而非可编辑的核验通过标志。

来源模块完整常规回归、相关来源竞态回归及新增六项竞态测试通过。断网、非 root、只读根、限资源 Linux 容器中，新增及原来源兼容共十九项顶层测试通过；大样本单次用户投影核验约 0.32 秒，仅代表此合成本机环境。原准备/生成兼容二十九项顶层竞态测试先因组合累计超过三分钟而超时，保留全部断言拆成四组后全部通过，覆盖原用量核验、规范化、历史资料、封存、保存与下载。静态检查、`go vet`、格式检查和全包编译通过；编译不能冒充业务验收。这些测试使用合成资料，不是线上 200 账号压测，也不是完整大组织账单已发布的证明。

### 容量收尾第四轮：封存交接、原规范化与实际出账接线（仅本机）

### 容量收尾第六轮：已正式保存资料的单任务归档、释放与原样恢复（仅本机）

复制、启用、释放/恢复三步独立：`CopyPublishedGenerationArchive` 向调用方明确指定的空私有目录写入单份 v2 清单及原计划、准备资料和完成产物，校验后发布清单；完整副本可回放，失败残留不覆盖、不删除。`InitPublishedGenerationRetention` 必须单独显式调用，仅改变本机独立接收库的删除保护，不改主业务库。`ChangePublishedGenerationPayload` 每次只处理一个原任务，重新核验当前账单、原件和清单后，在一个接收库事务里核对保存日志/任务完整快照，原子提交归档引用、临时许可及热载荷释放。恢复也受原 32 份/64 MiB 预算约束，只插回同样字节，不重新排队、不重置失败次数、累计额度或创建时间。

归档 v2 明确固定原任务、存储快照、产物、保存日志、客户账单完整记录/金额、成员授权和证据摘要。核对客户账单时复用原展示读取及原证据构建规则；逐账号/令牌、充值和消费必须匹配原证据。并从冻结的分币钱包、来源与锚点重建**原保存日志的同一种绑定摘要**，不是把账单证据摘要错误地当作保存日志摘要。旧绑定摘要的算法和序列化不变。旧 v1 清单保持原 JSON 字节兼容；冷读器支持两种格式，但旧维护入口不能降级新的删除保护。主账单、来源文件、任务/保存记录均不删除或改写。

这不是全自动生命周期收尾：尚未接入运行时的容量回收调度，也没有释放原始封存队列的 32 份容量，旧失败任务的有界恢复仍单独处理。主库与接收库是两个数据库，归档不能声称与主库之后发生的撤回跨库原子；因此冷原件及引用永久保留，撤回不改变账单金额或销毁原件。新 v2 清单不承诺旧二进制可读：启用前必须部署冷读兼容代码，退回旧代码时先停生成，不能在热库已满时强行恢复全部旧资料或抹去容量限制。已保存客户账单的独立查看/下载不依赖热载荷。

### 容量收尾第七轮：原始封存资料原地保留、工作槽与完成件分账（仅本机）

定位到另一处独立瓶颈：原始资料目录将已经封存、不再分配新尝试的任务与仍在处理的任务共同计入 32 个槽位。直接移动/删除完成目录会破坏已经固定的 `materials.json`、观察库、原索引、令牌及历史范围路径，因此本轮**不搬、不删、不重封存、不改引用**。

### 容量收尾第八轮：完成交接后不再被旧准备失败状态遮挡（仅本机）

状态读取保持只读、元数据级，不读取大份原件、不连新采集、不建立任务、不改失败次数/累计步数/创建时间、不追加恢复授权或发布账单。客户仍需点击生成；原提交、原件/余额/金额/令牌核验和保存边界保持原样。元数据可以显示原选择仍在，但实际原件损坏后，原提交或原 `Run` 必须拒绝，不能凭状态按钮批准金额。新代码无数据库迁移、配置开关、前端格式或计费公式变更。

### 容量收尾第九轮：未完成原件的单次有界续作（仅本机）

本轮只处理已有原始采集计划、仍缺资料且准备队列因原 24 小时或 4096 协调步数停止的任务。默认关闭，不接客户 HTTP、启动自动授权或无限重试。现有未超限任务、已完成资料交接、计费、展示和下载格式保持原路径。

授权固定绑定原组织/完整成员权限、请求月份、真实失败快照、当前待补月份、来源、采集计划、观察断点和封存容量身份。每请求终身最多一份，每接收库最多 256 份；24 小时新窗口从首次应用时固定，最多 4096 个协调步骤及 100000 次派发。成功原始观察沿用原采集计划的独立限额记账，等待也单独记账，均不擦除已发生派发。旧失败与续作失败合计仍最多三次；租约丢失、进程中断仍计入，达到任一上限即停。重复调用只确认同一份授权，不能重新排队、延长时间或清零预算。

### 自助收尾第二步之四：首次资料取得的同视图来源读取器（2026-10-30，仅本机，尚未接线）

3. 新计划可使用 `observation_store_source_id` 绑定独立封存的资金资料库。追加其他月份时不得修改旧资料文件，使已固定的摘要失效；未填写该字段保留原输入兼容方式。
4. 以正式命令检查计划、来源指纹、选择链当前头和规范化输入，再准备新私有包；不要修改已选择输入、已发布金额或其摘要。
5. 经过明确操作授权才交接资料并选择版本。客户点击生成由后台执行核验及保存，不赋予客户上传证据、指定路径或修改金额的能力。
6. 先对少量已准备的组织/月启用，确认生成、逐账号明细和下载后再扩大范围。缺少依据的历史月份需另行补证，不冒称已全量完成。

历史冷备份仅用于少量余额快照时，可由本机准备代码调用 `monthlysource.ReadRetainedSnapshotSelection`，提取原 `usage_user_snapshots` 表的固定五列。输出保留原库 SHA-256、字节数、全部原行、整数 quota 及空值，明确标记为原行投影；不生成新采样时间、月界或审核结论。原库与原始引用须留存，规范化资料改用新的投影来源 ID，并逐项核对被引用账号的余额、累计消费及原采样时间。不得静默替换旧来源身份。

提取只接受显式 `query_only` 连接、校验值一致且无 WAL/SHM/journal 的封存本机普通文件；拒绝浮点金额、重复账号、超限行数及变化中的文件，不修复或删除原文件。遗留副文件不能直接忽略：已核对留存摘要且 WAL/journal 为空的历史备份，可在本机独立目录制作校验值完全相同的封存副本后提取；运行中数据库或非空 WAL 不适用。投影文件摘要仅证明行身份，不能代替月界、覆盖完整性及正式生成验收，也不调整既有来源总量预算。

内部工具按职责分开：

- `monthlyfundingcapture`：有界只读采集、续取和观察留存。
- `monthlybillprepare`：准备与核验规范化账单输入。
- `monthlybillstage`：`init`、`plan-collection`、`prepare`、输入检查/选择及 `handoff`。
- `monthlybillimport`：明确授权的账单导入。
- `monthlybillwithdraw`：明确授权的撤回，保留审计，不删除历史。

每个命令的实际参数以相应入口的 `-h` 为准。命令、计划和输出应仅使用私有绝对路径；采集凭据、客户资料、账单及运行记录不能提交 Git，也不能进入镜像构建上下文。

令牌采集失败会输出固定的 `stage`、`class`，以及可识别时的 `reason` 原因码，不输出 SQL、凭据、令牌名称或金额。`observation_timing`/`deadline` 与 `group_totals_mismatch` 必须分开处理：前者可在原时限内重新规划更小时间片，后者须停止核对，不能当作超时跳过。错误分类不改变金额校验、五秒观察限制或每条 SQL 的两秒限制；失败仍不返回或封存部分结果。

资金和令牌采集共用四秒上限的 SSH/MySQL 连接准备，仍受各自原有命令总上限约束（令牌单次观察十秒），不放宽单条 SQL、五秒业务观察或底层连接配置限制，也不增加自动失败重试。连接准备失败标记 `stage=transport_prepare`，与真正进入业务查询后的超时区分；已封存资料续取前须重验原断点，不重新采集已完成窗口。

旧 RC4 的 `AdminClearUserBinding` 只更新明确列出的七类绑定字段，不改变额度。资金分类器仅在已核验生产者、无其他操作元数据且完整日志格式符合该源码时，将其视为非资金事件；不再让无关用户的清除绑定日志阻挡整月核验。保留原行及摘要，不把它变成零元流水；未知绑定类型、未知元数据和结构化资金操作继续按原规则核验，不按宽泛关键词忽略管理日志。

### 已留存规范化资料的兼容准备

`monthlybillstage prepare-retained` 是显式的兼容准备入口，不是原始资料出错后的自动回退。它重新核验已有规范化输入、计划、资料摘要、当前完整权限、选择链和自动保存约束，不允许用一份已渲染账单替代来源。

必须显式提供 `--expected-head`，即使首次版本的值为空也不能省略该参数。默认仅检查；`--write` 只向资料根内已有的空私有目录独占写入新包，不覆盖旧文件，不排队、不发布、不初始化业务库，也不改金额。失败留下的部分输出应保留检查，不能当作完整交接包。

新包标记为 `retained_normalized_revalidated`。旧准备程序不应消费这一新格式；未知格式应拒绝，而不是静默降级。这不影响已保存账单的读取。

## 发布、停止与回滚

发布应分别记录镜像摘要、版本、开关、挂载路径、资料摘要和一致性备份；备份需包含主库、用量事实库及独立生成资料，不只备份容器。先确认磁盘、健康检查和原有 Usage 可用，再做小范围启用；不要把启用生成与全量历史补数混为一次变更。

停止顺序：

1. 关闭生成开关，可继续查看、下载已保存账单。
2. 如需完全隐藏月度入口，再关闭页面总开关；原使用日志不依赖这两个开关。
3. 回退旧程序前停止接入新资料，等待生成任务退出并保留当前一致备份，再切换镜像。

兼容演练基线为 `v1.18.36` 的源码重建版本，不等同于对任意旧生产镜像均已验证。候选在主库仅新增 `portal_monthly_bills` 和 `portal_monthly_bill_withdrawals` 两张表，旧功能可重新打开迁移后的库。独立生成资料必须保留，新格式不得交给旧生成程序处理。

旧版没有月度入口；恢复候选后可再次读取留存账单。**不能为了回退程序直接用发布前整库覆盖当前库**，否则会丢失上线后其他功能的新增数据。恢复备份是单独的数据恢复流程，必须核对目标、时间点和增量影响。

## 验收要求

- 白盒：整数金额守恒、逐账号与逐令牌归属、重复请求、并发、损坏输入、完整性、权限版本及跨组织隔离。
- 黑盒：正式登录、生成进度、查看、下载、失败恢复、退出登录和月份切换；页面与 Excel 的金额和版本一致。
- 集成：当前生产源码构建的候选、默认关闭、生成关闭、整功能关闭、重启、旧版回退和恢复；原有 Monitor/Usage 功能不受影响。
- 安全：依赖漏洞、密钥扫描、构建上下文和提交范围检查。测试及客户资料不打包，合成身份不能代替真实发布授权。
- 真实样本：仅经授权读取或复用私有留存，独立核对组织合计及每个账号/令牌，不因一个样本通过推断所有组织历史月份均已准备完成。

本机真实资料测试必须显式提供输入；默认跳过的项目不能计为已执行。完整开发记录和客户核验报告保留在不提交的私有目录，仓库文档不记录客户余额、私有本机路径或凭据。

## 固定起点的连续月份准备模式

月度金额仍保留原始额度整数；客户展示按分计算。连续月份必须采用服务端确定的同一起点，不能由“用户先点击哪个月份”决定。当前提供显式的 `automatic-series` 模式；已有 `draft`、`automatic` 配置不会被悄悄切换，原使用日志、导出明细及其他 Monitor 模块也不依赖该模式。旧 `automatic` 模式仍是旧的单月发布路径，不应将它用于本轮连续月份上线验收。

启用时，在原有独立接收库、资料根、范围权限及自动核验配置之外，需要：

```text
MONITOR_PORTAL_MONTHLY_GENERATION_MODE=automatic-series
MONITOR_PORTAL_MONTHLY_GENERATION_DISPLAY_SERIES_INDEX=display-series.json
```

`display-series.json` 是资料根内的私有配置文件，权限为 `0600`，只能使用文件名，不能是绝对路径、子路径、隐藏文件、软链接或硬链接。其结构为 `{"version":1,"ranges":[...]}`，每项包含 `group_id`、`source_identity`、`from`、`through`；月份格式为 `YYYY-MM`，来源身份使用已核验原始资料中的规范摘要。起点来自已核验的服务端支持范围，不得从客户选择、首个完成任务或当前“恰好有数据”的月份推断。终点只允许闭合月份。每个组织最多一个范围，范围必须覆盖其显式开放的生成月份。

每个客户使用自己的固定起始月，而不是网站建站月份、Monitor 添加组织的时间、客户当前选择的月份或本机最早留存文件的月份。起点应依据开户及更早真实业务记录核验；较晚注册的客户不要求其注册前的账单资料。

客户仍只生成自己选择的月份；工作线程在后台预处理固定起点到所选月份的完整前缀，不额外创建其他月份的客户任务或发布账单。未进入发布流程的较晚月份不是早期账单的依赖；如果较晚月份已经进入发布流程（包括主库写入后尚未确认的情况），仍将校验范围扩展至该月份，并由原有主库事务重新核对全部已出账单，不降低已出账单的一致性保护。缺少必要资料时等待接入，不把缺失当成零，也不跳过缺口重新选择金额起点。

第一次核验的逐月证据和展示名称以 `display-source-<来源请求摘要>.json` 留存在同一私有资料根。文件独占锁、完整性校验、临时文件同步后原子替换用于保护重启恢复；已有缓存仍须重验原始消费、入账、钱包和令牌来源，缓存不能代替原始证据。当前整次准备的规范化输入预算为 8 MiB、独立原始文件预算为 128 MiB；逐月证据缓存单份最多 4 MiB，总计最多 256 份及 64 MiB。达到容量后停止创建新缓存，不自动删除历史锚点，已有有效缓存仍可使用。长期容量调整和归档需要单独验收。

本轮也不提高独立接收库原有的 32 份计划、64 MiB 留存预算。单组织 120 个月是计算层范围上限，不表示可以在一个接收库无限接入历史计划；扩大组织或月份范围前，必须先核对接收库、原始资料及缓存的实际占用，并验证归档后仍可恢复所需证据。

没有前序资料时不领取正式发布租约，也不消耗其重试次数。同一依赖版本的准备失败最多核验三次，随后只做轻量版本检查；新选择版本会激活新的核验预算，明确停止并重启服务也可激活准备检查。暂停不会影响已保存账单。真正进入发布后，仍使用原有持久化重试日志，并将证据、固定起点及该月展示金额绑定到同一个恢复身份；不得因重试而改变已发金额。

实际发布在原有账单事务内再次核对当前授权、已有账单、逐月证据与固定起点。历史名称沿用留存版本，当前名称变化不重新定价。旧账单不自动重写；旧证据或原锚点无法与新范围一致时停止补发，需保留资料另行核验。资料版本、缓存和已发布账单必须一并备份；不得为了释放空间直接删掉已采用的初始证据。

停止和回退仍按前述流程：先停止生成并等待退出，保留当前一致备份，再切换程序。新程序的旧发布入口会拒绝继续扩展新模式已绑定的组织；**回退到真正的旧程序时仍必须关闭自动生成**，不能将这一新保护误认为旧二进制也具备。

### 首次历史余额的同视图衔接（尚未替代历史资料）

新增的 `CaptureWalletTail` 仅采集一个账号从北京时间当月月初至同一数据库快照内可见的资金、消费及退款，并保留该快照中的注册时间、真实余额和累计消费。余额与日志在同一个只读、可重复读事务中读取；不能把读取开始的秒数当作日志上界，否则会漏掉同秒已入库的流水。原始开始、结束时间保持不变，不伪装成月界采样。

采集共用原有钱包并发通道，整个事务不超过五秒，每条 SQL 不超过两秒；只走已有的用户/时间/类型索引和时间/类型索引。资金日志按游标翻页，上限 2,000 行、正文合计 2 MiB，单页继续沿用原来的行数和字节限制。缺索引、超时、传输错误、超限均失败，不返回部分资料、不重试、不改源库；管理日志不能按操作者账号过滤，必须识别实际受影响账号。

`DeriveWalletTailBoundary` 用两次间隔至少五分钟、来源和账号一致的原始观察分别计算：月界余额 = 真实余额 − 后续资金变动 + 后续消费 − 后续退款；月界累计消费 = 当前累计消费 − 后续消费 + 后续退款。两次结果必须相同。计算全程采用精确整数，最终溢出、未知计费来源、未识别资金事件及与注册时间矛盾的记录不能产生结果；注册后才存在的账号也必须由真实流水反推出零，不能默认补零。

结果是带两份原始资料摘要的不可反序列化计算对象，**不是月末原始快照、历史完整性证明或发布授权**。尚未替代现有 `history` 配置。后续必须完成闭合月份流水衔接和自动历史准备，以及从空历史资料开始的实际自助生成验收；不能用本小节底层测试代替整项功能上线验收。

私有准备配置 `capture_wallet_tails` 默认关闭，必须已启用 `capture_registered_origins`、注册月份策略和连续月份准备。独立接收库须显式执行 `InitWalletTailCaptureStore`；正常启动只验证表和保护触发器，缺失即拒绝新路径，不自动建表、不提前连接源库。旧配置省略该字段时旧路径和原计算不变。

新路径复用现有后台队列及关停顺序：先采首份观察，继续其他资金、令牌工作，封存前补齐间隔至少五分钟的第二份观察。每步最多采一个账号的一份观察；等待只返回下次可运行时间，不占用连接或事务。每次源库操作前后重验完整组织权限，撤销后不继续封存或发布。

完整原始 JSON、摘要和任务/计划/完整账号范围/边界/序号保存在同一条不可变记录中。精确重放可复用，修改、删除及改变内容的 `REPLACE` 被拒绝。已完成组跨重启、跨月继续复用；未完成跨月组保留，可另采新月界，不移动旧时间戳。单份编码后上限 4 MiB，该类原始记录合计上限 64 MiB/12,800 条，单任务最多 12 个跨月组；不自动删除。容量、损坏或两次计算不一致均停止，不靠改消费、覆盖旧记录或反复重读绕过。

封存只复制当前任务选定的完整原始组，不复制其他任务、账号或未采用的旧组；数据进入原有 `observations.sqlite` 摘要，不放宽物理页数或整包预算。新路径采用独立封存目录身份，不原地升级旧包；读取仍重验原始资料，不能只看完成计数。原选择文件、令牌档案、旧历史余额和已保存账单的含义均不改变。

### 已核验月份的余额衔接（计算组件，未替代历史文件入口）

`ReviewCapturedWalletHistoryMonth` 从本机原始资金页、用户用量投影及完整令牌原件重建每个账号的整月记录。每个令牌原件必须与同一选择中的原始父记录及实际投影逐一对应，不能只比较月合计；缺日、未知计费来源、错账号、错版本及缺少原件不作零处理。沿用既有资金、用量和令牌核验的窗口、字节和超时限制，不读取上游或创建表。

`ReviewCapturedWalletHistoryBoundary` 重验两次同视图余额衔接原件；`DeriveWalletHistory` 要求从最早真实注册月份到该月界之前的月份连续齐备，且完整组织、授权版本、成员清单及来源一致。逐账号反推月初余额和累计消费，再顺推检查相邻月份，保留消费、退款、资金变动及逐令牌金额，不做跨账号净额抵消。重复日志端点、注册前活动（包括零价请求）、整数溢出和负的初始累计消费都会阻断。

注册月反推后仍存在的初始余额或累计消费残差会保留为内部 `OriginRequiresResolution`，不会改消费/退款来抹平，也不能据此认定已取得真实月初快照。较晚注册的成员不能在注册前获得推算余额。已有历史差异处理规则没有被改写，残差仍须经过后续相同的历史处理与准入流程。

这三个过程只产生不可反序列化的进程内核验对象；可复制的 `Report` 是内部诊断，不是账单或发布授权。身份和月份范围绑定不能替代当前权限检查、原始文件摘要和完整准入校验。衔接元数据及端点索引合计限 8 MiB，最多 120 个完整月份；没有扩大原有准备输入或原件预算。

**该组件尚未接入自动历史准备入口，`history` 依赖仍在。** 下一步须把完整月份资料的后台准备、该衔接结果和原有历史处理/账单准入接通，再做空历史资料的实际客户首次生成、查看及下载验收。不能将本节的计算通过等同于所有组织已可自助生成；客户展示、金额舍入和既有生成路径本轮均未改变。

### 原始月份资料与账单准入分离（本机衔接层）

内部 `collectCapturedSources` 复用同一套采集、等待和封存机制，但完成只表示原件已封存，不表示账单已核验。后续反推所需的其他月份只能作为数据依赖准备，不能借此新增客户账单任务、选择输入或发布账单。新封存与原先一样，须在下一步重新验证后才返回资料；权限撤销时不继续读取源库或复用封存结果。

`auditAutomaticHistorySources` 读取服务端持有、摘要固定的月份原件清单。清单只能列材料文件和原选择文件，不能传入月初/月末余额、消费合计或通过标记。它逐月以只读、不可变方式重新打开封存库，核验资金原页、用户用量投影、完整令牌原件及选定的双份余额衔接原件，然后调用前述连续月份计算。边界原件须属于清单中确切的同一份材料，不能同月换包；请求月份须另行存在于完整清单中。准备内部连续月份时，可复用同一份边界原件，不将边界所在月误认为账单月份或发布授权。

整个清单共用原有 128 MiB 原件预算，读取前按总量预检，再流式校验，不能每个月重新获得一份预算。重复路径、硬链接或符号链接、未封存的 WAL、错组织/授权/成员/来源、材料与选择不一致以及原件变动均拒绝；边界原件的注册时间还须与同一封存内的注册原件一致。失败不初始化表、不覆盖原件、不写任务或发布记录。重放仍重新核验原件，不能将上次生成的报告反序列化成通过凭据。

这一衔接层尚未安装为新的运行时入口，不改变旧配置、客户页面或既有账单计算。仍需完成原始月份依赖的后台推进、历史输入投影及准入绑定，并以不含人工 `history` 文件的实际客户按钮、查看和下载链路验收。不能把本层不依赖人工文件的读取测试称为整项自助功能已经完成。

### 原始月份依赖的队列推进（本机验收，未启用新入口）

内部 `automaticHistoryPreparation` 复用现有按需队列，不创建第二个定时器或将数据依赖创建成客户账单。范围从原始注册时间中最早的真实注册月开始，延伸到实际选定余额衔接原件的月界之前；不以客户点击的月份截断后续所需流水，也不硬编码网站搭建月份。完整旧组跨重启继续使用，不将历史原件的时间移动到当前月份。

每步至多推进一次原始源库采集或新封存。先准备各月份的首份普通观察，再穿插资金及令牌工作，避免每个月串行空等；某月等待独立第二份原件时，其余月份仍可推进。全部暂时无法推进时返回原有队列的等待时间，不占用连接或事务、不新增失败次数，也不重置原任务的寿命上限。

非请求月份使用独立的 `history-source-dependency-v1` 封存身份，只复制资金、用量、令牌及普通采集观察，不升级或覆盖旧封存。只读发现已经完成的材料引用可避免每次队列推进都重新读取整份数据库，但它不是核验通过：后续必须重新执行完整原件审计和既有账单准入。完成后保留内容寻址的资料清单，复用原有封存锁、字节预算和最多八份附加准备文件限制；不新增无限缓存或删除策略。

本机已验证较早月份需要较晚原始月份、实际只读采集进度、独立等待期间的其他月份工作、重建处理器后复用、权限撤销、坏原件不重采，以及队列拒绝将仅有资料的 `true` 当作账单已通过。金额、舍入、客户展示和旧配置均未改。

**仍不能作为新运行时入口直接启用。** 后续原始月份与 `account_token_work` 的限额兼容已按下节完成本机衔接，但必须显式绑定同一队列，不允许直接调用或静默绕过记账。还须接通历史输入投影、原件绑定及原有准入，再验收不依赖人工 `history` 的实际客户生成、查看和下载闭环。启动配置目前没有安装本协调器，旧生成路径保持不变。

### 后续原始月份的工作量记录（不是收费记账）

既有版本 1 继续用于请求月份及以前的工作，省略新增字段，保留原有 JSON 字节格式；版本 2 仅用于同一完整组织的后续原始月份。新增的私有范围包含实际注册原件 ID、来源身份、父范围摘要、注册起月和实际余额衔接边界，不包含收费金额、余额修改或发布授权。范围不能超出 120 个完整月份，也不能延伸到尚未闭合的月份。

新协调器启用工作量模式时，必须在启动前显式绑定现有队列及相同鉴权库。每次派发从真实注册、余额衔接原件重新建立进程内能力；该能力拒绝 JSON 序列化/反序列化，不能通过客户请求提供。单凭任务描述或一份可编辑范围 JSON 不能授权后续月份的采集。财务连续月份权限没有被扩大，数据准备仍不能选定或发布其他月份的账单。

只有实际新增且经原始来源核验的一份令牌观察，才计入一次工作量。原计划、基线、单来源上限及首次记录字节保持不变；跨月扩展所需数据范围也不能替换旧记录或重置原任务创建时间。4096 次协调/错误预算、24 小时任务寿命、三次失败上限、每个任务最多 120 份来源记录及全局 256 份上限均不放宽。记录丢失、来源/计划/限额变化、注册绑定丢失、旧采集库恢复及别名/未知字段输入均停止，不靠重采或重新授予预算掩盖。

原件已捕获而接收库写入失败时，保持保守：事务回滚不留下半份工作量记录；恢复后不忘记已消耗的次数，也不重复补偿额度。所有操作只影响后台任务记录及独立采集库，不改变用户收费或余额。接收库表结构不变，新增版本仅存于既有不可变记录的 JSON 中。

回退须先停止并排空生成工作、保留一致备份，再切换程序。旧/默认工作量读取策略明确拒绝版本 2；不能让旧后台处理器继续派发新模式任务。只读检查或暂停不修改已保留记录，恢复正确模式后可继续原进度。新模式当前也不与既有“预算耗尽后人工延续”流程混用：两个方向的启动绑定均拒绝组合，避免隐式续期；旧模式的延续流程继续保留。完整自助生成及运行时安装仍按前节待验收，不能将本节通过当作整项账单已可上线。

### 原始历史到既有规范化输入的本机衔接

`prepareAutomaticHistoryInput` 每次重新审计完整原件清单，再将请求月份交由既有的资金、消费、采集余额及令牌明细规范化器处理。此前与此后的完整月份保留各自原件引用和逐账号金额；请求月份不预填消费或充值，避免重复计入。整个组织始终使用同一份封存清单，不为同一个文件增加不同来源别名，不扩大既有输入大小及来源数量限制。

反推的历史起点仍标记为算术起点，不声明为历史原始余额快照；注册起点差异单独保留，不并入消费、退款或其他账号。普通余额仍是原始采集观察，不移动时间、不声明历史月界。账号名称暂不猜测，后续必须由可信目录及历史范围绑定补入。

本步骤只返回不可序列化的进程内中间结果，不选择输入、不创建客户账单或发布记录，也没有安装到主程序。仍须完成历史范围与原件的强制重放准入绑定、无人工 `history` 的运行时配置，以及真实按钮到查看、下载的空历史资料闭环验收。不得把规范化完成或金额加减闭合当作已经允许发布。

### 历史原件的强制复用校验

新模式的规范计划显式保留 `automatic_history_source_id`，并参与原有计划摘要及任务身份。旧计划省略该字段，JSON 字节与原有计算路径不变。新模式保留原件清单却删除绑定、换成其他来源 ID、取消用量/余额/令牌原件选择或伪装为旧资金模式均被拒绝；不能只改摘要后继续复用。

原有余额输入核验入口现在会对新模式重新打开每个月明确指定的封存原件，重建历史输入，并核对起点、前后月份、资金覆盖和原始资金行。不新增来源连接，不修改共享或目标月份的只读句柄。调用方处于单月句柄时，也不会将该月份的数据库当成其他月份的默认来源。请求月的消费、资金、余额观察与令牌核验仍保留，不由历史汇总替代。

相等增减额、相等消费退款或额外“历史余额快照”即使维持余额加减闭合，也不能替换原件。任务执行、正式准备检查和自动交接复用同一入口；已有内部 ready 标记不跳过原件核验。只有原件规范化、没有独立历史范围的计划，仍不能通过账单发布校验。

该变更没有安装新的运行时入口或修改接收库结构。历史范围的来源绑定、无人工 `history` 的启动模式以及实际客户自助生成闭环仍待接通，不能把本节通过称为整项功能已经可上线。旧版读取器不认识新绑定时，其既有规范计划字节比较会拒绝该记录；回退仍须先停止生成工作，不能期待旧处理器继续处理新模式记录。

### 组织账号目录与真实余额观察衔接

`LoadMonthlyGenerationDirectory` 在单个本机只读授权视图中取得完整成员范围、组织名称和账号名称。目录只保存这些显示资料及既有范围版本，不带邮箱、备注、密码、余额或消费。名字相同不合并账号，始终按用户 ID 关联；名字缺失时不猜测。目录内容相同则字节相同，改名产生新目录内容，不重写旧快照。当前目录不是历史钱包证明。

`prepareAutomaticHistoryContextInput` 在原件规范化前后分别读取目录；账号范围、授权版本或名称发生变化，整次准备返回错误，不返回部分组织。既有原件必须通过原来的完整核验；不读取线上、初始化目录表或保存账单。

余额衔接中间结果保留实际采集毫秒时间、两份原件摘要、逐账号消费/退款和资金行，包含采集同一秒已经可见的入账。请求月份之后的完整月份也进入衔接，不将后续消费漏掉或把同秒流水截掉；金额使用整数及大整数校验，不跨账号抵消。注册起点差异仍明确保留，不隐藏、不变成消费。

该结果不可通过 JSON 声明为已核验历史范围，不是 `AutomaticScope`、客户账单或发布许可，也没有安装到运行时。后续须将同视图原件衔接接入正式历史范围与发布校验，再完成无人工历史文件的客户生成、保存、查看及下载验收；本步骤不把采集时间或计算结果伪装成历史月末原始快照。

### 同视图原件到现有制单计算器

`prepareAutomaticHistoryCandidate` 从留存原件重新建立历史证明，核对规范化输入，再读取与只读目录快照字节一致的私有目录文件。账号名称按 ID 关联，完整月份的资金与原件视图中的尾部资金分开传递，不把尾部可见数据写成覆盖整秒的准备区间。记录实际采集毫秒和两份原件摘要，采集同秒已经可见的入账不被截掉；尾部资金也不会算作此前账期充值。

此步骤已能在本机从原件进入现有候选账单计算和金额发布策略，但不写账单、不选择运行输入，也没有安装新模式。下一步仍须完成留存历史范围的复用/发布绑定、无人工历史文件的运行时入口，以及真实客户按钮、保存、查看、下载验收；不能将内存候选账单当作已发布账单。

### 同视图历史范围的留存、复用及保存核验

原件派生模式的目录与历史范围可进入既有准备、运行、交接和金额发布路径。目录仅补充显示名称；历史范围必须与重新核验原件后推导出的完整结构逐字段一致，不能靠自己文件的摘要证明自己的金额。正常规范化输入只临时剥离精确选定的目录/范围元数据，再与原件重建结果比较，不修改留存资料。账号名称按完整成员 ID 核对，授权范围改变则仍由原来的实时权限与选择版本校验拒绝。

原件核验后产生的进程内证明绑定精确计划、输入和上下文；JSON 序列化/反序列化不保留证明。自动交接重新读取固定范围并核验原件，拒绝调用方替换上下文。原件模式即使已存在内部完成标记，也必须重建历史范围核验；不能退回普通余额锚点绕过。旧模式没有增加原件读取，也不改变旧账单数据格式或保存金额。

读取取消或超时保留原错误类型，不额外标为金额依据不合格，避免临时读取失败变成永久核验失败。重复的目录/范围来源须在剥离元数据前拒绝，不能靠清理重复项使含糊输入通过。

本机合成测试覆盖正式只读检查、临时接收库选择、真实 Usage 生成接口、后台保存、查看及三页工作簿下载。重启不重复保存，已经保存的账单在生成资料不再可用时仍能查看下载。这个阶段的测试使用原件派生范围，但当时依赖测试主动完成正式准备，不能将其称为无人工历史文件的自助准备验收。后续显式运行时模式见下一节；非零历史起点差异的既有处理规则仍需单独接通，不能据此宣称整项功能已经可上线。

### 显式启用原件派生的自助准备模式

私有采集配置可显式设置 `derive_history_from_originals: true`。此模式使用客户真实注册范围和原始采集资料自动准备核算输入，不读取人工 `history` 或 `scope_catalogue`；这两个引用须为空，且不能同时开启 `assemble_retained_history`。必须使用已注册客户策略和动态月份范围，并开启 `capture_registered_origins`、`capture_wallet_tails`、`partition_usage`、`retain_completed_seals`、`account_token_work`。配置不满足条件时，在连接上游之前拒绝安装。默认关闭，旧配置省略新字段，格式与旧路径不变。

客户仍只选择已结束月份并点击生成。原件采集在注册月份前缀准备的外层执行，同一个实际采集视图供全部必要月份核验，且保留原客户请求的工作额度及断点。每个依赖月份的目录和派生范围存入它自己的原件封存目录，沿用现有八个元数据版本及全局容量限制；不把全部历史月份的文件堆在一个月份下，也不提高任何容量、SQL、工作、重试或生命周期预算。历史依赖只准备内部输入，不额外生成或发布客户账单。

每次采集前先检查整个所需前缀的选择状态，已撤销、冲突的月份不能触发重新采集或被自动替换。正式选择继续复用完整原件、当前授权和 CAS 校验；中断后内容相同的私有文件可复用，已有账单仍按原样保存、查看和下载。启动保持懒连接，不开第二套工作器，不初始化来源库或修改上游数据。

此模式不替代非零历史起点差异的既有金额核验规则；尚未接通的差异仍明确拒绝，不会为了通过生成而改写日志消费或伪造期初。启用需要单独准备配置和本机验收，不因代码存在自动影响线上。回退前停止生成工作并恢复原配置；旧读取器会拒绝带新字段的配置，不能仅清掉开关却继续使用缺少历史引用的旧模式。已保存客户账单的格式没有因此变更。

### 历史小额差异的原件诊断边界

`ReviewWalletHistoryOriginResidual` 与正式 `DeriveWalletHistory` 分开。原始采集的累计用量仍不允许为负；仅在诊断还原中，允许逐账号明确保留“起点余额为正、起点累计用量为同额负值”的算术差异，且仍核对完整月链、正反计算、注册前零活动与原件一致性。负的算术起点不是负的原始余额观察，也不是已核验的历史期初，不能归零或混入消费。正式来源核验、输入规范化和发布入口仍使用严格路径。

`reviewAutomaticOrigins` 从留存原件重新核验后逐账号分类。它复用最终金额校验的绝对上限和万分之一比例上限，区分无差异、现有规则范围内的待处理差异、超限及不互为相反数的差异；不跨账号抵消。逐个闭合账期列出满足金额门槛的确认账期候选，不将注册月份、候选账期或客户所选月份猜作差异实际发生时间。注册月份消费尚未闭合时不推算、不据此放宽限制。诊断结果不能序列化为核验能力，不创建核算范围、任务或账单，也不代替业务处理决定。

此步骤尚未开放自动金额处理。还需将符合条件的差异与既有确认账期、同视图原件及一次性承接规则接通，尤其要保证较晚注册成员在注册前账期保持零账目，不把不明发生时间的差异随意归入某个月。其他方向、超过现有上限、缺失或变化中的原件仍拒绝处理。

### 已接受的小额历史差异与客户按需生成衔接（本机候选）

本节更新前述诊断阶段的状态：仅在显式启用 `derive_history_from_originals` 的新路径中，将此前已接受的历史小额处理规则接到实际生成链路；不是扩大差异限额，也不是把差异确认月份当成丢失日志的发生月份。旧模式及没有差异的原件模式继续使用原来的严格处理，不增加金额校正。

每个账号须独立满足：完整原件反推的起点余额为正、累计用量差额为同额负数，且不超过 5 元及所选闭合确认月份净日志消费的万分之一。确认账期选取真实注册月起第一个满足既有门槛的闭合月份，作为已接受差额的业务处理期间；不知道差异原因时不声明已证明原因。全组任何账号不满足条件即停止本次准备，不能跨账号抵消或修改消费、退款、充值日志。原始余额与累计用量观察仍完整保留。

规则文件只有固定政策，不接受金额或通过标记。计划新增可选 `automatic_history_policy_source_id`，与原件、规范化输入、原生核验能力及精确派生范围共同绑定；后续每次准入与复用均从原件重新核验。修改规则并重新计算摘要、删除计划绑定或篡改规范化余额/消费均不能代替原件核验。留存文件仍使用各月份原有的八份元数据上限，不扩大查询、容量、重试或任务寿命。

确认账期之前不计入这笔业务余额校正；确认账期计入一次，后续月份仅在期初承接，不再次计入。晚注册成员在注册前仍为零账目。逻辑账簿起点和实际余额观察严格区分，不制造月界快照、不改写原始累计用量；同视图衔接另外传递经原件核验的尾部消费和退款，不能把半月尾部误认为完整历史区间。已保存的客户账单继续沿用既有不可变格式和重复校正校验。

回退仍须先停止并排空生成工作、保留一致性备份，再恢复旧程序和旧配置；旧处理器不支持带新政策绑定的待处理计划，不能直接接管。已保存账单的证据版本与历史处理结构不变，不需要重写客户账单或来源数据库。当前只做本机验证，没有启用线上配置；功能级上线结论还须覆盖当前候选的回归、隔离容器、留存真实数据及页面验收。

### 新增账单表的发布恢复点与真实大数据量门槛

月度账单与撤回表加入主库 `AutoMigrate`，即使功能开关关闭也会创建。因此基础与 source-v2 两种迁移计划均提升到 v60，不能复用 v59 较早的恢复点。双库备份必须包含升级前最新已提交 WAL，成功校验后才允许创建新表；备份失败不迁移。相同版本重启复用本次固定恢复点，而不是每次重复备份。

本机已覆盖 v59→v60 的两种迁移分支、备份失败、双库恢复和重启，并使用独立的留存数据副本运行新版→当前 main 基线→新版程序切换。基线程序不提供新增月度账单入口，但原有 Usage 页面仍可登录；再次运行候选版后，已保存账单的客户数据与下载文件保持原样。此演练不代表线上发布停机时间或大库备份耗时已经验证。

真实数据补采发现：当前月整月尾部查询在大数据量账户上触发 MySQL 两秒执行时限。采集已停止，部分原件不作为完整依据发布；没有自动重试或通过加长超时绕过。索引和执行计划另行只读核验，不重跑失败的聚合。`WalletTailFailureStage` 只提供固定阶段名称，保留超时/驱动错误分类，不暴露 SQL、凭证或原始记录内容。

**当前仍不能据此判定整项功能可上线。** 须先解决整月尾部读取的有界性与真实数据量性能，保持原件范围、金额口径和读取一致性，不能只加缓存就宣称缓存数据属于当前读取视图。修复后复用已留存的注册原件与核验资料，补做真实客户按需生成及页面验收；不扩大业务功能，也不放宽两秒 SQL、五秒观察或已有任务限额。

### 整月尾部超时：第一步只增加有界读取原语

`CaptureWalletTailPage` 尚未接入运行任务或制单入口。每次只在同一个只读、可重复读视图内读取来源标识、真实注册/钱包和有限索引页，再对该页选中的主键读取金额；不对整月先聚合后限行。索引游标遵循现有索引的时间、类型、主键顺序，每页最多 8,192 个索引元数据，管理/充值正文最多 200 条。续页的互斥范围各自先限行，再合并排序；正文通过 MySQL 8 `JSON_TABLE` 小型键表驱动主键单行查找，避免大 `IN` 列表触发全量扫描。缺索引或不支持该语法直接失败，不自动回退到原先的整月大查询。

全局资金发现保留有限候选键，供后续发现流程复用，不代表其他账号的资金。管理记录保留真实操作人，充值记录按目标账号隔离，其他账号只返回存在性标记、不读取其充值正文。每个选中主键必须有对应结果；金额仍为整数计费单位，退款与消费分开，不跨账号抵消。SQL 两秒、整次观察五秒、字节和并发限制不提高；取消、超时、缺项和提交失败均不返回部分成功结果。

`view_end_reached` 仅表示这一次读取视图的索引已结束，**不是整月完整性或金额核验通过**；索引摘要也不构成金额依据。页结果不能传给既有完整尾部推导器生成月界余额。跨页属于不同读取视图，仍须完成可恢复的留存/容量核算、迟到或回补日志处理、月切换及最终钱包与尾部的一致性衔接，才能安装到按需生成流程。不能把缓存页改名为同视图完整原件，也不能因分页单测通过就认定真实客户账单已验收。

### 分段读取的私有断点留存

`InitWalletTailPageJournal` 与 `CaptureNextWalletTailPage` 只提供显式私有接收库的单步采集接口，尚未由启动、客户 HTTP 或生成任务调用。每一步仍共享原钱包采集通道、限速和两秒 SQL / 五秒来源视图；本地读写各限两秒，不启动新工作器、不自动重试。任务、原计划、权限/成员范围、账号、数据来源、日志类别及独立遍历序号共同绑定断点。第零遍未结束，或结束未满五分钟，不能开始第一遍。

一个不可变行同时提交原始页、摘要、前一页标识、序号与游标。SQLite 写锁内重新核对断点后才追加，过期写入者不能覆盖或多推进一页；查询或落盘失败不返回成功进度。重启只读取固定计划和有限首尾页来恢复游标，不在每次续跑时重扫所有已保存正文；这不是完整原件的金额复审。首尾账号注册依据变化、页链缺项、摘要/正文损坏、跨月或单条遍历超过二十四小时均停止，不换新标识掩盖旧断点。已经完成且仍在有效范围内的遍历可在来源离线时只读复用。

日志迟到场景已明确区分：后补的日志可能时间早、ID 大，仍落在旧时间游标之前。旧遍历的续页不能声称已经包含它；独立遍历从起点读取，结果另存，不与前一遍重复相加。管理日志保留真实操作人，其他账号的充值正文不进入当前账号留存页；有限候选键只是发现元数据，不是资金归属。

页表自身以四千零九十六条 / 六十四 MiB 为硬上限，满额在访问来源之前停止，事务内再校验。本接口**尚未纳入现有整批一百二十八 MiB / 四千零九十六工作额度及封存清理流程**，这个局部上限不能被当作额外总额度；这些接线与完整原件复审完成前，不允许将它安装到客户生成流程。`traversed` 只表示一遍游标遍历结束，不包含完整性、金额通过或发布权限。当前收费公式、已保存账单和既有正式尾部读取入口均未改动。

### 留存页完整复审与未变化历史段

`ReviewWalletTailPagePrefix` 只读取已初始化的私有 SQLite 接收库，不连接来源、不写数据库、不创建任务。断点恢复读取首尾页是为了续跑效率；金额准备前的本接口会在一个本地只读事务内，逐页复查全部序号、前页引用、正文摘要、规范化原件、游标衔接、真实注册依据及物理采集时间。中间页损坏、提前结束、缺项、重复资金候选或重新计算摘要后仍不连贯的原件不能通过。完整复审保留紧凑页指纹和整数金额，不同时保留两遍完整资金正文；沿用页表的总条数/字节上限，本地复审限五秒。

两遍原始遍历必须完整，且后一遍开始距前一遍结束至少五分钟。逐页比较真实索引元数据和日志内容，钱包余额与采集时间的正常变化不算历史段变化。前一遍的末页始终作为仍需读取的尾部，不因两遍内容恰好一致就变成已闭合历史段。遇到回补旧时间日志、删除、消费/退款类别变化、计费来源变化或金额改变，只保留变化位置之前已核对的段；变化位置及后续不能继续复用。两遍金额不相加、不取平均，也不跨账号抵消。

核对段的消费、退款分别保留原始整数额度，管理操作保留真实操作人、按受益账号计算；其他账号的充值不混入。沿用既有 RC4/RC26 资金解析规则；未知计费来源、无法解析的相关入账不视为零。正负资金及多页汇总使用任意精度整数，输出前检查 `int64` 边界，避免浮点舍入和中间累加溢出。所有客户可见的金额格式与已有账单保持不变。

复审对象绑定原任务、计划和完整账号/权限范围。诊断报告可复制，但不能反序列化为来源核验能力，也没有月初/月末余额或发布标记。已经完成的原始遍历可在之后月份本地复审，仍保留其原采集月份和时间，不重命名为当前观察。

**未变化历史段仍不是当前来源快照。** 本步骤不能证明复审之后来源未再补写或改动，更不能直接把跨次读取拼装成旧的同视图尾部原件。尚须实现来源端的当前覆盖核验、同视图实时尾部与最终钱包的衔接，再纳入既有工作/容量、封存和按需生成流程；本接口目前没有运行时调用，不能据此宣布客户自动准备或整项上线验收通过。

### 同一来源视图的分段完整读取：正确性基线与性能门槛

`CaptureWalletTailPaged` 是显式的完整视图正确性基线，尚未接入生成任务。它只开始一次来源只读、可重复读事务，只读取一次来源标识和钱包，在该事务内完成全部分段消费、退款和资金读取。复用的页读取函数不创建事务、不重新取钱包、不重置时限；旧的单页采集入口仍使用原来的独立事务边界。这里不使用历史缓存的金额冒充当前快照，因此只有真正读全当前视图，才返回既有 `WalletTailObservation` 格式，不需要修改金额推导或发布门禁。

分段消费按原计费来源和日志类别分别合并，保留记录数、最小/最大 ID、时间、金额范围及整数总额。资金读取的索引顺序为时间、类型、ID，返回旧格式前恢复时间、ID 顺序，保留操作人并检查重复记录。任意精度整数用于累加，最终各类总额单独检查 `int64`，不以退款抵消消费溢出。仍使用原来的整次五秒、单 SQL 两秒、资金两千条/二 MiB 以及完整原件四 MiB 限制；每页预算不是提高整次预算的理由。读取或提交失败不返回部分完整视图。

本机覆盖新旧完整原件逐字段一致、补写旧时间日志在新视图中纳入、并发写入/余额变动不混合进已建立的视图，以及沿用既有两次独立观察的金额门禁。实际 MySQL 引擎验证了 SELECT-only 权限与这些行为；没有修改旧账单或消费计费公式。

**大数据量性能仍未达标，禁止因此启用运行时。** 断网、二 CPU/二 GiB 容器中，以三百六十五万六千八百五十条合成日志、其中目标账号一百四十八万二千二百九十六条进行同量级特征测量；日志只含最小计费元数据，不能等同于线上真实正文大小。目标消费读取启动一百八十一次索引页和一百八十一次主键聚合后，进入全局索引阶段；总计约五千零四毫秒触发五秒限制。没有返回部分结果，复测时连接已回收。该次性能门槛结果为失败，不能用小数据量通过或测试总数代替。

下一步须降低全局非资金索引的数据传输和分段查询往返，将过滤与有界聚合留在数据库内执行，并保持同一视图、金额口径及现有时限。初次特征脚本只在保护异常后退出、未留下耗时/连接数，不能据此断言存在连接泄漏；后续记录补齐了查询类别和有界回收观察，没有调整业务超时。所有测量仅使用本机合成数据，未读取或修改线上。

### 资金侧筛选优化：首个瓶颈修复，较大元数据仍待优化

完整视图基线的资金侧改为数据库内筛选：全局只取类型 3，保留全部操作人；类型 1、4 只取目标账号。继续使用已经核对的现有索引，不增加来源索引或修改 schema。第一页拆成三个互斥类型分支，续页再拆成“同秒较大 ID”和“后续时间”两个互斥范围，不使用大范围 `OR` 或 `OFFSET`。每个分支先限 201 个候选，合并后再限 201，最后通过主键读取正文；先按时间、ID 合并，不按类型推进资金游标，避免同秒不同类型相互跳过。覆盖索引筛选仍可能检查多于 201 个索引项，整条语句的两秒限制不变，不能把候选限行误称为扫描量恒定。

本机覆盖同秒多页、不同类型交错、大量其他账号充值、错误游标、整次行数/字节预算及新旧完整原件一致。实际 MySQL 验证首次/续页的分支没有整月 filesort，正文使用 `PRIMARY eq_ref` 单行查找；外层有限候选排序不算整月排序。旧的完整采集入口、单页留存格式、充值解析与账单金额公式未变，新优化仍未接入生成任务。

同样的二 CPU/二 GiB、3,656,850 条合成日志（目标账号 1,482,296 条）下，最小计费元数据样本首次完整读取成功，约 4,620 毫秒，记录数及整数总额与生成依据一致；全局资金读取只需一次查询，不再向程序传送无关消费索引。此结果只有约 380 毫秒余量，不能作为真实环境已充分达标的结论。

再将目标日志每条增加 128 字节合成元数据后，消费读取阶段约 5,002 毫秒触发总时限，消费主键聚合启动至第 151 次查询，未到资金阶段。没有输出部分金额；取消返回瞬间观察到的一个在用连接在约 11 毫秒后释放，没有持续占用。**较大元数据压力门槛仍为失败，整体禁止启用运行时。** 下一步只针对消费侧减少主键往返，将有界分段聚合与游标信息直接在来源数据库内完成；仍须保留一视图、原口径和既有时限，不能以过滤异常或扩大超时掩盖问题。

### 消费侧数据库内分段汇总

实验性完整读取器现在通过 `serverTailUsageQuery` 将消费类型 2、6 的分段主键、有界汇总、记录数和末游标放在同一条 SQL 中返回。`usage_keys` 每段最多 8,192 条；续页的三个互斥范围各自先限行，合并后再次限行。`usage_totals` 只对这些主键通过 `PRIMARY` 单行连接读取，沿用原来的 `usageBillingSourceSQL` 表达式及整数金额解析，不增加新的计费来源解释。主键不再整段传回应用程序并重新编码发往来源库。没有修改来源索引、消费计费公式、已保存账单或旧的完整读取入口。

返回的是元数据与最多十个分类汇总，不是任意截取的日志。每行的元数据必须一致，非空段汇总记录数之和须与主键数相等；缺失连接、NULL 金额、NULL 计数、非整数或溢出金额、重复分组、异账号及不一致游标均失败。空段用一条明确的全零汇总承载元数据，不允许借空段隐藏金额。恰好满段时不假定结束，必须再读取后续段；该额外确认仍计入原工作预算。所有读取仍在原来那一次只读、可重复读事务内，总时限五秒、单 SQL 两秒，不从历史缓存冒充当前完整原件。

本机 85 项相关竞态回归、断网容器 85 项来源回归及三项实际 MySQL 验收通过。实际引擎覆盖新旧完整结果逐字段一致、五类计费来源、真实 NULL 额度、同秒多页、并发原子更新和旧时间补写；查询计划验证聚合正文使用 `PRIMARY eq_ref`，没有把先限行的主键段改为整月聚合。静态检查通过；全库编译检查不等于全部业务功能回归。

二 CPU/二 GiB 合成样本仍为 3,656,850 条总日志、目标账号 1,482,296 条。简单元数据样本约 2,732 毫秒完成；目标日志增加一个长度 128 字节的合成字段值（另有字段名和 JSON 开销）后，首次约 4,650 毫秒完成，三次独立事务连续读取约为 4,545 / 4,541 / 4,608 毫秒。每次均核对整数总额与记录数，连接回收正常；消费逻辑查询从每段两次减少为一次，本样本共 181 次分段汇总及一次资金读取。测试生成的时间分布按当月已过去时间限定，本轮约 39,000 秒，与此前十月的较长分布不同，不能据此计算严格的前后提速倍数。

**本机指定样本的性能门槛已通过，但不等于整项可上线。** 较大元数据样本仍只有约 0.35—0.45 秒余量，未证明任意 JSON 大小、现场网络延迟或所有客户都达标。新读取器尚无生成任务调用；仍须接入既有任务、权限/容量与留存流程，并验证真实客户的按需生成、保存、查看、下载及回退。未执行线上读取、数据变更或部署，也不因本机测量通过自动启用运行时。

### 成功原件工作指纹与分片计划隔离

真实只读恢复验收发现一个可在本机复现的组合缺陷：任务已有成功观察和工作计数后，聚合超时触发了既有的受控分片，但新计划尚无任何子观察。工作检查点把这个空计划也编码进原件指纹，导致“成功观察数量未变、指纹却变了”，下一个步骤被完整性保护拒绝。它会阻断生成；不能通过重置计数、删除原件或放宽金额检查处理。

修复仅在 `ReadTokenWorkCheckpoint` 的指纹编码中排除没有成功观察引用的恢复计划。恢复清单仍先执行原有完整性、范围、字节和预算校验；无原件不等于不检查计划。已有真实观察引用的编码、成功数量、最大工作量、任务年龄和源端时限不变。分片规划由原协调器步骤预算记录，不取得成功观察信用；`recordTokenWork` 的递增保护未改，真正读回一个已确认无消费的视图仍是一份成功原件，不会因金额为零而被忽略。

新增回归覆盖“先成功采集、再超时分片、再采集子原件”的真实队列顺序，而不是仅从空任务开始；同时检查空计划的非法内容仍被拒绝、无观察增量不能申请成功信用、子原件只计一次、不重置任务年龄或批准账单。先复现失败，再实施最小修复。本机留存的 19 个真实原件和原工作计数无需改写，修复后只读校验通过；19 个时间窗的用户及令牌金额、记录数也逐一与已核验历史资料对齐，其中一个整日窗口与历史的两个半日窗口按整数审计汇总比较，没有伪造同视图原件或发布权限。

### 两位分位分配：规则验证阶段，尚未接入客户功能
