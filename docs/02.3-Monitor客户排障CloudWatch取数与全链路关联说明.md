# Monitor 客户排障 CloudWatch 取数与全链路关联说明

## 1. 文档目的

本文说明 Monitor 的“客户排障”功能应如何从 CloudWatch 获取数据，并与现有 NewAPI 只读业务日志组合成一条可解释的请求链路。

本文面向 Monitor 研发、测试和运维人员，重点回答以下问题：

1. Monitor 应读取哪些 CloudWatch 日志组；
2. 每组日志能说明什么、不能说明什么；
3. 用户只提供时间、用户 ID、模型、分组或 Request ID 中部分信息时，如何逐步定位请求；
4. CloudFront、Nginx、NewAPI 和 RDS 证据如何关联；
5. 如何区分事实、相关性推断和证据缺失；
6. 如何控制 AWS 权限、查询费用、查询并发和敏感数据；
7. 现有采集器如何平滑退出，避免 ECS 自动扩缩容后继续依赖逐任务维护。

本文只规定 Monitor 的读取和展示方案：

- 不修改 NewAPI 代码；
- 不修改 NewAPI 数据库结构；
- 不向 NewAPI 生产数据库写数据；
- 不进入客户同步请求链路；
- 不自动调整渠道、权重、优先级或启停状态；
- 不在本文实施阶段移除现有采集器和日志桥。

## 2. 结论先行

Monitor 的客户排障不能只查 CloudWatch，也不能只查 NewAPI `logs` 表，正确方式是两者组合：

```text
NewAPI 只读业务日志
  └─负责回答：谁、什么模型、什么分组、走了哪个渠道、怎么计费、应用记录了什么错误

CloudWatch Logs
  ├─CloudFront：请求有没有到达网站边缘、边缘返回什么、客户网络特征如何
  ├─Nginx：请求有没有到达 Worker、入口状态、总耗时、上游连接耗时、是否由客户端断开
  ├─NewAPI stdout/stderr：应用在路由前、路由中和运行时发生了什么
  ├─Master：后台任务、渠道测试、订阅重置、邮件等是否异常
  └─RDS：数据库是否同时出现连接、IO、重启或慢查询问题
```

客户排障的主查询入口仍然复用现有 `logchain`。CloudWatch 是它的证据增强层，不另做一套互相割裂的排障页面。

目标架构是：

```text
浏览器
  ↓ 只提交排障条件，不获得 AWS 凭证
Monitor 后端
  ├─读取 NewAPI 生产只读库
  ├─读取 Monitor 自己的渠道快照
  ├─调用 us-east-1 CloudWatch Logs
  ├─调用 us-west-2 CloudWatch Logs
  └─在本地完成关联、归因、脱敏和证据分级
```

对于 ECS、RDS、ALB、CloudFront 等非 Lightsail 服务，CloudWatch 应成为 Monitor 的唯一云端日志来源。Monitor 不应枚举每个短命 ECS Task，也不应要求每次自动扩容后人工注册采集器。

## 3. 当前能力与目标能力

### 3.1 当前客户排障功能

当前代码已经存在“客户排障（logchain）”页面和接口：

```text
GET /logchain/requests
GET /logchain/filters
```

当前主要数据来源为：

- NewAPI 生产数据库 `logs` 表；
- Monitor 本地 `channel_snaps` 渠道快照；
- Monitor 本地 Nginx 短期证据库；
- 已采集的上游错误日志。

当前 `LogChainRow` 已经可以展示：

- 用户 ID、用户名、令牌名称；
- 分组、模型、模型重定向后的上游模型；
- 渠道 ID、渠道名称、供应商、上游域名；
- NewAPI Request ID；
- 输入、输出、缓存 Token、费用；
- 是否流式、总耗时、首字节耗时；
- 上游状态码、错误类型、错误码和错误原文；
- 流结束原因、客户端断开、计费异常；
- 当前归因及其置信度。

现有功能的主要不足是：

1. 客户请求未进入 NewAPI `logs` 表时，按用户查询可能完全没有记录；
2. 入口证据依赖节点侧采集器和日志桥，ECS Task 变化后维护链路较复杂；
3. CloudFront、WAF、Nginx、NewAPI 和 RDS 证据尚未在同一排障结果中统一展示；
4. CloudFront Request ID 与 NewAPI Request ID 尚未统一传播，不能直接假设二者相同；
5. CloudFront 标准访问日志存在投递延迟，不能把“暂时查不到”解释成“请求没有到达”。

### 3.2 目标能力

目标不是把所有 CloudWatch 原始日志复制进 Monitor，而是实现两类读取：

| 类型 | 使用方式 | 目的 |
|---|---|---|
| 按需排障查询 | 用户发起排障时，查询窄时间窗和固定日志组 | 补齐某一次或一组候选请求的链路证据 |
| 后台异常采集 | 按固定周期和水位读取经过筛选的异常 | 稳定性统计、Incident、数据源健康和盲区监控 |

两类读取共用 CloudWatch 客户端、解析器、脱敏规则和数据源健康状态，但查询调度、保留策略和费用控制必须分开。

## 4. 当前生产请求链路

```text
客户客户端
  ↓
客户本地网络 / VPN / 代理 / 运营商网络
  ↓
CloudFront（全球边缘）
  ↓
WAF / CloudFront Function
  ↓
ALB（us-west-2）
  ↓
ECS Fargate Worker × N
  ↓
Nginx
  ↓
NewAPI
  ├─读取/写入 RDS MySQL
  └─访问上游模型渠道

ECS Fargate Master × 1
  └─定时任务、渠道测试、订阅重置、邮件等后台任务
```

客户请求正常情况下不经过 Master。只有排查渠道自动测试、后台任务、订阅重置、邮件或 Master 自身异常时，才查询 Master 日志。

## 5. CloudWatch 数据源清单

### 5.1 `us-east-1`：CloudFront 入口日志

| 日志组 | 保留期 | 用途 | 访问级别 |
|---|---:|---|---|
| `nexusapi-cloudfront-access` | 30 天 | 日常入口请求、状态、路径、延迟和边缘结果 | 普通排障 |
| `nexusapi-cloudfront-client-diagnostic` | 14 天 | 客户 IP、User-Agent、ASN、国家、TLS 等网络诊断 | 敏感排障 |

两个日志组均来自 CloudFront Distribution：

```text
E25FZDB19ACOZ2
```

当前覆盖域名：

```text
nexusapi.link
us.nexusapi.link
```

不覆盖：

```text
pathgo.link
verify.pathgo.link
```

如果客户访问的是不在覆盖范围内的域名，不能用上述两组日志得出“请求没有到达”的结论。

核心日志当前包含 26 个字段，主要包括：

```text
timestamp(ms)
date
time
distributionid
x-edge-request-id
x-edge-location
cs-method
cs(Host)
x-host-header
cs-uri-stem
sc-status
x-edge-result-type
x-edge-response-result-type
x-edge-detailed-result-type
cs-protocol
cs-protocol-version
cs-bytes
sc-bytes
time-taken
time-to-first-byte
origin-fbl
origin-lbl
sc-content-type
sc-content-len
cache-behavior-path-pattern
ssl-protocol
```

诊断日志在上述字段基础上增加：

```text
c-ip
c-port
x-forwarded-for
cs(User-Agent)
asn
c-country
ssl-cipher
connection-id
```

两组日志均不采集：

- Authorization；
- API Key 或完整 Token；
- Cookie；
- URL query；
- Referer；
- 请求体；
- 响应体；
- 提示词、模型响应或工具参数。

因此 CloudFront 日志不能直接回答用户 ID、模型、分组、渠道和上游错误内容。

### 5.2 `us-west-2`：Worker 日志

生产 Worker 日志组：

```text
/ecs/nexusapi-prod-worker
```

Monitor 查询日志组内所有任务日志流，不按固定 Task ID 配置。日志流后面的长串 ID 是 ECS Task ID，任务滚动更新或自动扩缩容后会变化。

主要日志流前缀：

| 前缀 | 内容 | 是否为目标架构直接来源 |
|---|---|---|
| `nginx/` | Nginx access/error 输出 | 是 |
| `new-api/` | NewAPI stdout/stderr | 是 |
| `nginxcollector/` | 现有 Nginx 采集器自身日志 | 仅迁移期检查 |
| `reject-collector/` | 现有前置拒绝采集器自身日志 | 仅迁移期检查 |

Nginx 结构化访问日志应至少提供：

```text
msec
request_method
uri
status
request_time
upstream_status
upstream_response_time
upstream_connect_time
upstream_header_time
bytes_sent
nginx_request_id
oneapi_request_id
request_completion
```

这组数据主要回答：

- 请求是否到达 Worker；
- 请求落在哪个 ECS Task；
- Nginx 最终状态码；
- 是否连接到 NewAPI；
- 总耗时、连接耗时、响应头耗时和上游耗时；
- 客户是否提前断开；
- 是否存在多个 upstream attempt；
- NewAPI Request ID 是否被 Nginx 观察到。

`new-api/` 主要回答：

- 请求进入应用后的鉴权、参数、分组和路由问题；
- `No available channel` 等未进入业务 `logs` 表的前置拒绝；
- 上游 401、404、408、429、5xx；
- 数据库错误；
- panic、fatal、超时和其他运行时错误。

### 5.3 `us-west-2`：Master 日志

```text
/ecs/nexusapi-prod-master
```

用于：

- 定时任务异常；
- 渠道自动测试；
- 订阅重置；
- 邮件发送；
- 后台数据刷新；
- Master 启动、退出和任务重叠风险。

普通客户 API 请求排障默认不查 Master，避免噪声和不必要扫描。

### 5.4 `us-west-2`：RDS 日志

```text
/aws/rds/instance/nexusapi-mysql-prod/error
/aws/rds/instance/nexusapi-mysql-prod/slowquery
```

RDS 日志只在以下情况下补查：

- 同时段多个模型、多个渠道、多个客户异常；
- NewAPI 出现数据库连接、事务或超时错误；
- Monitor 发现查询耗时异常；
- Dashboard 显示连接数、CPU、内存、磁盘队列或 IO 同时异常；
- 客户控制台日志查询明显变慢。

RDS 日志不能直接通过用户 ID 定位客户请求，属于时间窗和故障类型证据。

### 5.5 迁移期日志组

```text
/aws/lambda/nexusapi-monitor-ecs-log-production-bridge
```

这是现有 ECS 日志注册/桥接链路自己的运行日志，不是客户请求权威日志。目标架构下 Monitor 直接读取 CloudWatch 后，它只用于迁移期验证和故障排查。

```text
/ecs/nexusapi-prod-worker-buffer-canary
/ecs/nexusapi-buffer-lab-6cm1iv
```

这两组为历史缓冲实验日志，不得纳入生产客户排障默认查询。

## 6. 客户排障输入要求

### 6.1 最少信息

客户提供的信息可能不完整，但至少必须有：

- 一个明确时间范围；
- 时区；
- 用户、请求 ID、模型、接口、分组、IP 中至少一个筛选条件。

不接受只输入“晚上 9 点左右”后直接扫描全天日志。页面应先引导转换成类似：

```text
2026-09-13 20:55:00～21:05:00，Asia/Shanghai
```

### 6.2 支持的查询条件

| 条件 | 用途 | 敏感性 |
|---|---|---|
| 用户 ID / 用户名 | 从 NewAPI 业务日志定位候选请求 | 内部 |
| NewAPI Request ID | 精确查业务日志、Nginx 和应用日志 | 敏感标识 |
| CloudFront Request ID | 精确查 CloudFront 入口日志 | 敏感标识 |
| 时间范围和时区 | 所有数据源的共同约束 | 普通 |
| 模型 | 缩小业务候选 | 内部 |
| 分组 | 缩小业务候选 | 内部 |
| 渠道 ID / 上游域名 | 判断上游影响面 | 经营敏感 |
| API 路径 | 区分 Responses、Chat、Messages 等接口 | 普通 |
| HTTP 状态码 | 缩小异常类型 | 普通 |
| 是否流式 | 区分长连接、终态和客户端断开 | 普通 |
| 客户出口 IP | 查入口网络、ASN、国家和重复来源 | 个人/网络敏感 |
| User-Agent | 判断客户端及版本 | 个人/设备敏感 |

完整 API Key、Authorization、请求体、提示词和响应正文不得作为排障输入。

### 6.3 查询接口必须使用 POST

现有 `/logchain/requests` 是 GET 接口，应继续保留以避免破坏现有功能。新增 CloudWatch 增强查询应使用 POST body，不能把用户 ID、Request ID、IP 等放进 URL、浏览器历史和 Nginx access log。

建议新增：

```text
POST /logchain/investigations
GET  /logchain/investigations/:id
POST /logchain/investigations/:id/cancel
```

## 7. 标准取数流程

### 7.1 第一步：校验与标准化输入

Monitor 后端完成：

1. 把用户时区转换成 UTC；
2. 限制查询最大跨度；
3. 校验用户是否有普通排障或敏感排障权限；
4. 将域名、路径、模型、分组和状态码收敛到允许格式；
5. 拒绝前端提交任意日志组、任意 Logs Insights 语句或任意 AWS 区域；
6. 为本次排障生成 `investigation_id`；
7. 记录操作者、用途、查询时间范围和筛选类型，不记录完整敏感值。

建议默认时间窗口：

| 场景 | 默认窗口 |
|---|---:|
| 已知精确 Request ID | 报障时间前后各 2 分钟 |
| 已知用户 ID、模型和大致时间 | 前后各 5 分钟 |
| 只知道 IP 或接口 | 前后各 10 分钟 |
| 超过 2 小时 | 拒绝交互查询，要求继续缩小或走受控历史任务 |

### 7.2 第二步：从 NewAPI 只读数据锁定候选请求

先调用现有 `logchain` 查询能力，按以下优先级定位：

1. NewAPI Request ID 精确匹配；
2. 用户 ID + 精确时间；
3. 用户 ID + 模型 + 分组 + 时间；
4. 令牌名称片段 + 时间；
5. 渠道、模型、分组和错误类型组合。

继续保留现有保护：

- 生产库只读；
- 单次 SQL `MAX_EXECUTION_TIME` 8 秒；
- 与客户 Portal 共用的明细查询并发闸门；
- 内部排障超时不得大于客户 Portal；
- 单页默认 50、最大 200；
- 复合游标分页；
- 禁止无筛选的大跨度全表扫描。

输出一组候选 `LogChainRow`。每行至少包含：

```text
created_at
user_id
request_id
request_path
model_name
group
channel_id
status/error
use_time
is_stream
```

如果 NewAPI 没有候选记录，不应立刻结束。继续查 CloudFront 和 Worker，因为路由前拒绝、入口拦截、客户端提前断开等情况可能不会写入 `logs` 表。

### 7.3 第三步：查询 CloudFront 核心日志

先查：

```text
区域：us-east-1
日志组：nexusapi-cloudfront-access
```

优先级：

1. 有 CloudFront Request ID：精确查询；
2. 无 CloudFront Request ID：按域名、路径、完成时间、状态码和耗时寻找候选；
3. 候选不唯一：全部返回，标记 `ambiguous`，不得自动选一条；
4. 查不到：标记 `pending_delivery` 或 `unavailable`，不得直接标记“客户未到达”。

CloudFront 标准日志中的时间更接近“CloudFront 完成响应的时间”，NewAPI `created_at` 也通常在请求完成后写入。关联时应使用完成时间附近的窄窗口，同时结合路径、状态码和耗时，不要只按秒数硬匹配。

核心日志用于判断：

| 结果 | 可确认事实 |
|---|---|
| 有记录、`sc-status=2xx` | 请求到达 CloudFront，边缘已经开始/完成正常响应 |
| 有记录、`sc-status=403` | 请求在边缘或源站返回 403，需结合详细结果类型/WAF 判断 |
| 有记录、`sc-status=429` | 存在限流响应，需继续定位边缘、Nginx、NewAPI 或上游 |
| 有记录、`sc-status=502/503/504` | 请求到达 CloudFront，后续链路异常 |
| `sc-status=000` | 客户在 CloudFront 返回响应前关闭连接 |
| 完全无记录 | 当前没有入口证据；不能单凭这一点确认客户未到达 |

### 7.4 第四步：按需查询诊断日志

仅当以下条件成立时读取：

```text
区域：us-east-1
日志组：nexusapi-cloudfront-client-diagnostic
```

- 客户反馈反复重连、连接失败或区域性超时；
- 只有某个客户/网络出现问题；
- 需要确认客户出口 IP、ASN、国家、User-Agent、TLS；
- 核心日志存在多个无法区分的候选。

普通排障默认不读取和返回完整 IP、User-Agent。页面默认展示：

- IP 脱敏值或 HMAC；
- ASN；
- 国家；
- User-Agent 归类和版本摘要；
- TLS 版本和密码套件；
- 是否与该客户近期成功请求一致。

查看原始 IP 或完整 User-Agent 应要求敏感排障权限，并记录审计。

### 7.5 第五步：查询 Worker Nginx 日志

查询：

```text
区域：us-west-2
日志组：/ecs/nexusapi-prod-worker
日志流范围：nginx/*
```

有 NewAPI Request ID 时，优先精确匹配 `oneapi_request_id`。没有时，按时间、路径、状态码和耗时候选关联。

需要提取：

```text
@timestamp
@logStream
nginx_request_id
oneapi_request_id
request_method
uri
status
request_time
upstream_status
upstream_response_time
upstream_connect_time
upstream_header_time
bytes_sent
request_completion
```

Nginx 证据用于区分：

| 证据 | 判断方向 |
|---|---|
| CloudFront 有，Nginx 无 | CloudFront 到 ALB/Worker、日志延迟或日志缺口 |
| Nginx 有，NewAPI 业务日志无 | 路由前拒绝、鉴权/参数失败、客户端提前断开或应用未写业务日志 |
| `upstream_status` 为空 | Nginx 未取得应用响应，需查连接/应用进程 |
| 499、`client_gone`、broken pipe | 客户或中间网络提前断开，不能直接归责上游 |
| `upstream_connect_time` 高 | Nginx 到应用连接建立异常 |
| `upstream_header_time` 高 | 应用/上游首字节慢 |
| `request_time` 远高于上游耗时 | 下游传输、客户端读取或其他入口处理可能参与 |

### 7.6 第六步：查询 Worker NewAPI 日志

查询同一日志组中的：

```text
日志流范围：new-api/*
```

优先按 NewAPI Request ID 查询；没有 Request ID 时只允许在窄时间窗内按用户 ID、模型、错误类型或固定错误短语查询。

需要识别并结构化：

- 鉴权失败；
- 令牌禁用或额度问题；
- 分组或模型权限不匹配；
- `No available channel`；
- 渠道选择与重试；
- 上游 401、404、408、429、5xx；
- 数据库连接或 SQL 错误；
- panic、fatal、context canceled、broken pipe；
- 请求开始、结束和耗时信息；
- ECS Task 日志流身份。

`No available channel` 等路由前拒绝可能不写 NewAPI `logs` 表，但会出现在 `new-api/` stdout/stderr。CloudWatch 适配器必须覆盖这类日志，才能在最终移除 `reject-collector` 后不产生监控盲区。

### 7.7 第七步：按条件补查 RDS 与 Master

只有前述证据指向数据库或后台任务时才补查：

```text
/aws/rds/instance/nexusapi-mysql-prod/error
/aws/rds/instance/nexusapi-mysql-prod/slowquery
/ecs/nexusapi-prod-master
```

这一步是故障时间窗相关证据，不尝试把某条 RDS 错误强行绑定到某个用户请求。

### 7.8 第八步：合并时间线并输出结论

最终页面按请求生命周期显示：

```text
1. CloudFront 接收
2. WAF/边缘处理
3. CloudFront 访问源站
4. ALB/Worker 接收
5. Nginx 转发 NewAPI
6. NewAPI 鉴权、分组、模型和渠道选择
7. NewAPI 访问上游或数据库
8. Nginx/CloudFront 向客户回传
9. 客户正常完成或提前断开
```

每个节点必须同时显示：

- 时间；
- 数据源；
- 事实摘要；
- 原始证据引用；
- 关联置信度；
- 数据是否完整；
- 是否存在投递延迟。

## 8. CloudWatch 查询方式选择

### 8.1 `FilterLogEvents`

适合：

- 已知精确 Request ID；
- 已知固定错误短语；
- 后台每 5 分钟增量读取异常；
- 读取某个日志流前缀下的事件；
- 需要低成本、简单分页和水位控制。

必须处理：

- `NextToken` 分页；
- 空页不代表没有下一页；
- 每轮最大事件数；
- 起止毫秒时间；
- 日志组和日志流前缀白名单；
- CloudWatch `eventId` 去重。

### 8.2 Logs Insights `StartQuery`

适合：

- CloudFront JSON 多字段组合检索；
- 状态码、路径、延迟和地域聚合；
- 多个候选请求的排序和统计；
- 客户排障页面的单次窄窗口查询。

调用过程：

```text
StartQuery
  ↓ 返回 queryId
GetQueryResults
  ↓ Scheduled / Running：继续轮询
  ↓ Complete：读取结果和 statistics.bytesScanned
  ↓ Failed / Cancelled / Timeout：返回查询失败
StopQuery
  └─用户取消或应用超时后主动停止
```

要求：

- 不允许前端提交原始查询语句；
- 查询语句由后端固定模板和参数构造器生成；
- 单次最多查询明确列出的日志组；
- 默认返回 100 条，硬上限 500 条；
- 应用层单次查询超时建议 10～15 秒，不等待 AWS 的 60 分钟上限；
- 用户取消、HTTP 请求结束或超时后调用 `StopQuery`；
- `GetQueryResults` 状态为 `Running` 时返回的是部分结果，不能当最终结果；
- 记录 `bytesScanned`、命中条数、耗时和查询状态。

### 8.3 使用原则

| 场景 | 首选 |
|---|---|
| 精确 ID / 固定错误文本 | `FilterLogEvents` |
| CloudFront 多字段筛选 | Logs Insights |
| 统计、分位数、聚合 | Logs Insights |
| 每 5 分钟后台异常采集 | `FilterLogEvents` |
| Dashboard 已有图表 | 直接使用 CloudWatch Dashboard，不由 Monitor 重复采集 |

严禁用 Logs Insights 每 1～5 分钟反复扫描数小时或数天日志。

## 9. 推荐查询模板

这些模板只能由 Monitor 后端按固定结构生成，前端不得原样传入。

### 9.1 按 CloudFront Request ID

日志组：`nexusapi-cloudfront-access`

```sql
filter `x-edge-request-id` = "REQUEST_ID"
| fields @timestamp,
         `x-edge-request-id`,
         `sc-status`,
         `cs-method`,
         `cs-uri-stem`,
         `x-edge-result-type`,
         `x-edge-detailed-result-type`,
         `time-taken`,
         `time-to-first-byte`,
         `origin-fbl`,
         `origin-lbl`
| sort @timestamp asc
| limit 20
```

### 9.2 按路径、状态和时间寻找入口候选

```sql
filter `cs-uri-stem` = "/v1/responses"
| fields @timestamp,
         `x-edge-request-id`,
         `sc-status`,
         `cs-method`,
         `cs-uri-stem`,
         `time-taken`,
         `time-to-first-byte`,
         `origin-fbl`,
         `x-edge-detailed-result-type`
| sort @timestamp asc
| limit 200
```

状态码、域名和耗时条件由后端在需要时追加，不能把空条件拼成全量查询。

### 9.3 按客户 IP 查询网络证据

日志组：`nexusapi-cloudfront-client-diagnostic`

```sql
filter `c-ip` = "CLIENT_IP"
| fields @timestamp,
         `x-edge-request-id`,
         `sc-status`,
         `cs-method`,
         `cs-uri-stem`,
         `c-country`,
         asn,
         `cs(User-Agent)`,
         `ssl-protocol`,
         `ssl-cipher`,
         `time-taken`,
         `origin-fbl`,
         `x-edge-detailed-result-type`
| sort @timestamp asc
| limit 200
```

### 9.4 按 NewAPI Request ID 查询 Nginx

日志组：`/ecs/nexusapi-prod-worker`

```sql
filter @logStream like /^nginx\//
| filter oneapi_request_id = "REQUEST_ID"
| fields @timestamp,
         @logStream,
         nginx_request_id,
         oneapi_request_id,
         request_method,
         uri,
         status,
         request_time,
         upstream_status,
         upstream_response_time,
         upstream_connect_time,
         upstream_header_time,
         bytes_sent,
         request_completion
| sort @timestamp asc
| limit 50
```

上线前必须用生产样本验证 JSON 自动发现字段名。如果某些 Nginx 行仍是纯文本，应先由解析器读取 `@message`，不得静默丢弃。

### 9.5 查询 NewAPI 应用异常

```sql
filter @logStream like /^new-api\//
| filter @message like /REQUEST_ID/
| fields @timestamp, @logStream, @message
| sort @timestamp asc
| limit 100
```

没有 Request ID 时只能使用固定错误短语和窄时间窗，例如：

```sql
filter @logStream like /^new-api\//
| filter @message like /No available channel|panic|fatal|timeout|broken pipe/
| fields @timestamp, @logStream, @message
| sort @timestamp asc
| limit 200
```

自由文本在返回前必须经过统一脱敏。

## 10. 跨区域读取实现

Monitor 需要两个长期复用的 CloudWatch Logs Client：

```text
us-east-1 client
  ├─nexusapi-cloudfront-access
  └─nexusapi-cloudfront-client-diagnostic

us-west-2 client
  ├─/ecs/nexusapi-prod-worker
  ├─/ecs/nexusapi-prod-master
  ├─/aws/rds/instance/nexusapi-mysql-prod/error
  └─/aws/rds/instance/nexusapi-mysql-prod/slowquery
```

不能用一个区域客户端读取另一区域日志。两区查询可以并行执行，由 Monitor 在本地按 UTC 时间合并；任何一个区域失败时返回 `partial`，不能把另一侧成功结果一起丢弃。

推荐代码边界：

```text
monitor/cloudwatch_logs_client.go
  └─封装 AWS SDK、分页、Start/Get/Stop、超时和重试

monitor/cloudwatch_log_sources.go
  └─日志组白名单、区域、日志流前缀和数据源健康

monitor/logchain_cloudwatch.go
  └─根据排障条件生成固定查询、解析和关联证据

monitor/logchain_investigation.go
  └─异步任务、权限、缓存、审计、取消和 API 响应
```

Go 依赖：

```bash
go get github.com/aws/aws-sdk-go-v2/service/cloudwatchlogs
```

业务代码只使用 AWS SDK 默认凭证链，不自行读取或拼接密钥。

## 12. 关联规则与证据等级

### 12.1 禁止伪造全链路精确关联

当前标识包括：

- CloudFront `x-edge-request-id`；
- Nginx `nginx_request_id`；
- Nginx `oneapi_request_id`；
- NewAPI `logs.request_id`；
- 上游返回的 request id 或错误体内 ID。

CloudFront Request ID 和 NewAPI Request ID 当前不是同一个值，也没有完成统一透传验收。因此：

- 有相同 NewAPI Request ID 的 Nginx 与业务日志可以标记 `exact`；
- 有相同 CloudFront Request ID 的两组 CloudFront 日志可以标记 `exact`；
- CloudFront 与 Nginx/NewAPI 之间只能在没有统一 ID 时做候选相关，不能标记 `exact`。

### 12.2 证据等级

| 等级 | 定义 | 示例 |
|---|---|---|
| `exact` | 同一已验证 ID 或同一日志事件直接证明 | `oneapi_request_id = logs.request_id` |
| `correlated` | 时间、路径、状态、耗时和唯一候选高度一致 | 窄窗口只有一个 CloudFront 与一个 Nginx 候选 |
| `inferred` | 多个弱条件支持，但仍可能是其他请求 | 同用户同模型高并发下的时间相关 |
| `ambiguous` | 同一回退键存在多个候选 | 一秒内多个相同路径请求 |
| `unavailable` | 必要观察点不存在、未覆盖或尚未投递 | CloudFront 日志延迟或域名不在覆盖范围 |
| `telemetry_gap` | 按设计应该有数据，但采集或查询链路存在缺口 | Worker 有请求但对应日志流断流 |

`correlated`、`inferred` 和 `ambiguous` 不得在页面上写成“就是这条请求”。

### 12.3 无统一 ID 时的候选匹配键

按以下顺序组合：

1. 完成时间；
2. Host；
3. API 路径；
4. HTTP 状态；
5. 总耗时容差；
6. 是否流式；
7. 客户 IP/ASN/User-Agent 摘要；
8. 同一窗口候选唯一性。

只有候选唯一且各关键字段一致时，才允许标记 `correlated`。存在多个候选时返回列表，不替用户猜测。

### 12.4 推荐的后续增强

在不修改 NewAPI 代码和数据库结构的前提下，可评估由 Nginx 日志记录 CloudFront 传入的 `X-Amz-Cf-Id`，形成：

```text
CloudFront x-edge-request-id
  = Nginx 记录的 X-Amz-Cf-Id
```

这项增强必须先确认请求头传播、日志字段脱敏、大小和全节点一致性，再灰度启用。验证完成前，不能提前把 CloudFront 与 Nginx 关联标为 `exact`。

## 13. 故障分类输出

结果应使用共享 `observability.v1` 的 fault class。客户排障最常用：

| 分类 | 主要证据 |
|---|---|
| `transport_connect` | CloudFront/ALB/Nginx 连接失败 |
| `transport_timeout` | 入口、应用或上游连接/读取超时 |
| `upstream_first_byte_slow` | Nginx header time、CloudFront origin-fbl 与业务耗时 |
| `stream_interrupted_before_first_event` | 无有效事件即中断 |
| `stream_interrupted_midstream` | 已有数据但无合法终态 |
| `client_gone` | 499、broken pipe、NewAPI `client_gone` |
| `route_no_channel` | `No available channel` |
| `model_not_found` | 模型或映射不存在 |
| `auth_quota_account` | 上游/本地凭证、账户或额度确定性错误 |
| `rate_limit_capacity` | 429、RPM、TPM、并发或容量限制 |
| `upstream_5xx` | NewAPI 明确记录上游 5xx |
| `billing_anomaly` | NewAPI 使用和计费事实不一致 |
| `telemetry_gap` | 应有日志但数据源缺失 |
| `unknown` | 已确认异常但证据不足以分类 |

必须把“故障分类”和“责任归属”分开。例如 `client_gone` 是事实，不等于客户有责任；它也可能由上游首字节过慢导致客户或代理超时。

## 14. 页面展示要求

### 14.1 搜索区

分成两层：

1. 常用条件：时间、用户 ID/用户名、Request ID、模型、接口；
2. 高级条件：分组、渠道、状态码、IP、User-Agent、是否流式。

页面必须显示当前查询：

- 北京时间与 UTC；
- 实际生效的时间范围；
- 查询了哪些区域和日志组；
- 是否读取了敏感诊断日志；
- 是否命中缓存；
- 是否存在结果截断或日志投递延迟。

### 14.2 结果区

建议顺序：

1. 结论摘要；
2. 候选请求列表；
3. 单请求全链路时间线；
4. NewAPI 业务信息；
5. CloudFront 客户与网络证据；
6. Nginx 与应用证据；
7. 上游错误；
8. RDS/Master 同时段证据；
9. 盲区和下一步建议。

每一项明确标识：

```text
事实
高置信相关
推断
候选
不可用
数据缺口
```

### 14.3 原始日志

默认不展示整段原始 CloudWatch 日志。页面只展示结构化字段和脱敏摘要，并提供受限的“查看原始证据”操作：

- 仅管理员或指定运维可用；
- 每次查看记录审计；
- 不允许批量导出；
- 不显示 Authorization、Cookie、API Key、请求体和响应体；
- 自由文本再次经过脱敏。

## 15. 数据保存与缓存

### 15.1 不复制全部日志

CloudWatch 是原始云端日志的权威存储。Monitor 不保存完整副本，只保存：

- `investigation_id`；
- 查询范围和筛选条件摘要；
- 操作者和审计信息；
- 数据源状态；
- CloudWatch Event ID、Request ID 的 HMAC 或证据引用；
- 结构化故障类型、状态码、耗时；
- 脱敏错误摘要；
- 关联等级和结论；
- 查询扫描量、耗时和是否截断。

### 15.2 缓存

相同操作者在短时间内重复刷新同一条件时，应复用结果：

- 精确 Request ID：缓存 10 分钟；
- 普通时间窗查询：缓存 3～5 分钟；
- CloudFront `pending_delivery`：允许后台在 5、15、60 分钟后受控复查；
- 缓存键使用标准化条件和 HMAC，不保存原始 IP/Request ID 到通用缓存键。

缓存只减少重复 AWS 查询，不能把旧结果长期当成最新事实。

### 15.3 Monitor 自有存储

如果需要持久化异步任务，可在 Monitor 自己的 SQLite/WAL 中增加最小任务表和证据引用表。这不属于修改 NewAPI 数据库结构。

不建议为首版建立一套完整日志仓库。

## 16. IAM 与凭证

### 16.1 身份分离

| 场景 | 身份 | 凭证来源 |
|---|---|---|
| 开发人员本地调试 | 个人只读 IAM 身份，如 `monitor-dev-gaowenxing` | `aws login` 临时会话 |
| 正式 ECS Monitor（部署目标） | 已有 `nexusapi-monitor-ro` ECS Task Role | ECS 自动发放临时凭证，SDK 默认链读取 |
| 本机只读验收 | 临时只读 IAM 身份 | `aws login` 或受控 `.env`，不得提交或写入镜像 |

浏览器不直接调用 AWS，不获得任何 AWS 凭证。

### 16.2 程序最小权限

生产身份只允许读取明确列出的日志组，所需动作按实现选择：

```text
logs:FilterLogEvents
logs:StartQuery
logs:GetQueryResults
logs:StopQuery
```

如果运行时使用固定日志组名称，则不需要为了“自动发现”把权限扩大到账号全部日志。

建议显式拒绝：

```text
logs:Unmask
```

示例策略需要在测试账号或 IAM Policy Simulator 中验证后再上线：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadNexusAPICloudWatchLogs",
      "Effect": "Allow",
      "Action": [
        "logs:FilterLogEvents",
        "logs:StartQuery",
        "logs:GetQueryResults"
      ],
      "Resource": [
        "arn:aws:logs:us-east-1:842806122225:log-group:nexusapi-cloudfront-access:*",
        "arn:aws:logs:us-east-1:842806122225:log-group:nexusapi-cloudfront-client-diagnostic:*",
        "arn:aws:logs:us-west-2:842806122225:log-group:/ecs/nexusapi-prod-worker:*",
        "arn:aws:logs:us-west-2:842806122225:log-group:/ecs/nexusapi-prod-master:*",
        "arn:aws:logs:us-west-2:842806122225:log-group:/aws/rds/instance/nexusapi-mysql-prod/error:*",
        "arn:aws:logs:us-west-2:842806122225:log-group:/aws/rds/instance/nexusapi-mysql-prod/slowquery:*"
      ]
    },
    {
      "Sid": "StopOwnCloudWatchQueries",
      "Effect": "Allow",
      "Action": "logs:StopQuery",
      "Resource": "*"
    },
    {
      "Sid": "DenyUnmask",
      "Effect": "Deny",
      "Action": "logs:Unmask",
      "Resource": "*"
    }
  ]
}
```

注意：CloudWatch Logs 的大多数读取动作要求 IAM `Resource` 使用日志组 ARN 的 `:*`
后缀；漏掉后缀会表现为“凭证有效、部分旧权限可读，但新列出的日志组仍
AccessDenied”。不同动作的 ARN 形式仍可能不同；实际部署前必须通过 IAM Policy
Simulator 和真实窄窗口请求验证 `FilterLogEvents`、`StartQuery`、`GetQueryResults`、
`StopQuery`，不能因为某项被拒绝就临时授予管理员权限。

### 16.3 敏感诊断权限

建议在 Monitor 应用层把诊断日志单独授权：

- 普通 `view`：只查核心日志、Worker、Master、RDS；
- `sensitive_diagnostics`：允许查诊断日志中的 IP 和 User-Agent；
- `admin`：允许查看脱敏后的原始证据和查询审计。

AWS 侧可进一步将诊断日志组拆给单独角色；首版如果共用同一程序身份，也必须在应用层做权限和审计隔离。

## 17. 安全与隐私要求

1. 前端不传任意 Logs Insights 查询；
2. 前端不传任意日志组、区域或日志流前缀；
3. 所有查询参数均由后端校验和参数化；
4. 不把 Request ID、用户 ID、IP 写入 GET query；
5. 不采集或保存请求体、响应体、提示词和工具参数；
6. 不保存完整 API Key、Token、Authorization、Cookie；
7. 原始 IP、User-Agent 只在受限页面短期展示；
8. Request ID 和 IP 的长期关联使用带 `key_id` 的 HMAC；
9. HMAC 密钥只在 Secrets Manager 或安全部署变量中保存；
10. 页面导出默认脱敏、限量、限时并记录审计；
11. 日志解析失败时不能把未脱敏原文直接作为错误消息返回前端；
12. Monitor 自身日志不得打印完整查询输入和 AWS 查询结果。

## 18. 查询费用和性能控制

CloudWatch Logs Insights 按扫描数据量收费，过滤后返回几条并不代表只扫描几条。控制成本最有效的是缩短时间范围、减少日志组，而不是只增加复杂过滤条件。

必须设置：

| 控制项 | 建议值 |
|---|---:|
| 交互查询默认时间窗 | 5～10 分钟 |
| 普通交互最大时间窗 | 2 小时 |
| 默认结果数 | 100 |
| 单源硬上限 | 500 |
| 单次 AWS 调用超时 | 10～15 秒 |
| 单个排障任务总超时 | 20～30 秒 |
| 单用户并发排障任务 | 1 |
| 全局 CloudWatch 交互查询并发 | 2～4 |
| 查询结果缓存 | 3～10 分钟 |
| 后台异常读取周期 | 5 分钟 |
| 后台重叠窗口 | 2 分钟左右 |

Monitor 必须记录：

- 每次查询的日志组；
- 时间范围；
- 命中数；
- `bytesScanned`；
- 查询耗时；
- 是否使用缓存；
- 是否被限流；
- 是否截断；
- 每日和每月累计扫描量。

建议配置软预算和硬保护：

- 单次扫描量超过软阈值时提示缩小范围；
- 日累计扫描量异常增长时告警；
- 达到硬保护后暂停非必要历史查询，不影响精确 Request ID 排障；
- Dashboard 自动刷新与 Monitor 查询分别统计，避免费用来源混淆。

## 19. 可靠性与降级

### 19.1 CloudWatch 查询失败

CloudWatch 失败只能影响当前证据源，不能导致：

- Monitor 主进程退出；
- NewAPI 请求失败；
- 现有数据库排障结果不可用；
- 稳定性采样和告警整体停止。

返回示例：

```text
NewAPI 业务证据：成功
Worker 日志：成功
CloudFront 核心日志：查询超时
客户诊断日志：未授权
RDS 日志：未触发查询
整体状态：partial
```

### 19.2 日志延迟

CloudFront 标准日志不是严格实时日志。刚发生的问题暂时查不到时：

1. 页面标记 `pending_delivery`；
2. 保留查询条件；
3. 允许 5、15、60 分钟后受控复查；
4. 不自动把结果改成“客户网络问题”；
5. 仍优先使用已实时到达的 Worker、NewAPI 和 ALB 指标。

### 19.3 极端请求无法记录

CloudFront 官方说明，URL 或全部请求头超过其解析上限时可能无法生成正常访问日志。因此 CloudFront 无记录只表示“当前没有可用入口日志证据”，不是请求一定没有接触过 CloudFront。

### 19.4 自动扩缩容

Monitor 只查询日志组和日志流前缀：

```text
/ecs/nexusapi-prod-worker + nginx/
/ecs/nexusapi-prod-worker + new-api/
```

它不保存 ECS Task 白名单，不要求新 Task 回调注册。新任务只要使用同一任务定义和 `awslogs` 配置，其日志会自动进入同一日志组，Monitor 无需修改和重启。

## 20. Monitor 自身可观测性

Monitor 必须为 CloudWatch 读取模块展示：

| 指标 | 说明 |
|---|---|
| 最后成功查询时间 | 按区域和日志组分别显示 |
| 最后事件时间 | 判断数据新鲜度 |
| 查询延迟 | AWS 请求和整个排障任务耗时 |
| 查询成功率 | 区分正常无结果与查询失败 |
| 读取事件数 | 原始命中和解析成功数量 |
| 解析失败数 | 日志格式漂移或异常行 |
| 去重数 | 重叠窗口和重复事件 |
| 截断数 | 达到事件上限 |
| 限流次数 | AWS Throttling |
| 扫描字节 | Logs Insights 成本依据 |
| 缓存命中率 | 判断重复查询 |
| `pending_delivery` 数量 | CloudFront 延迟任务 |
| `telemetry_gap` 数量 | 应有证据但日志缺失 |

数据源异常必须显示成“监控盲区”，不能把错误数显示为 0 或把渠道标记为健康。

## 21. 开发实施顺序

### 阶段 1：只读客户端与固定查询

1. 引入 CloudWatch Logs SDK；
2. 建立 `us-east-1`、`us-west-2` 两个客户端；
3. 写死允许的区域、日志组和日志流前缀；
4. 实现 `FilterLogEvents` 分页读取；
5. 实现 `StartQuery/GetQueryResults/StopQuery`；
6. 完成超时、取消、限流和错误分类；
7. 使用 fixture 测试，不接页面。

### 阶段 2：解析与脱敏

1. 解析 CloudFront 核心 JSON；
2. 解析 CloudFront 诊断 JSON；
3. 解析 Nginx JSON 和纯文本 error；
4. 解析 NewAPI 关键错误；
5. 解析 RDS error/slowquery；
6. 建立统一结构化证据和脱敏测试；
7. 未识别格式计入解析失败，不静默丢弃。

### 阶段 3：接入现有 logchain

1. 保留现有 `/logchain/requests`；
2. 新增 POST 异步排障接口；
3. 复用 `LogChainRow` 作为业务候选；
4. 对每个候选补齐 CloudWatch 证据；
5. 显示 evidence level、source status 和 blind spots；
6. CloudWatch 失败时保证现有排障仍可用。

实施状态（2026-09-17）：阶段三已在本地生产只读验收栈 `127.0.0.3:8204` 以
`newapi-monitor:v90` 部署并完成真实窄窗口验收。异步任务、取消入口、跨来源时间线、
来源状态、证据等级、blind spots、查询成本、短缓存和追加式 HMAC 审计均已实证；页面资源为
`logchain.js?v=15`。阶段四 7 天 Shadow 尚未开始，因此旧采集器仍保留，不能因阶段三已完成
而提前删除。

开发准备状态（2026-09-18）：已新增阶段四 Shadow 的运行表和差异表、旧采集器与
CloudWatch 结构化证据的逐分钟归一化比较器、差异维度 HMAC 留痕、默认关闭的配置契约和
有界后台执行骨架。生产 Nginx JSONL 小窗口验收通过后，已将 v92 阶段四二进制部署到
8204 只读验收栈；但核对发现该栈没有当前旧采集器基线，因此 Shadow 已保持关闭，正式
7 天计时尚未开始。

持续采集状态（2026-09-20）：在不启动完整来源 worker 的前提下，8204 已新增并开启独立的
CloudWatch 前置拒绝连续 lane，使用固定白名单查询把 168 小时拒绝事实聚合到本地
`rejection_samples`，供模型统计读取。它有独立持久水位、失败不推进、迟到 20 分钟重放、
截断递归拆分和原子窗口替换；与阶段四 Shadow 完全独立。真实 168 小时回补已追平，v98
重建后只重放尾部窗口；2026-09-20 后续页面增强已重建为 `newapi-monitor:v99`，持续采集
水位和原数据卷保持不变。Shadow 两个准入开关仍为 false，7 天对账没有
因此自动开始；这是主动直采切换前的状态，后续决策见下一段。

Nginx 主动直采状态（2026-09-20）：旧 `nginxcollector` 已不再向生产 Monitor 正常上报，
恢复旧链路也不作为本轮方案。Monitor 新增独立的 CloudWatch Nginx 连续 lane，直接读取
结构化 access 与标准 error.log，按分钟聚合到现有 Nginx 本地事实表；原始日志、IP、Header、
请求/响应正文和 Request ID 原值均不落盘。access/error 共用一个原子水位，查询、解析和事务
发布全部成功后才推进；高流量窗口自动拆分，追平后重放最近 20 分钟。v101 另加最近 72 小时
的低频闭合小时补扫，每 20 分钟修复一个小时，修复水位持久化且不改写主水位；窗口采用
删除后原子重建，超过 20 分钟的迟到日志能够补回且不会重复累计。重叠分钟优先采用
`cloudwatch-direct`，旧历史只作为未覆盖分钟的回退，避免双算且不破坏历史。

### 阶段 4：Shadow 对账

阶段四原定的“旧采集器与 CloudWatch 同窗口 Shadow”开发基础已经具备，但当前没有可用的
旧 Nginx 同窗口基线，因而不能按原方案开始正式计时：

- `CloudWatchShadowReconciliationRun` 保存每个有限时间窗的状态、查询成本、两侧总量和盲区；
- `CloudWatchShadowReconciliationDiff` 只保存泳道、分钟桶、差异指标和维度 HMAC，不保存
  Request ID、客户 IP、模型、分组、用户 ID 或原始日志；
- Nginx 对账比较请求数、状态码、上游状态码、请求耗时总和/最大值和 Request ID 覆盖数；
- 前置拒绝比较 reason、model、group、user 的分钟计数，并把旧的 `no_channel` 等值归一为
  `route_no_channel`；普通 NewAPI 错误不会混入拒绝对账；
- 对账结果采用单事务发布，运行头或差异批次任一写入失败都不发布半个结果。
- 已补上有界后台执行骨架：每轮只使用 Nginx access 与 NewAPI 前置拒绝两类
  白名单 Insights 查询。单次查询保持 500 行上限，截断后在 64 次、2 分钟总预算内按秒边界
  自动拆分；记录查询次数/扫描字节/盲区并按保留期清理；默认不开启，且
  只有显式确认 `MONITOR_CLOUDWATCH_SHADOW_NGINX_CONTRACT_READY=true` 才会启动。
- 旧拒绝表中的未知 reason 与普通 NewAPI 错误会被排除；Nginx 查询只接收必需 access 字段
  完整的结构化行，同前缀错误/运行日志不会进入 access 解析；结构化解析失败时泳道标记
  `blocked_log_contract`，不会把纯文本日志或零条结果当成一致。

生产侧 Nginx 日志投递准入已在 2026-09-18 完成小窗口验收：最近窗口中的访问日志已为
结构化 JSONL，字段覆盖 `nginxcollector` 对账所需的请求方法、路径、状态、耗时、上游字段、
完成原因及两个 Request ID；同一 `nginx/` 前缀下的错误/运行日志仍按错误日志解析，不计作
访问事实。不能把 CloudWatch 的零条结果直接当成“与旧采集器差异为零”，只有查询成功、
未截断、结构化解析通过且旧侧在同一窗口有基线时才允许发布 Nginx/拒绝差异。v92 已加入
旧侧基线缺失的 fail-closed 状态 `blocked_legacy_baseline`，避免把 8204 的空旧表误报为
全量差异。2026-09-20 对生产 SQLite 一致性副本核对后确认：完整旧 Nginx 基线止于
2026-09-16 19:02 CST，而结构化 CloudWatch access 在 2026-09-18 改造后才具备，当前没有
可用于签字的同窗口重叠；因此正式 7 天 Shadow 计时仍未开始。

2026-09-20 的实际决策是不恢复旧 `nginxcollector`，并明确不把固定 7 天作为本轮继续推进的
必要条件，改用 8204 真实闭合窗口的逐字段短期验收。v101 的真实验收先发现同一小时总量相同
但分钟明细存在迟到差异，随后由 72 小时补扫原子修复；复查时 478 个 access 聚合行和 61 个
error 聚合行逐字段一致，重启后主/修复水位均保持。该结果证明当前 Monitor 直采和迟到补数
链路在已测范围内有效，但**不等于旧/新两套独立来源的 7 天 Shadow 已通过**。若未来重新要求
证明两套来源等价，仍必须另行提供独立同窗口基线。

原定 7 天 Shadow 内容保留为可选的独立来源等价验收方案，不再是当前门槛：

1. 同窗口对比 CloudWatch Nginx 与现有 `nginxcollector`；
2. 对比 CloudWatch NewAPI 拒绝日志与 `reject-collector`；
3. 对比请求量、状态码、耗时、错误类型和 Request ID 覆盖率；
4. 验证 ECS 滚动更新和自动扩缩容期间无需人工配置；
5. 记录所有差异，不用“总量差不多”代替逐类验收。

### 阶段 5：切换默认来源

1. Monitor 页面默认使用 CloudWatch 证据；
2. 旧采集器继续运行但不作为主来源；
3. 观察数据完整性、查询成本和排障效果；
4. 出现缺口时可通过功能开关回退旧来源；
5. 不影响 NewAPI、ECS 和客户请求。

8204 验收栈已按此顺序切换为 `cloudwatch-direct` 默认来源：同一分钟有新旧两类事实时只读
CloudWatch 行，尚未覆盖的旧分钟继续可查；旧历史和旧镜像仍保留作为回看与回滚依据。

### 阶段 6：移除旧链路

只有 Shadow 和正式观察均通过后，才按顺序：

1. 停止 Monitor 对旧采集数据的依赖；
2. 验证稳定性报表、模型监控、渠道异常、Nginx 耗时和拒绝统计；
3. 逐步移除 Worker 中 `nginxcollector`；
4. 逐步移除 Worker 中 `reject-collector`；
5. 确认 Lambda Bridge 调用降为 0 且无重试；
6. 再评估删除 API Gateway、Lambda、密钥和桥日志组；
7. 每一步单独观察并保留回滚点。

不能因为 CloudWatch Dashboard 已能看图表，就直接删除旧采集器。Dashboard 能看基础设施和原始日志，不等于 Monitor 已完成业务解析、关联和统计替代。

## 22. 验收场景

验收使用通用场景，不绑定某个过时用户或某次历史故障。

### 22.1 请求未到达入口

- 客户提供时间、域名和本地错误；
- CloudFront、Worker、NewAPI 均无记录；
- 系统输出 `unavailable`，说明可能未到达、域名不在覆盖或日志延迟；
- 不直接归因为客户网络。

### 22.2 WAF/边缘拦截

- CloudFront 有 403；
- Worker 无记录；
- 详细结果或 WAF 证据一致；
- 输出边缘拦截事实，不归为上游错误。

### 22.3 到达 Worker 但没有业务日志

- CloudFront 和 Nginx 有记录；
- NewAPI `logs` 表无记录；
- NewAPI stdout 出现鉴权、参数或路由前拒绝；
- 能说明为什么数据库使用日志没有该请求。

### 22.4 无可用渠道

- NewAPI 业务表没有消费/错误行；
- `new-api/` stdout 有 `No available channel`；
- 能解析模型、分组、用户或请求 ID 中实际存在的字段；
- 输出 `route_no_channel`。

### 22.5 上游 429/5xx/超时

- 业务日志有渠道和上游错误；
- Nginx 与 NewAPI Request ID 精确关联；
- CloudFront 候选按当前标识能力显示 `correlated`；
- 输出对应 fault class、渠道和影响面。

### 22.6 客户端断开

- Nginx 499/broken pipe 或 NewAPI `client_gone`；
- 同时展示首字节、总耗时和已发送字节；
- 不直接认定为客户责任；
- 能提示检查上游慢、代理超时和客户网络。

### 22.7 数据库异常

- 多用户、多模型同窗口异常；
- NewAPI 有数据库错误；
- RDS 日志或指标同步异常；
- 输出数据库相关证据和范围，不强行绑定单条慢查询。

### 22.8 日志延迟和数据源失败

- CloudFront 暂时未投递；
- 某一区域 AccessDenied、超时或限流；
- 页面显示 `pending_delivery` 或 `partial`；
- 不把缺失显示成 0 或健康；
- 其他来源结果仍正常展示。

### 22.9 自动扩缩容

- 扩容产生新的 ECS Task ID；
- 新任务日志自动进入既有日志组；
- Monitor 无需新增实例配置和重启；
- 客户排障能查到新任务上的请求。

### 22.10 多候选歧义

- 同一用户在一秒内并发多个相同模型请求；
- CloudFront 与 NewAPI 无统一 ID；
- 页面列出多个候选并标记 `ambiguous`；
- 不自动选中一条并输出确定性结论。

## 23. 上线门禁

上线前必须全部满足：

- CloudWatch 查询为只读；
- 未修改 NewAPI 代码和数据库结构；
- 浏览器无 AWS 凭证；
- 两区客户端和日志组白名单正确；
- 普通日志与敏感诊断权限分离；
- 查询超时、取消、并发和结果上限生效；
- 查询失败不影响现有 Monitor 和 NewAPI；
- CloudFront 延迟和日志缺失不会被误判；
- 关联等级在页面清晰展示；
- 原始 ID、IP 和自由文本经过脱敏；
- `bytesScanned` 和查询成本可观察；
- 自动扩缩容新 Task 无需人工注册；
- 按批准口径完成真实闭合窗口逐字段对账；若要证明旧/新独立来源等价，再提供同窗口基线并
  运行约定时长的 Shadow；
- 旧采集代码、旧历史和旧镜像仍保留回滚能力；
- 删除旧链路必须单独审批和分步执行。

## 24. 当前明确限制

1. CloudWatch 不能单独按用户 ID、分组、模型或渠道查询 CloudFront 请求；
2. CloudFront 与 NewAPI Request ID 尚未统一，跨层精确关联能力有限；
3. CloudFront 标准日志存在延迟，不能承担秒级实时告警；
4. CloudFront 日志不覆盖 `pathgo.link` 与 `verify.pathgo.link`；
5. CloudFront 不记录请求体，无法判断请求体内模型和 `stream`；
6. RDS 日志只能作为时间窗故障证据，不能直接定位用户；
7. 客户端最终是否收到完整流，需要客户端直接遥测才能成为精确事实；
8. “CloudWatch 查不到”不等于“没有发生”；
9. “HTTP 200”不等于流式协议完整成功；
10. “client_gone”不等于客户必然有责任。
