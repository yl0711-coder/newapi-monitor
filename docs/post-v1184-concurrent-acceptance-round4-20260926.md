# 第四小步：报表与本地写入并发验收

## 边界

本轮只补并发验收与自动回归，不增加产品功能、不开新连接池、不改变现有连接预算或生产开关。未访问线上、未下载新数据、未提交/打 tag/部署。前几轮产品改动继续保留。

使用已有本地备份的私有临时副本。真实备份只读打开用于复制，所有模拟写入都发生在副本和临时测试表；没有启动 NewAPI、上游、AWS 采集或真实生产回填任务。运行后临时数据库由测试框架清理。

## 确定性事务回归

在 `finance_facts_reader_test.go` 增加完整赠送分配路径的 WAL 事务测试，而不止做单条 Count 查询：

1. 预热已校验赠送证据；主库/事实库独立文件，事实写池限制为一个连接。
2. 外层事务内使用既有发布函数更新用户事实和对应赠送边界，在提交前核验仍得到旧金额。
3. 同时从被占用的写池查询，确认测试确实制造了等待；独立只读连接仍能完成完整核验。
4. 提交后缓存失效，核验得到修正金额。
5. 未提交的篡改不泄漏到读取结果，回滚后原金额保持不变。

本轮该测试未发现需要修改的产品错误，没有放宽金额断言。

## 真实备份副本负载

- 8 个客户端，每 150ms 调用一次实际经营核算 HTTP handler（httptest，无网络监听），不是直接读取缓存函数。
- 主库、事实库各一个写循环：每 100ms 尝试一次小事务，更新隔离的测试行，事务内等待 20ms，模拟短批次持有连接。
- 同时进行最多 3 次强制冷月组件重算；HTTP 继续展示已核验快照。
- 完整报表除 `generated_at` 外逐项对照基线；负载结束后必须重新构建成功且结果相同。
- 明确开启现有 `FinanceFactsReadIsolationEnabled` 和快照读取功能，仅用于测试配置，不代表改过生产配置。

| 场景 | HTTP 成功读取 | 写入成功 | 错误/结果差异 | HTTP p95 | 写入 p95 |
|---|---:|---:|---:|---:|---:|
| 本机 12 秒 | 632 | 238 | 0 | 45.8ms | 28.3ms |
| Docker 12 秒，1.25 CPU / 768MiB | 616 | 237 | 0 | 165.7ms | 76.9ms |
| Docker 65 秒，同样限制 | 3,452 | 1,298 | 0 | 97.2ms | 49.0ms |

本机完成 3 次并发冷构建，Docker 在负载窗口内完成 2 次，第三次随测试结束取消；两者结束后显式重建均成功。测试结束时的 context canceled 诊断由验收主动取消触发，不计作运行期间的 HTTP 成功或失败；金额对照没有忽略运行期间错误。

主库累计连接等待分别约 11.1 秒、45.9 秒，这是多个并发调用的累计值，不是单次请求等待。事实写池累计连接等待为 0；仍不能推导为生产不会等待或 SQLite 无压力。

## 限制

测试证明的是当前快照路径、金额核验和受控短事务并发，不是所有真实采集 SQL 的完整复演，也不是全天 soak test 或生产 SLA。持续业务事实修订的拒绝发布、保留旧快照、提交/回滚边界由独立故障回归覆盖；本地负载中的模拟写入没有伪造业务金额变更。

此次没有证据支持直接加大 SQLite 连接池。主库配置读取仍可能排队；长期事务、生产真实任务调度和更大历史数据量仍需后续有证据地治理。
