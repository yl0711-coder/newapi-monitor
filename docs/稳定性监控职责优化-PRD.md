# 稳定性监控职责优化——产品需求文档（PRD）

> 版本：v1.0
> 日期：2026-09-02
> 状态：已评审，待研发
> 第一优先级：稳定性统计口径纠偏
> 页面名称约束：“模型监控”保持原名

## 1. 产品概述

本项目调整 Monitor 对服务质量问题的分类、展示和联动方式，使三个现有模块形成清晰闭环：

- 模型监控回答“现在是否有模型、分组或实际渠道正在出问题”；
- 稳定性报表回答“一段时间内平台、渠道和用户体验是否稳定，问题趋势是什么”；
- 客户排障回答“某一次请求具体发生了什么，有哪些证据，结论可信到什么程度”。

本项目不通过隐藏用户异常来提高稳定率，也不允许用户误用降低平台和渠道稳定率。所有影响用户使用的事件都必须可见，但归入不同指标和处置流程。

## 2. 产品原则

1. **先分类，后计算。** 未完成责任和证据分类的数据不得直接进入稳定率。
2. **请求与尝试分开。** 平台按逻辑请求统计，渠道按实际尝试统计。
3. **问题可见但不混算。** 用户使用异常从服务稳定率中排除，但必须独立展示和提醒。
4. **未知不是成功。** 缺数据、缺 Request ID、证据冲突或无法判断时，显示未知。
5. **只对实际渠道归责。** 候选渠道仅作排障上下文。
6. **不夸大证据。** 没有客户端回执时，不宣称用户已完整收到结果。
7. **业务与运维分离。** 业务页面展示数据质量摘要，任务水位和重试统一放在数据同步状态。
8. **页面职责单一。** 聚合、趋势和请求级证据各有唯一主页面。

## 3. 信息架构

现有左侧导航名称保持：

- 模型监控
- 稳定性报表
- 客户排障
- 服务端监控
- 数据同步状态

本需求不新增“服务质量”一级菜单，也不重命名“模型监控”。

页面关系：

```text
模型监控（实时发现）
   ├─ 查看长期趋势 → 稳定性报表
   └─ 查看请求证据 → 客户排障

稳定性报表（历史衡量）
   └─ 查看问题样本 → 客户排障

客户排障（证据取证）
   └─ 返回同类趋势 → 稳定性报表

所有页面的数据维护信息 → 数据同步状态
```

## 4. 全局指标与状态

### 4.1 平台逻辑请求结果

| 状态 | 产品含义 | 是否进入平台有效请求分母 | 是否算成功 |
|---|---|---:|---:|
| 成功 | 最终完成且无明确交付异常 | 是 | 是 |
| 降级成功 | 最终成功，但发生重试、明显慢响应或可证明的体验降级 | 是 | 是，另计体验异常 |
| 平台失败 | 有效请求最终失败，责任属于平台/上游/平台网络链路 | 是 | 否 |
| 用户拒绝 | 用户配置、权限、额度、参数或未提供模型导致 | 否 | 否，独立统计 |
| 未知 | 证据不足、链路不完整或无法可靠归责 | 不进入正式稳定率；单列 | 否 |

平台逻辑请求稳定率：

> （成功 + 降级成功）÷（成功 + 降级成功 + 平台失败）

页面必须同时显示有效请求数、用户拒绝数、未知数和覆盖率，不能只显示百分比。

### 4.2 渠道尝试结果

| 状态 | 含义 |
|---|---|
| 成功 | 实际渠道完成本次上游尝试 |
| 失败 | 实际渠道明确返回失败 |
| 超时 | 实际渠道请求超时 |
| 取消 | 尝试被取消，需结合证据判定责任 |
| 未知 | 尝试存在但结果证据不足 |

渠道尝试可靠率：

> 成功尝试 ÷（成功 + 失败 + 超时）

取消和未知单列；只有 `actual_channel` 能进入渠道指标。

### 4.3 用户体验观察

状态包括：正常、慢响应、降级成功、部分返回、流式中断、连接提前结束、疑似已扣费未交付、失败、未知。

该口径回答“用户可能感受到什么”，不等于责任判定。产品上必须同时展示责任方和证据置信度。

### 4.4 数据质量状态

| 状态 | 展示规则 |
|---|---|
| 完整 | 在允许延迟内，关键采集均有覆盖 |
| 延迟 | 数据仍在更新，展示截止水位和延迟 |
| 不完整 | 存在明确缺口，结论标记暂定 |
| 不可用 | 关键采集失效，不展示正常/异常百分比结论 |
| 未知 | 尚未完成覆盖判断 |

## 5. 模型监控页面

### 5.1 页面目标

支持技术负责人和运维在分钟级发现模型、分组和实际渠道的实时异常，回答“是否需要立即干预”。

### 5.2 默认时间范围

- 默认：近 1 小时；
- 快捷范围：近 15 分钟、近 1 小时、近 6 小时、近 24 小时；
- 超过 24 小时的趋势分析引导到稳定性报表。

### 5.3 顶部状态区

必须展示：

- 业务 RPM；
- 有效逻辑请求成功率；
- 降级成功数/率；
- 平台失败数/率；
- 用户使用异常数；
- 未知请求数及占比；
- 数据截至时间与覆盖状态。

禁止：

- 将日志行数标注成用户请求数；
- 将用户拒绝计入稳定率；
- 数据不完整时显示“全站正常”。

### 5.4 分组/模型实时质量

列表字段建议：

- 分组；
- 请求模型；
- 有效逻辑请求数；
- RPM；
- 平台稳定率；
- 降级成功率；
- P95 首字延迟/P95 总耗时；
- 用户使用异常数；
- 未知占比；
- 当前事件状态。

操作：

- 点击分组/模型进入稳定性报表相同筛选条件；
- 点击异常数进入客户排障候选请求列表；
- 点击事件查看首次发生、持续时间、影响用户数和恢复状态。

### 5.5 实际渠道实时质量

仅显示确实发生过上游尝试的渠道。字段建议：

- 实际渠道 ID/名称；
- 上游站点；
- 尝试数与 RPM；
- 成功、失败、超时、取消、未知；
- 尝试可靠率；
- P95 延迟；
- 被重试绕过次数；
- 影响最终失败的请求数；
- 当前自动禁用/启用状态仅作上下文展示。

候选但未实际调用的渠道不得出现在失败排名中。

### 5.6 实时问题流

按事件聚合，不逐条刷日志。每项包含：

- 问题类型；
- 分组/模型；
- 实际渠道或“路由前”；
- 首次/最近发生时间；
- 持续时长；
- 逻辑请求数、渠道尝试数、影响用户数；
- 责任分类与置信度；
- 查看请求证据按钮。

## 6. 稳定性报表页面

### 6.1 页面目标

提供历史稳定性、渠道可靠性、用户体验和用户使用异常的统一趋势视图，用于服务质量评估、渠道治理和复盘。

### 6.2 时间与筛选

- 默认：近 7 天；
- 快捷范围：近 24 小时、近 7 天、近 15 天、近 30 天、近 90 天、自定义；
- 筛选：分组、请求模型、实际渠道、上游站点、结果分类、问题类型、证据等级；
- 管理员可按用户或令牌筛选，但默认列表脱敏。

### 6.3 报表顶部总览

四组卡片必须分开：

1. 平台逻辑请求稳定性
   - 有效逻辑请求数；
   - 成功/降级成功/平台失败；
   - 平台稳定率；
   - 对比上周期。

2. 渠道尝试可靠性
   - 实际上游尝试数；
   - 成功/失败/超时；
   - 实际渠道数量；
   - 重试率。

3. 用户体验观察
   - 慢响应；
   - 部分返回/流式中断；
   - 客户端连接提前结束；
   - 已扣费未交付候选；
   - 责任未知数。

4. 用户使用异常
   - 不存在模型；
   - 无效令牌/权限；
   - 用户余额/额度不足；
   - 参数/协议异常；
   - 受影响用户数。

### 6.4 趋势图

不得将四类指标画成一条混合曲线。至少提供：

- 平台稳定率与有效请求量；
- 渠道尝试可靠率与尝试量；
- 用户体验异常率与数量；
- 用户使用异常数量和受影响用户数；
- 未知占比和数据覆盖率。

时间粒度根据范围自适应，但同一口径版本下重叠时间窗口结果必须一致。

### 6.5 分组、模型和渠道排名

分组/模型排名基于平台逻辑请求；实际渠道排名基于渠道尝试，两者不得混用分母。

列表必须标明：

- 指标口径；
- 样本数；
- 未知数；
- 数据覆盖；
- 是否存在重试导致的降级成功；
- 与上周期变化。

样本不足时显示“样本不足”，不做高低排名。

### 6.6 问题聚合

稳定性报表只展示聚合，不展示完整请求链。聚合维度包括：

- 问题类型；
- 责任类别；
- 分组/模型；
- 实际渠道/上游；
- 发生次数；
- 影响逻辑请求数；
- 影响用户数；
- 首次/最近发生时间；
- 趋势；
- 证据置信度；
- 查看客户排障样本。

对“无实际渠道”的路由前问题，渠道字段显示“未选中渠道”，不得展示候选渠道为责任方。

### 6.7 用户使用异常专区

此区域必须醒目但与服务稳定性视觉分离。核心内容：

- 异常类型排行；
- 用户/令牌/分组/请求模型聚合；
- 连续发生次数；
- 最近发生时间；
- 是否已通知；
- 推荐沟通或配置检查动作。

提示文案统一为：

> 此类问题影响用户正常使用，但不代表平台、分组或渠道服务不稳定，因此不计入服务稳定率。

### 6.8 数据质量横幅

页面顶部固定展示：

- 数据起止范围；
- 最新水位；
- 完整度；
- 未知占比；
- 分类口径版本；
- 状态：完整/延迟/不完整/不可用。

当数据不完整时：

- 所有结论标记“暂定”；
- 不显示绿色“正常”；
- 提供跳转数据同步状态，不在本页展示任务明细。

## 7. 客户排障承接要求

本需求不直接修改客户排障，但需要向其开发负责人交付以下要求。

### 7.1 查询入口

支持按以下任一条件定位：

- Request ID；
- 用户；
- 令牌；
- 时间范围；
- 分组/模型；
- 实际渠道；
- 问题聚合跳转条件。

### 7.2 请求证据时间线

按真实发生顺序展示：

1. Nginx/入口接收；
2. 鉴权或前置拒绝；
3. 路由上下文；
4. 第一次实际渠道尝试；
5. 后续重试尝试；
6. 最终平台/边缘结束；
7. 客户端结果（仅在有受控客户端证据时）。

每条证据显示来源、时间、关键字段、置信度和缺失说明。

### 7.3 结论卡片

分别显示：

- 体验结果；
- 平台结果；
- 各渠道尝试结果；
- 责任归属；
- 证据强度；
- 未覆盖的证据层；
- 分类口径版本。

不得用服务端成功替代客户端确认，不得用候选渠道替代实际渠道。

## 8. 告警与事件管理

### 8.1 事件聚合键

优先按以下组合聚合：

> 问题类型 × 分组/模型 × 实际渠道/上游（无渠道时为路由前）

### 8.2 生命周期

- 首次发现；
- 持续中；
- 影响扩大/升级；
- 缓解中；
- 已恢复；
- 观察期结束。

### 8.3 去重与抑制

- 同一逻辑请求最多产生一个平台主事件；
- 同一请求可对多个失败实际渠道产生渠道子事件；
- 用户使用异常使用独立通知通道，不与平台故障合并；
- 采集缺口优先产生“可观测性异常”，抑制基于不完整数据的正常/恢复通知。

### 8.4 通知内容

必须包含：问题、开始时间、影响范围、样本数、受影响用户数、责任及置信度、数据完整度、客户排障入口和当前状态。

## 9. 权限与隐私

- 聚合报表默认不展示完整邮箱、令牌、IP 或原始错误正文；
- 用户级和请求级证据只对授权管理员开放；
- 页面跳转必须保留筛选条件但不在 URL 暴露敏感令牌；
- 导出内容遵循相同脱敏规则；
- 原始证据的访问应具备审计记录。

## 10. 空状态、异常状态与文案规范

| 场景 | 正确文案 | 禁止文案 |
|---|---|---|
| 没有客户端遥测 | 尚无客户端结果，无法判断客户端是否完整接收 | 客户端成功/用户已收到 |
| 仅发现错误日志 | 观察到错误日志 | 上游明确故障（无上游证据时） |
| 当前配置存在候选 | 当前配置下存在候选渠道，仅供排障参考 | 该候选渠道导致失败 |
| 历史配置不可证明 | 历史服务承诺证据不足 | 用户请求了不存在模型 |
| 采集器缺失 | 数据不可用/结论暂定 | 正常、0 个问题、100% |
| 自动禁用状态存在 | 观察到渠道状态变化 | 系统已自动止损成功（无因果证据时） |

## 11. 兼容与上线产品要求

- 旧口径在灰度期保留并明确标注“历史日志推断口径”，不得无提示覆盖；
- 新旧口径需提供同时间范围对比；
- 正式切换前至少覆盖一个完整业务周期；
- 若新口径数据异常，可回退展示旧报表，但不得将已知不准确的旧值重新标记为正式稳定率；
- 页面改造不得影响用户用量、渠道管理、Usage 日志和数据同步任务；
- 任何上线阶段均不得直接触发 NewAPI 或上游来源查询。

## 12. 验收场景

### A. 请求与重试

1. A 渠道 502、B 渠道 429、C 渠道成功：平台 1 次成功/降级成功，A/B 失败、C 成功。
2. A 失败、B 失败且最终请求失败：平台 1 次失败，A/B 各 1 次失败。
3. 内部自动测试请求：不进入业务平台稳定率和用户体验统计。

### B. 用户使用异常

1. 用户请求从未提供的模型：不影响平台/渠道稳定率，进入用户使用异常。
2. 历史时刻是否提供无法证明：进入未知，不能判定为用户问题。
3. 无效令牌、权限不足、余额不足、400、413：不影响服务稳定率，保留并可告警。

### C. 交付与体验

1. 正常文本请求有计费但零输出：标记疑似已扣费未交付。
2. 非文本请求零 completion token：不得仅凭该字段误报。
3. HTTP 200 但流式结束不完整：进入用户体验异常，不能算完全成功。
4. 客户端提前断开：责任待定；存在更强上游/边缘证据时采用更强证据。
5. 服务器完成但无客户端遥测：只能显示平台观察完成，客户端结果未知。

### D. 路由和渠道归责

1. 平台当时明确提供模型但无可用路由：平台失败，无实际渠道。
2. 候选渠道存在但未调用：不进入该渠道稳定率。
3. 渠道 ID 为 0：显示路由前/未知，不分摊给候选渠道。
4. 当前已删除的历史渠道有真实尝试证据：历史尝试仍须展示。

### E. 数据质量

1. 关键采集停止或有缺口：页面显示暂定/不可用，不能显示绿色正常。
2. Request ID 缺失：无法可靠关联时进入未知，不按时间模糊拼接。
3. 新出现的结束原因：默认进入未知/异常待分类，不得默认为成功。
4. 同一时间窗口在模型监控与稳定性报表重叠时，相同口径版本结果一致。

## 13. 产品验收门槛

- P0 场景全部通过后，才允许将新指标命名为“平台稳定率”；
- 未知占比和覆盖率必须可见；
- 新旧结果对账无请求重复、丢失或跨类不守恒；
- 页面查询只读本地事实层，不新增生产数据库压力；
- 所有跨页面链接可正确带入时间、分组、模型、实际渠道和问题类型；
- 关键文案经过技术、运维和测试联合复核；
- 客户排障尚未完成承接前，稳定性报表不得删除现有必要的问题入口。
