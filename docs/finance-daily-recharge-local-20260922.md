# 充值修正成本日明细：本机验收

## 本轮范围

补齐每日“充值修正成本（含内部）”，仅包含所属核算期间已采用历史充值版本修正的账户账单，不含经济事实账回退成本，不替代渠道已配对客户成本。既有日表 statement 中配对、客户贡献、内部扣除等字段保持原样，避免把尚未统一的来源混为完整利润。

账单先按该桶有效的历史支付/到账比例修正，再四舍五入转换为整数微美元，最后汇总。不能先取整原账单再乘比例，否则会双重取整。月汇总、供应商充值修正明细和新日明细共用此规则。渠道管理仍使用原有算法，预计余额天数不变。

只本机代码和隔离 Docker；没有生产读取/写入、补采、提交、tag、部署，不操作 8100。

## 确认并处理的问题

1. 本地真实副本 16 个上游已有月充值修正成本，旧日表仍仅依赖渠道配对账本，19 天相应字段为空。新增单独标明来源的日明细，避免冒充已配对成本。
2. 修正成本按段分别取整仍可产生微美元差异，改为逐源桶修正、取整、整数累加；原始 SQLite 账单不改写。
3. 第一版真实对账失败：某些上游只有部分日期具备比例依据，独立日计算比所属月汇总采用更多账户。不是把差额抹平：日明细改为只采用所属月组件 `CorrectionSource=充值版本` 的账户，其他账户仍保留为覆盖缺口。新增缺历史版本的两日回归，不能将后一日额外来源塞入该月已确认成本。

该范围选择意味着：查询区间变化可能使某个上游具备完整的区间充值依据，从而改变可采用的账户集合；本轮只保证相同父期间、相同来源集合下日/月精度一致，不承诺任何窗口的“已知部分”可任意相加。后续若要发布更多局部已知成本，需要单独治理月度部分来源规则，不能悄悄混入本次修改。

## 边界与缓存

- 版本在账单桶边界生效：分别使用前后版本，不把新比例追溯到前一天。
- 版本在自然日桶中途变动且比例不同：该桶不可精确修正，不按小时猜分摊。
- 中途版本比例相同：可修正；无历史版本、无日期当前配置、无效版本：不倒推。
- 临时账单、未配置活动、缺失来源不宣称完整；真实零成本保留 0。
- 独立 `recharge_correction` 对象描述已知/完整金额及账户覆盖，不借用渠道配对覆盖。
- 月缓存 schema 10、报表键 `recharge-bucket-bills-v2`、finance.js v48，拒绝旧算法缓存。中间本机试验 schema 9 不沿用。
- 历史版本追加后：缓存失效，受影响日/月同步更新，较早日期不被重新套价。仅本地合成夹具验证，没有改真实配置。

## 真实副本验收

窗口为北京时间 2026-09-01 至 2026-09-19，数据来自已下载的 2026-09-20 SQLite 副本。独立 Node 脚本通过 sqlite3 只读原库，仅查询账单及充值版本金额/生效时间，逐桶选择有效版本和计算金额。

| --- | --- |
| 来源 | 16 个充值版本上游、19 天 |
| 日明细合计 | 77,037,509,218 微美元 |
| 同口径区间/供应商合计 | 77,037,509,218 微美元，差额 0 |

| 原有数据 | 用户消费、原账单、赠送、所有原日表 statement、已配对贡献、覆盖状态保持不变 |
| 渠道管理 | 汇总、逐账户消费指标与余额保持不变 |
| 缓存 | 强制重算与缓存返回金额/日明细一致 |
| 单次本机耗时 | 重算 1928ms、缓存 70ms、渠道 271ms；不是压力测试 |

月度修正成本（含内部/扣除内部）只产生上述取整变化；其他核算口径不改。每日新列独立于现有 paired cost，也不会生成额外利润。
