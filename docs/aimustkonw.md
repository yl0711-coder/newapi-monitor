# **Monitor 与 Usage：监控和用量平台**

Monitor 与 Usage 是 NexusAPI 的两套独立内部工具，与“测试与评测”同级维护，本地工作目录为 脚本/newapi\-monitor；**代码仓库：**[GitHub · yl0711\-coder/newapi\-monitor](https://github.com/yl0711-coder/newapi-monitor)。它们围绕主站运行产生的数据工作：一套负责稳定性、渠道与上游状态的持续观察，另一套负责把用户能够理解和核对的用量数据提供给管理端与客户门户。本文说明当前代码已实现的系统边界和维护方式；某项能力是否在生产环境启用，仍应以部署配置和运行状态为准。

|**先理解边界。**主站 new\-api 仍是业务数据的权威来源；Monitor 与 Usage 是旁路的读取、派生、展示和告警系统，不应直接修改主站日志、余额、令牌、渠道或模型配置。出现口径争议时，应先回到主站和原始来源核对，再判断派生数据是否需要修复。|
|---|

## **1\. 系统定位与职责划分**

这套系统解决的不是“再做一个主站后台”，而是让技术和运营能够在不反复扫描主站日志库的情况下，看到服务是否稳定、哪些分组或模型异常、上游余额是否存在风险、用户的用量和消费明细是否能够追溯。Monitor 更偏向运行质量与异常发现；Usage 更偏向用户侧用量、管理侧汇总和事实数据沉淀。

|模块|当前职责|主要使用者|不承担的职责|
|---|---|---|---|
|Monitor|采样分组、渠道、模型和请求表现；保留快照；同步可配置的上游余额与用量；生成告警和脱敏状态页。|技术、运维、运营管理者。|不替代主站调度，不对渠道或模型执行自动变更。|
|Usage|向已授权用户展示用量总览、使用日志、筛选和受控导出；沉淀小时、日等本地事实数据。|用户、客户支持、内部管理者。|不把门户统计作为最终财务账；不扩大用户可见的数据范围。|

## **2\. 当前架构与数据链路**

旁路设计是当前实现的核心。后台工作器以只读身份、有限时间窗口和退避策略读取主站或上游来源，将结果写入自身的数据卷。管理端、门户、告警和公开状态页优先读取派生数据，因此普通页面访问不会直接触发对主站日志表的大范围扫描。

|text<br>当前数据链路<br>new\-api 主站数据库、主站登录接口、可配置上游 API<br>             │  只读 / 限窗 / 退避<br>             ▼<br>newapi\-monitor 后台工作器<br>             │<br>             ├── Monitor SQLite：指标、快照、告警状态<br>             ├── Usage Facts SQLite：小时 / 日等用量事实<br>             └── 可选 Redis：门户查询缓存<br>             │<br>             ▼<br>Monitor 管理端 ｜ Usage Portal ｜ 邮件告警 ｜ 脱敏公开状态页|
|---|

这条链路中，主站原始日志和业务配置是“源数据”，本地 SQLite 是为查询、统计和恢复而生成的“派生数据”。缓存仅用于加速，不是数据来源。页面显示为空、延迟或覆盖不全时，不能直接推断主站没有数据，也不能用零值掩盖未知状态。

## **3\. 当前已实现的能力**

|能力域|当前实现|维护时需要关注的口径|
|---|---|---|
|稳定性观察|按分组、渠道和模型聚合请求结果，区分成功、客户端中断和失败；展示延迟分位数、首字节或首 token 时间、输出速度等指标。|采样结果反映观测窗口，不等于每一条生产请求；观察时间、样本量和数据缺口必须同时看。|
|配置与快照|保留渠道、模型和倍率等历史快照；已删除渠道仍可保留最后一次快照，便于追溯。|快照用于解释“当时的配置”，不应覆盖或改写主站当前配置。|
|上游风险观察|可按配置同步 NewAPI、Sub2API 等上游余额和用量；失败时保留最近一次成功值，并实施退避。|余额刷新失败代表来源暂不可用，不代表余额为零；告警依赖完整自然日数据和倍率口径。|
|异常提醒|支持采样器离线、失败率、异常突增、客户端异常聚集等邮件告警；可基于可靠数据评估充值风险。|告警用于提示人工判断，当前不应直接触发自动下线、自动切流或自动充值。|
|客户门户|复用主站登录能力，按用户与分组范围提供用量总览、使用日志、时间与模型筛选、CSV 导出等能力。|日志和导出均有限制；退款、异常或未纳入范围的记录不能被误解为正常消费。|
|用量事实|可将历史或增量来源整理为本地小时、日等事实数据，支持汇总、核对、可靠性和审计相关检查。|事实数据是否开启、是否回填完整、覆盖到什么时间点，必须由运行配置与任务状态确认。|
|对外状态|提供公开状态页面，只暴露分组与用户可见模型维度的匿名状态。|不得暴露渠道、成本、用户、令牌、原始错误和内部拓扑。|
|可选基础设施观察|代码支持 Lightsail 指标、端到端探针、证书到期和来源锁定等观察项。|该部分由开关控制；没有开启或没有数据时，应明确显示“未启用/无数据”，不能伪装为健康。|

## **4\. 数据、权限与安全边界**

接手维护时，应先确认每类数据由谁产生、谁能读取、谁能修改。下表是现有架构的基本边界；具体账号、连接串、密钥和环境变量只保存在受控部署配置中，不写入本文或普通协作文档。

|对象|权威位置|本系统如何使用|关键限制|
|---|---|---|---|
|主站日志、渠道、用户、令牌、选项|new\-api 主站|后台工作器只读同步或限窗采样。|不授予写入权限；避免页面请求直扫主站。|
|监控指标、历史快照、告警状态|Monitor SQLite|供管理端、告警和状态页查询。|必须挂载持久化数据卷，并按 WAL 规则备份。|
|小时/日用量事实与审计信息|Usage Facts SQLite|供客户门户和内部汇总读取。|需区分来源完整性、同步状态和事实口径。|
|门户缓存|可选 Redis|加速重复查询。|缓存失效或不可用不应改变原始事实，也不能当作账务依据。|
|上游凭据与余额结果|受控配置与本地派生状态|凭据加密保存，结果按频率同步。|不向前端、公开页或导出文件下发凭据。|

角色上，主站普通用户可进入与自身权限相符的门户范围；具备较高角色的人员才可进入管理配置；最高管理角色才可修改敏感配置。门户还需要经过用户、分组与可见范围的二次校验。公开状态页和客户导出属于不同安全级别，不能因“方便查看”而共享内部明细。

## **5\. 日常维护时如何判断系统状态**

**先看工作器是否持续运行。**管理端健康检查与稳定性健康检查用于区分“页面能打开”和“采样链路在工作”。若采样器离线、最近更新时间不推进或任务处于持续退避，页面上的旧数据只能视为历史快照，不能作为当前状态。

**再看数据覆盖与更新时间。**稳定性指标需要结合观测窗口、样本量和时间范围解释；Usage 汇总需要确认事实同步范围、时区、小时或日的闭合状态。数据缺失、未回填或来源不可达应标记为未知或不完整，而非显示为零。

**最后回到权威来源核对。**当用户反馈消费、余额或某条日志不一致时，先核对主站原始记录和请求时间，再检查本地同步任务、过滤条件、退款/异常处理及缓存。派生表可修复、可重算，但不应为了对齐展示而修改源数据。

**备份与恢复要按 SQLite 的运行方式执行。**Monitor 和 Usage Facts 使用 SQLite，在线写入期间不能简单复制单个数据库文件来做备份；应使用应用提供的备份流程或一致性方式，并同时保留数据库与 WAL 相关文件。恢复后还应验证最近同步时间、记录数量和关键汇总，而不是只确认文件能打开。

## **6\. 已知问题与限制**

- 监控是受控采样和窗口统计，不是对全量生产请求的实时镜像；低频模型、短时间异常或来源延迟可能造成覆盖不足。

- 上游余额、用量与价格口径受外部接口、账号权限和同步频率影响。一次同步失败只能说明本次未获得新值，不能直接得出余额或成本结论。

- 客户门户展示、CSV 导出和内部事实表服务于可读性与日常核对；正式财务结算仍需结合主站、上游账单和原始凭据。

- 可选基础设施模块、历史全量回填和某些告警策略依赖部署开关与运行环境。文档只记录代码支持范围，不能替代对当前环境配置的检查。

- 本地 SQLite 带来查询隔离与可恢复性，也带来数据卷、备份、容量和任务延迟的运维责任；数据盘丢失会使派生历史不可用。

- 公开状态页、客户门户与管理端的数据可见范围不同。任何新增字段、导出或接口都应先检查是否会泄露渠道、价格、成本、用户或令牌信息。
