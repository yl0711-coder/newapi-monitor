# 历史共享来源：本机链路收尾验收（2026-10-10）

## 范围与结论

基线为 `v1.18.18` / `ea60179f0096f9629438404d59a08fdad44e5d95`，工作分支为 `fix/latency-quantile-display-20261009`。本记录验收的是该分支尚未提交的历史共享来源能力，不代表已发布。

本轮补齐正常鉴权路由保存后的链路验证：预览 → 有限历史归属保存 → 有界重算队列 → 渠道/经营核算报表 → 缓存更新 → SQLite 关闭重开。没有新增数据库表、外部采集任务或依赖，没有访问或修改生产，没有提交、推送、打 tag。

用户用量、渠道管理、稳定性报表、经营核算是维护范围。模型监控仅比较既有只读接口返回不被本轮修改影响，不开发其功能；客户排障、问题预警和客户维护未修改。

## 历史口径边界

- 独占时段可绑定到已核实的单个渠道；共享时段使用明确、有限的开始和结束时间，保留在账户共享成本池，不猜测渠道。
- 共享成本计一次，不按请求数、Tokens 或当前配置强行分摊，也不能据此确认内部测试成本已剔除或完整渠道毛利。
- 相邻的“独占 → 共享 → 独占”互不覆盖；重复提交返回冲突，已确认的历史区间不能被悄悄覆盖。
- 旧客户端不传 `allocation_mode` 时仍按独占处理；只读快照环境可以预览，但保存被拒绝。
- 用户已确认的 4sapi/春秋历史比例误录，与渠道 86/87/88 的共享时段是两个问题。比例更正不证明渠道归属；本次没有根据记忆中的日期写真实归属。
- 真实快照验收使用先前本机比例更正副本，SHA-256 为 `f20c4395499e8e3a442c602b72da03e8b093ca5d5bf5759e8f6514bd07a6f7bc`。其中假设的归属仅用于隔离副本测试，不是可应用到生产的方案。

## 本轮补强的测试

复用 `channel_cost_history_flow_test.go` 和 `channel_cost_history_flow_fixture_test.go`，没有另起一套报表计算器：

1. 使用正常 `RegisterRoutes`、签名 root 会话和功能开关，通过实际预览/保存接口写入三段合成历史。
2. 验证重复保存不增加历史记录或队列小时。
3. 在发布账本清单时注入失败，验证事务回滚，不留下部分金额行；队列记录保留尝试次数及错误。
4. 真正关闭 SQLite 连接并重新 `openStore`，而非只替换内存对象。旧报告金额不变，队列可继续处理。
5. 重算后通过正常报表接口读取；允许先返回旧缓存并后台更新，等待替换后核对金额，不强制绕过缓存。
6. 再次关闭重开数据库，核对落盘结果与原热缓存一致。

合成用例采用 **2:5** 充值比例，防止只对 1:1 有效：用户消耗 6、上游原值 3、修正成本 1.2；已配对两小时对应消耗 4、成本 0.8、已知贡献 3.2。第三小时共享成本仍保留，完整毛利不被虚构成已核实数字。这些是测试值，不是平台经营数据。
